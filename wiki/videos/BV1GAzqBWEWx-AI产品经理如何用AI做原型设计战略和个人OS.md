# AI产品经理：如何用AI做原型设计、战略和个人OS

## 一句话摘要

三位真实AI产品经理分别演示了用AI写战略文档、原型设计和构建个人OS的完整工作流，核心结论是：把AI当作迭代伙伴而非生成器，用纯文本和markdown文件管理上下文，每个人都在打造自己的个人AI产品。

## 核心观点

- **战略写作不是从零开始，而是和AI迭代**：先有自己的判断，再让AI做研究和扩展，然后来回打磨，而不是让AI一次性生成
- **原型优先于文档**：用AI快速构建可交互原型，比写PRD或做Figma mockup更快得到用户反馈，应该先原型再设计再文档
- **个人OS的实质是上下文管理**：用Obsidian管理markdown文件，用Cursor/Claude Code作为思考伙伴，把目标、任务、会议记录等都变成文本文件，让AI始终对齐你的意图
- **每个人都在构建自己的个人AI产品**：三位PM各自搭建的系统形态不同，但本质相同——你是自己AI产品的唯一用户和产品经理
- **核心技能是管理上下文，不是写代码**：几乎不需要vibe coding，大部分工作是组织markdown文件和配置连接

## 详细笔记

### 第一部分：Peter — 用AI写战略文档（Claude Projects）

Peter演示了用Claude Projects写Google AI Studio的2026战略备忘录：

1. **上传模板和参考资料**：将一页纸战略模板（问题、愿景、原则、方案、不做什么）和竞品调研上传到Claude Project
2. **生成初稿**：让AI基于模板和调研生成一页纸策略备忘录
3. **团队讨论和迭代**：三人实时讨论策略方向，指出AI初稿过于泛化，缺乏北极星指标和长期愿景
4. **关键洞察**：AI生成的策略容易陷入具体功能细节（如SSO、企业治理），缺少"我们要去哪里"的顶层思考

讨论中形成的策略思路：
- Google AI Studio的优势是Gemini模型的多模态能力、Google生态捆绑、不需要自己盈利
- 短期应聚焦原型市场（与Figma Make、Lovable等竞争），长期打通原型到生产的路径
- 模型进化速度太快，策略必须包含"贴近模型"这一维度

**工作方式总结**：不闭门写文档，而是带会议记录（Granola自动笔记）、调研、个人判断进入AI对话，来回迭代。

### 第二部分：Peter — 原型优先开发（Google AI Studio + AI原型工具）

Peter用AI复制了Google AI Studio的UI，然后在其上迭代新功能：

1. **用Gemini复制现有UI**：提示"请复制Google AI Studio的UI并使其可交互"，AI做到了不错的还原
2. **在基础模板上迭代**：将复制的UI作为基线模板，用自然语言添加新功能（如预置模板区域）
3. **可分享原型**：AI Studio生成的原型可以直接分享给团队成员，他们也能用AI继续修改

**核心发现**：PM用AI做原型的速度比设计师做Figma mockup还快。等到Figma出来时，原型已经测过用户了。

对设计师的影响：
- 不是取代设计师，而是民主化原型阶段——任何人都能参与
- 类比数据分析领域：Mixpanel/Amplitude让PM自己跑数据，分析师聚焦高价值问题；同理，AI原型让PM自己出原型，设计师聚焦高价值设计
- 原型不会取代清晰写作，但是让想法具象化的另一个工具
- 向VP展示原型比展示文档清单有效得多

### 第三部分：Tally — Obsidian + Cursor作为思考伙伴

Tally展示了他的个人生产力系统：

1. **Obsidian作为可视化层**：所有内容都是markdown文件，用Obsidian查看和编辑，用插件生成看板视图
2. **Cursor作为AI交互层**：同一目录在Cursor中打开，可以直接和AI对话
3. **工作流**：
   - 标记整个目录给Cursor作为上下文
   - 用Ask模式让AI审视优先级排序，逐个提问深入
   - 让AI提供改进建议，再切回Agent模式让AI执行修改
   - 审阅diff，接受或拒绝每个变更

**关键偏好**：Cursor比Claude Code更适合需要审慎修改的场景——能看到diff、逐条接受/拒绝，像结对编程。Claude Code直接输出结果，对非代码文件容易搞乱。

4. **Linear管理开发任务**：将开发任务与PM层面的initiative看板分离，通过Linear MCP让AI读取项目状态，分析发布阻塞因素，生成发布阶梯计划

5. **AI作为严厉的批评者**：让AI通过Linear MCP分析后，给出"你太保守了"的判断——这是需要听到的反馈

### 第四部分：第三位PM — Claude Code个人操作系统

最系统化的演示，展示了完整的个人OS栈：

#### 架构三层
- **行动层**：Skills、子代理、MCP/APIs——执行代码做事情
- **任务层**：Obsidian中的任务管理 + Linear中的开发任务
- **记忆/知识层**：偏好、目标、会议记录、样本——让AI对齐你的意图

#### 晨间规划工作流
输入"今天我应该做什么"，触发morning planning skill：
1. 检查Granola中的新会议记录（通过自建Granola MCP读取本地缓存）
2. 列出任务和目标
3. 给出当日聚焦、快速胜利、重复任务提醒
4. 偏移检测：当你连续几天做与目标无关的事时，AI会提醒你偏移了

#### Skills机制
- Skills存储在`.claude/skills/`目录，本质是markdown指令文件
- Claude自己可以为自己构建skill（"把这个工作流变成一个skill"）
- 示例：morning planning skill = 检查会议 → 列任务 → 读目标 → 呈现概览

#### 目标文件
- markdown文件记录12个月目标、季度目标、北极星指标
- AI参考此文件来对齐日常任务建议
- 本质是"构建一个你自己"——AI应该参考"Peter会怎么做"

#### 工具链
- Granola MCP → 读取会议记录
- Linear MCP → 读取开发任务
- Obsidian → 查看和编辑markdown
- Claude Code / Cursor → AI交互

### 第五部分：总结——三位PM的共识

1. **Peter（企业PM）**：AI最大帮助是写备忘录和原型优先开发
2. **Tally（独立PM）**：AI是思考伙伴，帮你在个人任务和开发任务上都更清晰
3. **第三位PM**：AI解决两个问题——保持专注（偏移检测/问责伙伴）和自动化不喜欢做的事（邮件、提案）

**元洞见**：三人本质上都在做同一件事——构建自己的个人AI产品，自己既是用户也是产品经理。很少vibe coding，大部分是组织markdown文件和管理上下文。

**一句话总结**：If I can summarize what I've learned about AI, it's all text files all the way down.

## 我的评注

- **赞同**：原型优先的观点非常有实战价值。传统流程是PRD→Figma→开发，但AI让PM可以跳过中间步骤直接出可交互原型，这改变了产品验证的节奏。类比数据分析领域的民主化非常精准——工具让非专业人员也能做初级工作，专业人员聚焦高价值判断。

- **赞同**："all text files all the way down"是当前AI工作流的核心洞察。markdown文件既是人可读的，也是AI可处理的，这种双重亲和力使它成为人机协作的最佳媒介。Obsidian的成功证明了这一点。

- **质疑**：三位PM都高度技术化——能用Cursor、会装MCP、能写Python脚本包装Granola缓存。这对普通PM的门槛仍然很高。他们低估了自己技能栈的特殊性。"不需要vibe coding"的前提是你已经会用命令行和IDE。

- **质疑**：AI生成的策略文档质量明显偏低——泛化、缺乏顶层思考、容易陷入细节。这说明AI在战略思维上仍然是弱项，它擅长扩展和结构化，但不擅长提出"我们要去哪里"这种判断。

- **关联**：与[[上下文工程]]深度相关——三位PM的工作本质上都是在做上下文管理：什么信息放进系统、怎么组织、何时引用。这与AI Agent工程中的上下文窗口管理是同一问题在不同尺度上的表现。与[[规范驱动开发]]也有联系——Skills本质上是编码了工作规范的markdown文件。
