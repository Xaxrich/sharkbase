# AI Agent自验证循环

## 定义

Agent 执行代码后，通过测试、类型检查、lint 等工具获取执行反馈，自动定位问题并修复，直到输出通过验证——形成"写→跑→读错→修→跑"的闭环。

## 为什么重要

传统观念里，测试是给人看的质量保障。在 Agent 时代，测试同时是给 Agent 看的**反馈信号**。没有测试，Agent 只能靠人类反复说"这不对"；有了测试，Agent 能自己跑、自己读失败输出、自己修。同样的逻辑适用于 TypeScript 编译器、ESLint、任何能输出结构化错误信息的工具——它们都是 Agent 的"感觉器官"。

这改变了一个旧认知：AI 时代测试不是更不重要了，而是**更重要了**。不是因为你需要更高覆盖率的测试，而是因为 Agent 需要自验证回路来完成工作。

## 我的判断

自验证循环在"编译能捕获的问题"上非常有效（语法错误、类型不匹配、缺少依赖）。但在运行时逻辑错误、跨服务状态不一致、性能瓶颈等深层问题上，测试本身的设计质量成为瓶颈——如果你的测试只覆盖 happy path，Agent 的自验证循环就是个安慰剂。自验证循环的有效性受限于验证信号的质量。

## 深层联系

- [[驾驭工程]] — 自验证循环是驾驭工程在"反馈层"的体现：不是给 Agent 更多工具，而是给 Agent 更好的信号
- [[上下文工程]] — 测试失败输出是上下文工程的一种形式：精准的、自动生成的上下文，比人类手写的"这不对"有效得多
- [[确定性输出]] — 类型系统和 lint 是确定性输出的一个子集：用机器判断替代 LLM 猜测
- [[AI评估体系]] — 自验证循环是 Agent 运行时的内建评估，AI 评估体系是产品层面的系统性评估，两者互补——前者解决"Agent 能不能自己发现问题"，后者解决"产品是否达到质量标准"
- [[基于属性的测试]] — PBT 是自验证循环的升级：单元测试验证"我想到的场景"，PBT 验证"我没想到但系统可能遇到的场景"。Kiro 的 EARS→属性测试贯穿线让验证信号从代码层上升到需求层
