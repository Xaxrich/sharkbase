# AI评估实战：50分钟，AI评估完整入门课程

## 一句话摘要
用 On Running 客服机器人的完整实战，演示 AI 评估从零到 LLM-as-Judge 的全流程——不是理论介绍，是 PM 真正在电子表格里标注、辩论、迭代的脏活。

## 核心观点
- AI 评估有四种类型：代码评估（二元通过/失败）、人工评估（PM 标注）、LLM-as-Judge（规模化评估）、用户评估（真实世界信号），前三种是 PM 可控的，用户评估是噪音最大的
- 人工评估是一切的基础——没有对齐的人工标签，LLM-as-Judge 的结果不可信
- 评估的核心循环是：写 prompt → 生成数据 → 建评分标准 → 人工标注 → 迭代 prompt → 再标注，反复 20-30 次
- LLM 数学能力差是真实问题——视频中发现模型把"45 分钟"误判为"超过 60 分钟窗口"
- 迭代速度和置信度是正交维度——数据少迭代快但不确定，数据多置信高但迭代慢

## 详细笔记

### 四种评估类型

1. **代码评估**：二元通过/失败，检查字符串是否存在。例：用户问"如何预订达美航空的航班"，联合航空的机器人不应回答。代码生成让这类评估比过去容易得多
2. **人工评估**：PM 或领域专家对每条回复做赞/贬判断。PM 必须亲自做，不能完全外包给标注员
3. **LLM-as-Judge**：用 LLM 模拟人类标注，是目前最主流的规模化评估方式。但需要对齐人工标签才能信任
4. **用户评估**：真实用户的反馈（拇指朝上/朝下）。信号噪音大——用户给拇指朝下可能只是对结果不满，而非系统出错

### 实战：On Running 客服机器人

**第一步：写 Prompt**

使用 Anthropic Console 的生成功能，输入需求"为 On 跑鞋设计客服机器人 prompt"。系统自动生成含变量（用户问题、产品信息、政策信息）的 prompt 模板。从 On 官网复制退货政策和产品目录，填入 prompt 变量。

**第二步：建评分标准（Rubric）**

三个核心维度：
- 产品知识：是否了解产品？
- 政策合规：是否遵循公司政策？
- 语气：回应的语气是否合适？

每个维度分好/中/差三档，团队共同定义标准。

**第三步：人工标注——电子表格是终极工具**

在 Google Sheet 中录入问题、AI 回复，逐条标注。关键发现：
- 团队辩论比标准答案更有价值——"丢了鞋盒怎么办？"不在政策中，机器人推荐联系客服团队，这是好的还是差的？值得争论
- 机器人没给出联系方式——虽然政策中有，模型没正确引用，标记为差
- 语气偏正式——On 官网机器人更活泼，生成的内容偏死板

**第四步：迭代 Prompt**

在 Anthropic Console 中使用"优化 prompt"功能，要求"更友好、不那么正式"。结果：模型添加了大量规则和 mermaid 流程图，回复反而更长更形式化。结论：AI 优化 prompt 不一定比人工调整更好，需要真实数据和判断力。

**第五步：LLM-as-Judge**

将标注数据导入 Arise 平台，配置三个评估 prompt（产品知识、政策合规、语气），让 LLM 自动评分。结果：LLM 给几乎所有回复都打了"好"——明显与人工标注不符。

**第六步：对齐人工标签**

在平台中创建人工标注队列，对比人工标签与 LLM-as-Judge 标签的匹配率。结果：产品知识匹配率 100%，语气匹配率仅 20%。这意味着语气评估 prompt 需要改进——加入"回复过长则评差"等标准。

### 评估规模指南

| 阶段 | 数据量 | 目的 |
|------|--------|------|
| 内部测试/POC | ≥1 行 | 初步验证是否值得继续 |
| 团队验证 | ~10 行 | 建立对齐，迭代 prompt |
| 生产准备 | 100+ 行 | 量化置信度，规模化评估 |

### 用户评估的陷阱

用户给拇指朝下时，你无法区分：系统确实做错了，还是用户只是对结果不满（如不符合退货条件）。需要团队讨论的核心问题：**当评估指标好但业务指标差时，如何裁决？**

## 我的评注

- **赞同**：视频最诚实的部分是承认"评估就是脏活，没有银弹"。很多人在找 LLM-as-Judge 的万能 prompt，但视频清楚表明：不对齐人工标签，LLM-as-Judge 就是垃圾进垃圾出。这个观点和 [[确定性输出]] 一脉相承——评估的确定性来自人工标注的锚点，不来自模型自身的判断
- **赞同**：PM 必须亲自做标注，不能外包。这和之前 [[BV1UZqLBJEH1-Cursor主管演示从新手到精通]] 中"你必须懂底层才能问对问题"的逻辑一致——不懂产品的人标注出的数据，模型对齐后也是对齐到错误标准
- **质疑**：视频对"代码评估"一笔带过，但实际上代码评估（断言、正则、结构化检查）是成本最低、确定性最高的评估方式，应该在 LLM-as-Judge 之前优先部署。视频中四种评估的推荐优先级应该是：代码评估 > 人工评估 > LLM-as-Judge > 用户评估，而非并列
- **质疑**：LLM 数学能力差这个发现虽然真实，但解决方案应该是 [[确定性输出]]——用代码做数学，不让 LLM 做推理，而不只是在 prompt 里加"请检查你的数学"
- **关联**：这个视频填补了 [[LLM-Agent工程实践]] 中明确提到的空白——"评估体系与开发 Harness 完全不可见"。视频提供了一套可操作的评估流程，虽然场景是客服而非 Agent，但核心方法论（黄金数据集、评分标准、对齐匹配率）是通用的
