# 亚马逊Kiro团队：规范驱动开发

## 一句话摘要

亚马逊 Kiro 团队提出用"规范驱动开发"替代 vibe coding——通过结构化的需求→设计→执行工作流，让 AI agent 从随意生成代码变为可复现、可验证地交付高质量软件。

## 核心观点

- **Vibe coding 的根本问题是人肉护栏**：当前 AI 编程依赖操作者实时纠偏，质量完全取决于人的警觉性；规范驱动开发用结构化流程替代人肉护栏。
- **EARS 格式是自然语言与形式验证之间的桥梁**：用"当...则..."的结构化自然语言写需求，既人可读又可被解析为属性测试，形成从需求到代码的贯穿线。
- **spec 是活文档，不是一次性产物**：每次变更应修改已有 spec（diff），而非创建新 spec；spec 同时是系统在时间点 t 的快照、结构化工作流和可复现工具集。
- **不要让隐含偏见锁定技术决策**：用户在 prompt 中无意提到的技术偏好（如"用 S3"）会绑定 agent 的整个决策链，应主动要求 agent 提出替代方案。
- **agent 给的上下文越少，表现越好**：Kiro 团队发现增量披露（incremental disclosure）比一次性加载全部上下文效果更好——让 agent 自行发现所需上下文。

## 详细笔记

### Kiro 是什么

Kiro 是亚马逊推出的 AI 开发工具（IDE），2026年2月公开预览，4月17日正式 GA。核心定位：不是又一个 AI 代码补全工具，而是通过**规范驱动开发（spec-driven development）**改善软件交付全流程。团队最初只有3-4人，从与 Q Developer 不同的角度切入问题。

### 规范驱动开发的三层定义

1. **工件集（Artifacts）**：系统在时间点 t 的状态快照——需求、验收标准、设计文档
2. **结构化工作流**：需求→设计→执行的三阶段流程，强制左移质量保障
3. **工具与系统**：基于结构化工件构建的可复现工具——属性测试、需求歧义检测、约束冲突检测

### EARS 格式与属性测试

EARS（Easy Approach to Requirements Syntax）用结构化自然语言表示需求，典型格式："当[条件]时，系统应[行为]"。

GA 版本的新能力：EARS 需求可直接转换为**基于属性的测试（Property-Based Testing）**。属性测试的核心思路是寻找反例来证伪不变量——找不到反例则给出高置信度。这是从需求到代码的"贯穿线（through line）"：需求→属性→测试→代码，如果属性全部满足，系统与需求一一对应。

### MCP 在规范驱动开发中的用法

MCP 不只是聊天时的辅助，应在**规范流程的每个阶段**使用：

- **需求阶段**：从 Asana/Jira 拉取已有任务，避免从零写需求
- **设计阶段**：用 fetch MCP 搜索同类产品、拉取 API 文档
- **执行阶段**：用 AWS 文档 MCP 获取最新 API 参考

关键提醒：修改 MCP 配置是缓存破坏操作，长会话中不要随意调整。

### 定制规范流程

规范流程不是铁板一块，可以定制：

- **添加 UI mock**：在设计文档中要求生成 ASCII wireframe，提前对齐界面预期
- **添加测试用例**：在任务定义中要求列出必须通过的单元测试，用 agent hooks 自动验证
- **质疑技术选型**：主动问 agent"这是惯用做法吗？有没有替代方案？"——避免 prompt 中的隐含偏见锁定决策

### Steering（引导文档）

Kiro 的 steering 等同于 Cursor Rules / memory，用于持久化项目偏好：

- 代码风格、提交规范（如 `co-authored-by: agent`）
- 部署命令和参数（如 CDK 的特定 flag）
- 非功能性需求优先级（延迟 vs 可靠性）

经验：当你经历痛苦的学习过程后，让 Kiro 把教训写入 steering 文档。

### Spec 的演进与维护

- 一个 spec 代表一个功能或问题域，不是全项目一个 spec
- 修改已有 spec 时做增量变更（amend），而非创建新 spec
- Agent 应能发现已有 spec 并修改，而非重复创建
- 删除不再相关的 spec 是合理的（如实验性的 prompt registry）

### 现有代码库（Brownfield）的适用性

Kiro 在结构良好的代码库上表现更好——高内聚、低耦合的模块让 agent 能用较少上下文完成任务。技术债多的代码库对 agent 和人类同样困难。

### 上下文管理

- 优先保持 prompt cache 命中率（可达 90-95%），而非激进压缩上下文
- 当前没有增量摘要，到达上限时执行一次性摘要（体验较差，正在改进）
- Agent 给更少上下文 + 自发现工具的组合优于一次性加载全部信息

## 我的评注

- **赞同**：将 vibe coding 的隐性问题显性化——"人肉护栏"这个表述精准。当前大多数人用 AI 编程时的确是在做实时纠偏，但很少有人意识到这是不可扩展的。规范驱动开发把纠偏从实时操作变为前置设计，这是正确的方向。
- **赞同**：EARS→属性测试的贯穿线设计思路值得借鉴。很多 AI 工具试图让 LLM 写更好的测试，但 Kiro 的思路是让需求本身就成为测试的来源——这比让 LLM 猜测该测什么更可靠。
- **质疑**：演示中 agent 多次未能发现已有 spec、重复创建、忽略更好的技术方案，说明"agent 自发现"的可靠性还不够。结构化流程的价值依赖于 agent 能正确执行它，而当前 LLM 的指令遵循能力仍有缺口。
- **质疑**：Al Harris 承认 agent 说"我完成了"但测试没通过的情况很常见——这说明规范驱动的"规范"本身可能是脆弱的。属性测试能覆盖需求层，但需求本身的完备性谁来保证？
- **与AI工程实践的关联**：视频中提到的几个模式与 [[AI Agent自验证循环]] 高度相关——属性测试是自验证的一种形式，steering 文档是 agent 记忆的一种形式，MCP 集成是 agent 工具扩展的标准模式。Kiro 的贡献在于把这些模式组织成一个连贯的工作流，而非孤立的功能点。
