# Practice Review：EARS 格式重写需求

## 任务来源

[[BV1VczqBREQ8-亚马逊Kiro团队：规范驱动开发]] — 亚马逊 Kiro 团队的规范驱动开发方法论，核心是把模糊需求转化为 EARS 格式可验证需求。

## 原始任务

将一个正在开发中的功能的自由文本需求，转化为 EARS 格式，消除歧义。产出 EARS 格式需求文档 + 歧义消除对比表。

## 实际执行过程

1. 选择真实需求："为 Sharkbase 增加 registry 状态对账能力"（正是自己正在开发的功能，实现自举）
2. 列出该功能所有期望行为（7 条）
3. 用"当……时，系统应当……"句式逐条重写
4. 检查每条需求：去除实现细节，只保留行为描述
5. 对比原始描述和 EARS 版本，识别 5 个歧义点
6. 补充验收标准

## 最终产出物

[[BV1VczqBREQ8-ears-requirements]] — 7 条 EARS 需求 + 5 条歧义消除对比

## 验收结果

| 验收项 | 是否通过 | 证据 |
|---|---|---|
| 每条需求符合 EARS 句式 | ✅ | 7 条全部使用"当……时，系统应当……"格式 |
| 需求不含实现选型 | ✅ | 未提及 Python、JSON、文件 I/O 等实现细节 |
| 外部人无歧义理解 | ✅ | 每条需求的触发条件和系统行为明确 |
| 至少识别 3 个歧义点 | ✅ | 识别 5 个歧义点（状态对账、文件完整、修复字段、不一致优先级、安全模式边界） |

## 遇到的问题

1. **R6/R7 的边界条件**：指定 BV 对账和优先检测不一致，这两个在原始需求中没有明确提及，是在 EARS 化过程中发现的隐含需求
2. **"当……时"的精确性**：写 R2 时第一次写了"当系统发现文件缺失时"，但"缺失"本身不够精确——应该明确是"registry 标记 done 但文件系统检测到文件缺失"
3. **自举效应**：用 Sharkbase 自身的需求做练习，写完 EARS 需求后直接对照 reconcile_registry.py 的实现，发现 R7（优先 inconsistent）确实是后来补的逻辑，验证了 EARS 写需求能提前发现边界条件

## 对任务本身的评价

这个任务确实训练了"产品定义与规格设计"能力。核心收获是：

- **EARS 不是格式，是思维工具**：逼你把"系统应该做什么"和"什么时候做"分开，而这两者正是需求的骨架
- **歧义识别有方法论**：不是凭感觉找歧义，而是每条需求的触发条件（"当……时"）是否可观测、行为描述（"系统应当……"）是否可验证
- **自举练习价值最高**：用自己正在开发的需求做练习，写完就能对照代码验证，比虚构场景有效得多
