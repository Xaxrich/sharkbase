## 能力归位

**主要能力**：AI辅助开发与Agent调度
**次要能力**：产品定义与规格设计、Agent架构与工作流设计
**二级能力**：AI工具链编排、Prompt驱动开发、设计-代码自动化流转

## 任务 1：用 Stitch 从需求描述生成可用设计稿

**任务目标**：给定一个真实场景需求，产出符合预期的多屏 App 设计稿
**输入材料**：一个具体的移动端需求场景（如"公司年会日程 App"）、一个视觉风格参考网站 URL
**执行动作**：
1. 将需求拆解为：App 类型 + 屏幕数量 + 每屏内容清单 + 风格要求
2. 按 `[App 类型] + [屏幕数量] + [每屏内容] + [风格要求] + [参考网站 URL]` 格式撰写 Stitch prompt
3. 在 Stitch 中提交生成，预览移动端效果（滚动、交互模拟）
4. 识别设计稿中与预期不符的区域，用 annotation 标注具体修改指令，迭代至可用
**产出物**：一套多屏 App 设计稿，附带原始 prompt 和迭代记录
**验收标准**：
- [ ] 设计稿包含需求中所有关键元素（logo、核心内容区、导航）
- [ ] 布局在移动端预览中无溢出或遮挡
- [ ] 配色/字体与参考网站风格一致
- [ ] 每屏修改不超过 2 轮 annotation 即可达标
**常见失败**：prompt 写成"帮我做一个好看的 App"这种模糊描述，导致生成结果不可控；不提供参考 URL，AI 自由发挥后风格偏离预期
**复盘记录**：记录 prompt 的哪些措辞对输出影响最大、哪类修改最容易导致风格漂移

## 任务 2：配置 IDX 的 MCP Server 并走通设计→代码链路

**任务目标**：在 IDX 中配置 Stitch MCP 和 Flutter MCP，实现从设计稿到可运行 Flutter 项目的自动流转
**输入材料**：任务 1 产出的 Stitch 设计稿、Stitch API Key
**执行动作**：
1. 在 Stitch Settings 中获取 API Key
2. 在 IDX 中发送消息配置 Stitch MCP Server，确认 MCP 面板显示连接成功
3. 配置 Flutter MCP Server，验证 Flutter SDK 状态
4. 重启 IDX，用"List my Stitch projects"验证 Stitch MCP 读取能力
5. 让 IDX 读取 Stitch 设计并生成 Flutter 代码，启动浏览器预览
**产出物**：配置好双 MCP 的 IDX 环境 + 可浏览器预览的 Flutter 项目
**验收标准**：
- [ ] "List my Stitch projects"返回正确的项目列表
- [ ] IDX 能识别 Flutter 项目结构并成功构建
- [ ] 浏览器预览中布局与设计稿基本一致（允许细节偏差）
**常见失败**：API Key 复制不完整或已过期；Flutter SDK 未安装导致 Flutter MCP 报错；MCP 配置后未重启 IDX
**复盘记录**：记录配置过程中遇到的报错及解决方式，形成个人配置排错清单

## 任务 3：替换占位内容并打包到真机

**任务目标**：将 AI 生成的占位内容替换为真实素材，构建 APK 并安装到手机
**输入材料**：任务 2 产出的 Flutter 项目、真实图片/文字素材
**执行动作**：
1. 遍历项目，识别所有占位内容（假图片、占位文字、硬编码数据）
2. 获取真实素材 URL 或本地文件，放入项目 assets 目录
3. 用自然语言指令让 IDX 批量替换占位内容，或在代码中手动替换引用
4. 请求 IDX 执行 `flutter build apk`，下载 APK 到手机安装
5. 在真机上验证启动、布局、内容正确性
**产出物**：安装到手机上可正常运行的真实内容 App
**验收标准**：
- [ ] 所有占位内容均已替换为真实素材
- [ ] APK 在 Android 手机上正常启动，无崩溃
- [ ] 关键页面布局正确，图片正常加载
**常见失败**：图片 URL 有防盗链导致加载失败，需下载到本地；构建时依赖版本冲突需要 IDX 排查；iOS 构建需要 Apple Developer 账号，流程远比 Android 复杂
**复盘记录**：记录哪类占位内容 AI 无法自动识别、构建失败时的排查路径

## 任务 4：撰写一份"AI优先 vs 传统优先"决策表

**任务目标**：针对自己工作场景，建立清晰的技术路线判断标准
**输入材料**：本文的误区部分 + 个人工作中 3-5 个真实移动端需求场景
**执行动作**：
1. 列出自己工作中的 3-5 个移动端需求，按"展示型 / 轻交互型 / 重业务逻辑型"分类
2. 对每个需求，判断：适合用 Stitch+IDX 全链路 / 只用部分环节 / 必须传统开发
3. 写明判断依据（核心功能是展示还是业务？交互复杂度？是否有视觉参考？）
4. 标注每个需求的"AI 可完成度"预估（%）
**产出物**：一份个人化的 AI 开发路线决策表
**验收标准**：
- [ ] 覆盖至少 3 个不同类型的需求场景
- [ ] 每个场景有明确的判断结论和依据
- [ ] 决策表能被非技术人员理解
**常见失败**：把所有需求都标为"AI 可做"——实际上复杂业务逻辑型需求 AI 目前无法胜任
**复盘记录**：用实际尝试结果修正预估百分比，迭代决策表的准确性
