# 6个创建Agent平台测评，哪个最好用？

> **注意**：视频标题暗示是6个Agent平台测评，实际内容是对 Andrew Ng 的 AI Agent 课程（8小时）的精要浓缩。以下笔记基于实际转录内容。

## 一句话摘要

Andrew Ng 的 Agent AI 课程核心精要：Agent 不是二元概念而是一个自主性谱系，构建 Agent 的三块基石是模型、工具和评估，而评估（Evals）是被最多人谈论却最少人真正实施的环节。

## 核心观点

- Agent AI 不是"是或不是"的二元判断，而是从低自主到高自主的谱系，构建者需要显式选择自主程度
- 构建 Agent 的三大构件：模型（LLM等）、工具（API/数据库/代码执行）、评估（Evals）——评估是被严重忽视的第三支柱
- 评估（Evals）可沿两个轴分类：客观 vs 主观、有逐例基准 vs 无逐例基准，形成四象限矩阵
- 反思（Reflection）和工具使用（Tool Use）是成熟的低自主模式；规划（Planning）和多智能体（Multi-Agent）是实验性的高自主模式
- 先建脏的再补 Evals——很多失败模式在你跑通第一批样本之前根本想不到

## 详细笔记

### 模块一：Agent AI 基础

#### 自主性谱系

以"写一篇茶道仪式文章"为例：

- **低自主工作流**：步骤预定义——列大纲 → 判断是否需要搜索 → 搜索 → 写初稿 → 反思修改 → 请求人工审核 → 终稿。每一步都是明确的。
- **高自主工作流**：给 Agent 工具（网络搜索、论文检索）和自由度，让它自己决定用什么工具、怎么反思、何时结束。输入相同，但路径由 Agent 自行规划。

低自主 = 更多控制、更可预测；高自主 = 可能超预期好，也可能完全跑偏。

Andrew Ng 明确拒绝"是不是 Agent"的二元争论，主张将一切多步骤 LLM 工作流都视为 Agent AI，放在自主性谱系上即可。

#### 三大构建块

1. **模型**：LLM 或其他 AI 模型
2. **工具**：Agent 能调用的函数——API 调用、数据库查询、代码执行、邮件发送等
3. **评估（Evals）**：衡量 Agent 输出质量、驱动迭代改进的机制。这是第三支柱，也是大多数人忽略的部分。

以"回复客户发错货邮件"为例：提取关键信息（LLM 直接完成）→ 查询订单数据库（需要工具）→ 发送回复邮件（LLM 起草 + 发送工具）。如果 Agent 回复中提到了竞争对手品牌，这就是需要 Eval 捕获的"坏行为"——写代码检测竞品名出现次数，以此为指标驱动改进。

### 模块二：反思模式（Reflection Pattern）

最直觉的设计模式：让 LLM 写初稿 → 让它反思初稿并提出改进 → 产出更好的终稿。

核心逻辑和人写文章一样——回头检查自己写的，第二版几乎总比第一版好。简单但有效。

课程提供了代码实现示例。

### 模块三：工具使用模式（Tool Use Pattern）

工具 = 扩展 Agent 能力的函数。关键原则：

- **必须显式告诉 Agent 它有哪些工具可用**，否则 Agent 不知道工具的存在
- 在系统提示中声明工具名称、用途和调用方式
- 可以严格限制（只用特定工具做特定事）或给予自由（提供工具集让 Agent 自行选择）

定义工具的方式：
- **代码函数**：直接写 Python 函数，通过框架（如 AI SDK）暴露给 Agent
- **MCP（Model Context Protocol）**：Anthropic 开发的标准化工具协议，让 Agent 无需为每个工具写自定义集成即可接入

### 模块四：评估（Evals）——最被低估的环节

#### 为什么 Evals 是必需的

没有 Evals，你只能"感觉"系统在改善，但无法客观确认。有 Evals，你就有量化指标驱动迭代。

#### 实操方法

1. 先建一个能跑的脏版本
2. 跑 10-20 个样本，记录结果
3. 从失败模式中提炼 Eval（你通常事先想不到所有失败模式）
4. 为识别出的问题编写 Eval

以发票提取 Agent 为例：跑 20 张发票后发现 Agent 会编造日期 → 手动提取真实日期作为基准 → 在 prompt 中指定输出格式 → 代码比较 LLM 提取结果与基准。

#### 四象限分类

| | 有逐例基准 | 无逐例基准 |
|---|---|---|
| **客观** | 发票日期提取：提取值 = 真实值 or ≠ | 营销文案长度：所有输出 ≤ 1000 字 |
| **主观** | 研究报告：预先标注必须覆盖的关键论点，LLM 判定覆盖度 | 图表生成：LLM 按通用标准（有轴标签？颜色可辨？文本不重叠？）打分 |

- **客观 Eval**：通常用代码实现，二元判定（对/错）
- **主观 Eval**：需要 LLM-as-Judge，因为同一概念有多种表述形式
- **有逐例基准**：每个输入都有对应的正确答案
- **无逐例基准**：统一标准适用于所有输入

#### Evals 实践建议

- 先脏后精，立即开始
- 用多样化样本捕获不同类型的错误
- 重点关注 Agent 表现不如人类的领域——那是最好的改进切入点

### 模块五：高自主模式

#### 规划模式（Planning Pattern）

Agent 自行制定执行计划，而非遵循预设路径。

示例：客户问"有没有100美元以下的圆框太阳镜？" → Agent 制定计划：1) 用 get_item_description 找圆框款式 → 2) 用 check_inventory 查库存 → 3) 用 get_item_price 筛选价格 → 执行计划得到结果。

优势：灵活，能处理不可预见的复杂查询。劣势：计划不可预测，难以排查和预期结果。

#### 多智能体模式（Multi-Agent Pattern）

将单 Agent 拆分为多个专业化子 Agent 协作。直觉：一个人做公司所有事不如一个团队各司其职。

示例：营销团队 Agent → 研究员 Agent（调研趋势）→ 图形设计师 Agent（制作可视化）→ 写手 Agent（编写报告），流水线协作。

课程对此覆盖较浅，推荐了 Anthropic 的多智能体文章作为深入阅读。

### 讲者评价

**优点**：全面覆盖 Agent AI 各组成部分，评估部分深度罕见。

**不足**：
- 偏研究/理论视角，缺少部署和产品化的实操内容
- 作业全基于代码，容易给人"必须会写代码才能做 Agent"的误解——实际上 No-Code 方案完全可行

## 我的评注

- **赞同**：将 Agent 定义为谱系而非二元类别，这是最务实的框架。工程实践中，纠结"这算不算 Agent"毫无意义，关键是选择合适的自主程度。
- **赞同**：Evals 被定位为第三支柱而非事后补充，这和工程实践完全一致。没有 Eval 的 Agent 开发就是没有测试的软件开发。
- **质疑**："先脏后精"的方法论虽然实用，但对生产环境影响考虑不足。如果是面向用户的系统，第一批脏样本就可能导致糟糕的用户体验。应该至少有基础的护栏 Eval 再上线。
- **质疑**：课程对多智能体模式覆盖太浅，而这恰好是当前工程实践最有争议也最有潜力的方向。单 Agent 加工具在很多场景下已经足够，多 Agent 的协调成本和调试难度被低估了。
- **关联**：[[AI评估体系]] 的四象限框架和 [[LLM-as-Judge]] 直接相关——主观 Eval 几乎必然依赖 LLM-as-Judge，而 LLM-as-Judge 本身的可靠性又是另一个 Eval 问题，存在递归挑战。
- **关联**：[[Agent原生架构]] 中的自主性谱系与此视频核心论点一致——Agent 的架构选择应从任务需求出发，而非从技术框架出发。
