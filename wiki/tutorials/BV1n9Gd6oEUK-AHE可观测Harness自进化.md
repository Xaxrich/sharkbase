# AHE可观测Harness自进化：从视频到可复用 Agent 工程方法

## 一句话导读
AHE 的主张是：让 harness 自进化的关键不是让 Agent 盲目改 prompt，而是把组件、经验和决策都变成可观测对象。

## 适合谁看
- 正在做 Agent、工具调用、Skill 库或长期记忆系统的开发者。
- 需要把论文方法转成工程决策和评估标准的产品/研究同学。
- 想理解 Agent “自进化”到底发生在模型、外壳、技能还是数据层的人。

## 读完你会获得什么
- 能解释 `AHE可观测Harness自进化` 解决的核心 Agent 工程问题。
- 能区分它和同系列其他 Agent 进化路线的不同位置。
- 能把论文思路转译为自己的 Agent / Skill / Harness 系统设计检查项。
- 能识别这一路线的适用边界和潜在风险。

## 核心框架
- Harness 包含 system prompt、工具描述、工具实现、中间键、技能、子代理、记忆、日志和校验。
- 组件可观测性把可编辑部分文件化，便于失败归因到具体组件。
- 经验可观测性把海量轨迹整理成概览、单题报告和原始 trace 的渐进披露结构。
- 决策可观测性要求每次编辑写明证据、根因、预计修复和潜在回归。
- 下一轮评测会验证预测是否成立，不成立的修改可以按文件粒度回滚。

## 01 人工调 harness 为什么会成为瓶颈

- 开发者通常看失败轨迹、改几句 prompt、再跑评测；任务变长后人类注意力跟不上。
- 原始轨迹可能有千万级 token，粗暴总结会丢证据，直接改 prompt 无法稳定归因。

## 02 三层可观测性

- 组件可观测性：让 prompt、工具、中间状态和记忆都有固定文件与挂载点。
- 经验可观测性：从概览 drill down 到单题报告和原始轨迹。
- 决策可观测性：每次改动都必须绑定可验证预测。

## 03 典型改动

- 例如 agent 生成正确交付物后又清理删除，AHE 可演化出 publish state guard，保护已验证文件。
- 这类改动不是模型权重变化，而是 harness 层的工程守卫变强。

## 落地检查清单
- [ ] 这个方法优化的是模型内部能力、外部 harness、技能库，还是训练数据？
- [ ] 它依赖哪些可观测证据：轨迹、日志、分数、用户反馈、测试结果？
- [ ] 它的更新是否有验证、回滚或淘汰机制？
- [ ] 它是否会引入上下文成本、技能污染、过拟合或安全审计风险？
- [ ] 如果迁移到自己的项目，最小可试验版本是什么？

## 常见误区
- 不要把“保存更多历史”直接等同于“Agent 学会了经验”。经验必须变成可检索、可验证、可控制的表示。
- 不要只看单次成功案例。Agent 进化需要跨样本证据、失败归因和回归验证。
- 不要忽略运行成本。技能库、harness 日志、动态数据和测试沙箱都会引入额外 token 或执行成本。
- 不要把自动更新直接上线。共享技能和 harness 改动尤其需要灰度、回滚和审计。
