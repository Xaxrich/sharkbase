# OpenClaw 创始人：我是如何使用OpenClaw的？

## 一句话摘要
OpenClaw 创始人 Peter 展示了一个通过 IM（WhatsApp/Telegram）控制、拥有完整电脑访问权的 AI Agent，并论证了大多数 App 将被这种通用 AI 助手融化——前提是人类保持在环内提供品味和判断。

## 核心观点

- **给 AI 电脑访问权 = 解锁无限可能**：AI 不仅是编程工具，它能调用任何你电脑上的资源（API、文件、命令行），变得极度 resourceful
- **80% 的 App 会被融化**：当 AI 助手能直接操作 API、读取上下文、自动完成任务时，独立的健身追踪、航班值机、购物 App 都变得多余
- **工具陷阱（The Tool Trap）**：给 Agent 疯狂加工具和编排层很爽，但你会花时间造工具而不是造产品——这是当前 AI 工程最大的注意力黑洞
- **长时间自主运行是虚荣指标**：让 Agent 跑 24 小时不干预不是目标，没有品味导航的输出就是 slop
- **人机循环不可省略**：好的产品在探索-构建-感受的循环中涌现，每个下一步取决于当前状态——这不是 prompt engineering 能前置的

## 详细笔记

### OpenClaw 的起源

Peter 从"退休"状态回来后，想要在手机上远程监控电脑。他发现大厂没做这个"显而易见"的事——一个能通过消息 App 操作的 AI 操作系统。最初只是把 WhatsApp 消息接上 Claude Code，一小时内就做出来了。后来发现用户需求远超预期，逐步扩展到支持多个 IM 平台。

### AI 的资源fulness 案例集

- **语音消息的意外处理**：Peter 发了一条语音，系统没被编程处理音频，但它自己找到 ffmpeg 转格式，找到 OpenAI API key 用 curl 转录，再回复——完全自主发现和组合工具
- **在摩洛哥远程修 Bug**：收到推文截图 → 识别 Bug → 检出代码仓库 → 修复 → 提交 → 回复推特——全程手机操作
- **英航值机**：AI 在浏览器中导航，找到护照文件，提取信息，完成值机。Peter 称这是" HCI 图灵测试"——在复杂网页上模拟人类操作
- **智能家居控制**：Philips Hue 灯光、温度控制、摄像头监控（曾把模糊画面中的自己误认为陌生人报警）

### 安装与使用

- 一行命令安装，全平台支持（Mac/Linux/Windows）
- 开源，网站也可审计
- 两种安装方式：npm 一键安装 / 从 Git 仓库检出运行（后者让 Agent 能读自己的源码并重编程自己）
- 配合 IM 使用：WhatsApp、Telegram、Discord 等
- 推荐 API Key 而非订阅制

### "App 融化论"

当 AI 助手拥有：完整上下文（你的习惯、日程、文件）、API 访问能力、持久记忆（上次做过的操作会记住）——大多数功能型 App 失去存在理由：

| App 类型 | 被 AI 替代的方式 |
|---------|----------------|
| 健身追踪 | 拍照→AI 识别食物→存储→提醒 |
| 航班值机 | AI 直接操作浏览器完成 |
| 购物 | AI 根据偏好推荐并下单 |
| 日程管理 | AI 读写日历，主动提醒 |
| 密码管理 | AI 有自己的 1Password vault |

关键区别：AI 助手不需要"定制 UI"，因为对话本身就是最通用的接口。

### 工具陷阱（The Tool Trap）

Peter 自述掉进过这个坑：花两个月打磨 Vibe Tunnel（手机访问终端），而不是做真正重要的事。当前社区趋势：

- **过度编排**：Claude Code manager、Codex orchestrator、多层 Agent 层级（mayor、watcher、overseer）——看起来精密，实际是复杂性幻觉
- **Rolling 陷阱**：循环执行→丢弃上下文→重新开始，本质是 token 焚烧机
- **长时间运行为荣**：让 Agent 跑 26 小时很酷，但产出质量不保证——"vanity metric"

核心判断：**能用 ≠ 应该用，能跑久 ≠ 产出好**。

### 品味与人在环中

Peter 的工作方式是渐进式探索：

1. 粗略想法 → 开始构建 → 玩/感受 → 愿景逐渐清晰 → 下一步取决于当前状态
2. 这种"人机共同演化"无法通过前置 prompt/spec 复现
3. **AI 缺乏品味**——它"spiky smart"但不导航就会产出 slop
4. 没有品味导航的自主 Agent = 大规模 slop 生成器

对"plan mode"的看法：Opus 的 plan mode 本质是 Claude 对"模型太容易触发行动"的 hack——好的做法是直接跟模型对话讨论方案，而不是强制规划阶段。

### 实际工作流

- 多终端分屏：3-5 个 checkout，有的在构建，有的在探索，有的在修复
- 不用 worktree（过度复杂），不用 MCP（不信任大上下文系统）
- 限制因素是思考速度，不是 AI 等待时间
- PR 视为"prompt request"——提取意图，自己重写
- 从 Discord 社区反馈中发现痛点，让 AI 读取代码并自动添加 FAQ 条目

## 我的评注

- **赞同**："App 融化论"的洞察有力。当 AI Agent 能直接调用 API 时，中间层 UI 确实变得多余。这不是理论推测——Peter 的英航值机案例已经证明了可行性。
- **赞同**：工具陷阱的警告精准。当前 AI 工程社区存在明显的"造工具癖"——花时间优化 Agent 编排而非交付价值，本质是延迟满足的回避。
- **质疑**：Peter 对 MCP 和大上下文系统的否定过于武断。"我不用所以没用"是幸存者偏差——他的项目规模和单人开发者模式可能让轻量方案够用，但团队协作场景下结构化工具链有其价值。
- **质疑**：安全风险被严重轻描淡写。"它能把我的门锁上"被当趣闻讲，但 AI Agent 拥有完整电脑访问权 + 智能家居控制权 + 支付能力，风险面极其可怕。一句"of course with power comes risk"不够。
- **关联**：这个视频的核心张力——AI 的 resourcefulness vs. 人类品味的不可替代性——与[[Vibe Coding]]的讨论形成互补。Vibe Coding 强调探索式开发的乐趣，Peter 则更明确地指出没有品味导航的自主产出是 slop。两者共同指向[[上下文工程]]的核心问题：如何让 AI 的能力被正确导向。
