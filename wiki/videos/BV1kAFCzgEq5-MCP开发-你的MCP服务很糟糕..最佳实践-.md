# MCP开发：你的MCP服务很糟糕..最佳实践！

## 一句话摘要

MCP Server 不是 API 的搬运工，而是 Agent 的用户界面——必须像设计产品一样设计它。

## 核心观点

- Agent 和人类在三个维度上根本不同：发现（昂贵）、迭代（缓慢）、上下文（极小），因此不能把人类用的 API 直接丢给 Agent
- MCP 开发中最重要的动词是**策展（curate）**——从海量信息中为受限的 Agent 筛选出最小可用接口
- 不要把 REST API 直接转成 MCP Server，这是违反所有 Agent 最佳实践的最快方式
- 工具数量超过 50 个（对单个 Agent 而言）就会产生性能退化，必须拆分或精简
- 你不是在构建工具，你是在构建用户界面

## 详细笔记

### 讲者背景

Jeremiah Lowin，Prefect Technologies 创始人，Apache Airflow PMC 前成员。开发了 Agent 框架 Marvin，后创建 FastMCP——目前 MCP 生态中事实标准的服务端构建框架，日下载量超 150 万。FastMCP 正在定位为 MCP 生态的高级接口，而官方 SDK 聚焦底层原语。

### 核心论证：为什么 Agent 需要自己的界面

反对"如果人类能用 API，AI 也能"的观点，理由有二：

1. **AI 并不完美**——它有限、脆弱、会犯错
2. **人类也很少直接用 API**——人类用产品（网站、SDK、客户端），而不是裸 API

Agent 与人类的三个关键差异：

| 维度 | 人类 | Agent |
|------|------|-------|
| 发现 | 便宜，做一次就行 | 昂贵，每次连接都要枚举所有工具和描述 |
| 迭代 | 快速，脚本跑一遍就完 | 缓慢，每次调用都携带完整历史，迭代是敌人 |
| 上下文 | 丰富，跨时间尺度的记忆和经验 | 极小，只有最近 200K token + 训练权重 |

### 五条最佳实践

#### 1. 结果优先，而非操作优先（Outcomes over Operations）

- 陷阱：暴露一堆原子操作（对 REST API 是最佳实践，对 MCP Server 是灾难）
- 正解：一个工具 = 一个 Agent 故事（agent story），如 `track_latest_order(email)`
- 不要让 Agent 充当编排器——它贵、慢、随机、难调试
- 工具命名面向 Agent，不面向开发者

#### 2. 扁平化参数（Flatten Arguments）

- 避免 `config: dict` 这种复杂参数——Agent 很难正确构造
- 用 Literal/Enum 代替字符串枚举——大多数 LLM 不知道 Python 的 Literal 语法，但 Enum 能工作
- 避免紧耦合参数（一个参数的取值决定另一个参数的合法输入）
- 现实问题：Claude Desktop 会把结构化参数当字符串发送，FastMCP 不得不做自动反序列化

#### 3. 指令即上下文（Instructions are Context）

- 必须为 Server 和每个 Tool 写文档和示例
- **示例是契约**——Agent 会严格模仿示例的模式（包括隐含的维度如数组长度），写两个 tag 的示例就永远只得到两个 tag
- 可用"超分布"示例来对抗这种惯性
- 注意：不要把工具用法说明放在 system prompt 里然后改了工具但忘了更新——双份文档比没文档更糟

#### 4. 错误即提示（Errors are Prompts）

- Agent 无法区分"错误信息"和"正常返回"，它只是把错误当作下一步的输入
- 不要抛 `ValueError` 或整数错误码——要写清楚发生了什么、怎么修复
- 这催生了一种渐进式信息暴露策略：在错误消息中补充首次调用时省略的用法说明，以节省 token 预算
- 但错误信息不能太吓人，否则 Agent 会永久回避该工具

#### 5. 尊重 Token 预算（Respect the Token Budget）

- 这是唯一违反就会导致 Server 不可用的规则
- 实例：某公司要把 80 个端点暴露为 MCP，假设 200K token 上下文，每个工具只能分到约 250 token——还没写完就溢出了
- Agent 不会只连你的 Server，它同时连接多个 Server，token 预算是共享的
- 50 个工具/Agent 是性能退化的警戒线
- GitHub Server 有 170 个工具，但投入了大量语义路由和优化——这是特例，不是榜样

#### 6. 无情策展（Curate Ruthlessly）

- Kelly 的故事：FiveTran 的 MCP Server 从几个工具膨胀到 188 个，又砍回 5 个——从"能用"到"好用"的产品旅程
- 工程师的自然倾向是加工具、保持向后兼容，这在 MCP 里行不通
- 先让它工作，再砍到只剩精华

### 关于 REST-to-MCP 转换

- 这是违反所有最佳实践的最快方式
- 但它作为**引导启动（bootstrap）**手段是合理的：先选几个关键端点镜像出来，验证 Agent 能用，再逐步替换为策展后的工具
- FastMCP 提供了自动转换器，Lowin 承认自己对此负有责任——这个功能太受欢迎去不掉，只能靠文档引导

### 高级话题

- **MCP 注解（Annotations）**：`readOnly` hint 能让客户端（如 ChatGPT）对非只读工具要求额外权限
- **Elicitation**：MCP 协议中让 Server 在工具执行中途向客户端请求更多输入的机制——目前客户端支持不完善，限制了使用
- **SEP-1686**：为 MCP 添加异步后台任务的提案，不改变工具设计规则，仅是客户端选择是否异步等待
- **Code Mode**：让 LLM 写代码来调用 MCP 工具序列，绕过很多迭代问题，但引入沙箱等新问题
- **客户端兼容性**：Claude Desktop 不完全遵循 MCP 规范（如哈希工具到 SQL 数据库），这限制了 Server 端可用的优化手段

## 我的评注

- **赞同**：将 MCP Server 定位为"Agent 的用户界面"而非"API 的搬运工"是极具洞察力的框架。这个类比直接把产品思维引入了 Agent 开发——不是"能不能用"，而是"好不好用"。三维度差异（发现、迭代、上下文）的拆解简洁有力，为后续所有最佳实践提供了统一的理论基础。
- **赞同**："错误即提示"和"示例是契约"这两条非常实操，是经验之谈而非理论推演。特别是示例的隐含维度会约束 Agent 行为这一观察，对实际写 MCP Server 的人有直接指导意义。
- **质疑**：50 个工具的警戒线缺乏严格依据，讲者自己也承认这是经验值。不同模型、不同工具描述长度、不同客户端实现下，这个数字差异可能很大。更实用的建议可能是"监控 token 用量"而非"数工具个数"。
- **质疑**：对"不要让 Agent 编排"的强调有些绝对。当业务逻辑本身就需要 LLM 判断时（如"根据用户意图决定走哪条路径"），编排恰恰是 Agent 的价值所在。讲者的背景是编排框架（Prefect/Airflow），这让他天然倾向于程序化编排，但不是所有场景都有确定性算法可用。
- **关联**：与 [[AI驱动的产品工作流]] 和 [[Vibe Building]] 形成对照——讲者强调的是"为 Agent 设计产品"而非"用 Agent 设计产品"，这是 AI 产品化的两个互补方向。
