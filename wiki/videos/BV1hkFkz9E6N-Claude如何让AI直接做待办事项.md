# Claude：如何让AI 直接做待办事项

## 一句话摘要

Claude Code 内置任务管理系统的发布，引发了对 AI 工程中上下文管理、跨会话持久化和多 Agent 协作范式的深度讨论。

## 核心观点

- Claude Code 的新任务系统本质上是子 Agent 的重命名，但增加了跨会话持久化能力——这是最核心的价值
- 上下文智能是下一个前沿：与其强迫 AI 生成可读的 artifact，不如让 AI 主动查询分散在不同工具中的上下文
- 复利工程应拆分为复利规划（产品侧）和复利工程（技术侧），两者关注点完全不同
- 当前任务系统缺少关键状态：缺少"待审批"、"阻塞"等工作流状态，依赖关系仅限同一会话内
- 任务系统不应与上下文智能混为一谈——任务追踪是机械的，上下文获取是智能的，两者正交

## 详细笔记

### 背景：从 Markdown 任务到内置系统

两位讨论者都经历了相似的工具迭代路径：Markdown 任务清单 → Beads（太重，反复安装卸载十几次）→ Beads Rust 移植版（数据库同步问题）→ 回归 Markdown。核心矛盾是：越强大的任务系统引入的摩擦越大，而 Markdown 虽简单但 Claude 天然就能理解和更新。

Claude Code 内置任务系统的发布打破了平衡点：它提供了跨会话持久化，同时无需额外依赖。

### 任务系统的实际运作

通过现场探索发现：

- 任务存储在用户主目录的 `~/.claude/` 下，以会话 ID 为子目录
- 工具包括：`task_create`、`task_update`、`task_list`
- 状态流转：pending → in_progress → complete
- 支持依赖关系：`blockedBy` 字段引用任务 ID，但仅在同一会话内生效
- 有 `teammate` 工具：暗示多 Agent 通信/协调能力，但文档不明确
- 环境变量 `CLAUDE_TASK_ID` 可设置，但不是全局默认

关键发现：任务系统目前是会话级的，不是全局的。跨会话共享需要手动配置或 hack。

### 上下文智能：下一个前沿

讨论者认为工程师常犯的错误是把所有信息强制写进 Markdown artifact。但现实中，上下文散落在 Slack、Google Docs、Notion、代码仓库等各处。

产品 [Unblocked](https://getunblocked.co) 被提及作为范例：连接所有知识源（repo、Slack 等），提供 MCP 接口和桌面应用。讨论者已将其集成到自己的 skill 中——当提问时，同时查询本地知识库和 Unblocked MCP，合并结果。

核心洞察：**让机器主动查询上下文，而非人工喂给它**。这是与"生成 artifact"范式根本不同的思路。

### 复利规划的提出

讨论者提出了"复利规划"（Compound Planning）的概念，作为复利工程的超集：

- 复利规划 = 头脑风暴 + 迭代规划 + 任务生成
- 当前问题：AI 在规划阶段花大量 token 更新 Markdown 文档，而规划文档本质是快照，不需要成为工作账本
- 任务系统解放了规划文档——任务用内置系统追踪，规划文档保持为思想快照

### 任务系统与上下文智能的边界

明确警告：**不要把任务管理当作上下文智能来用**。任务追踪回答"做什么"，上下文智能回答"知道什么"。如果把两者混为一谈，会得到一个既做不好追踪也做不好查询的系统。

### 当前系统的不足

通过现场逆向工程发现的问题：

1. **缺少状态**：没有"待审批"（backlog → ready）、"阻塞"（blocked）状态
2. **依赖关系局限**：仅支持同会话内的任务依赖，不支持跨项目/跨会话
3. **无全局视图**：任务按会话存储，打开新 Claude Code 实例看不到其他会话的任务
4. **无删除操作**：`task_delete` 不存在，只能改状态
5. **分类缺失**：没有项目、标签、优先级的元数据结构——本质是一个扁平的 TODO 列表

### 预测与演进方向

- Anthropic 不可避免会构建项目管理和依赖追踪——本质是做一个轻量版 Beads
- 社区会先用 hack 绕过限制（如自定义属性前缀 `engineering_*`），等官方支持后再迁移
- 复利工程插件应拆分：复利规划面向产品侧，复利工程面向技术侧
- 多 Agent 协作（编排器 + 工作者 + 测试者）因跨会话任务持久化而成为可能

## 我的评注

- **赞同**：上下文智能的提法非常精准。当前 AI 工程最大的痛点不是 AI 不够聪明，而是它看不到该看的信息。Unblocked 这类产品指向了正确方向——让 AI 成为主动查询者而非被动接收者。
- **赞同**：任务系统和上下文智能必须分离的判断很重要。很多产品失败的原因就是把"记录要做什么"和"理解发生了什么"混在一个系统里。
- **质疑**：讨论中对 Anthropic "不可避免会做项目管理"的假设可能过于确定。Anthropic 有动机保持 Claude Code 的轻量性，项目管理的复杂度可能超出他们愿意承担的范围——这更可能是生态层的职责。
- **质疑**：现场逆向工程的方式虽然有趣，但得出的一些结论（如"仅限同会话"）可能是早期版本的限制而非设计意图，不应过度推广。
- **关联**：与 [[Agent原生架构]] 的思路一致——当 Agent 有了持久化的任务账本，它就从无状态工具变成了有状态协作者。这与 [[主动式Agent]] 的范式转变互相印证。
