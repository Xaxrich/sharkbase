# Sphinx CEO：数据科学领域的Data Agent

## 一句话摘要

Sphinx CEO 阐述了为什么通用 AI 工具服务不好数据科学家——核心是数据表征和非线性探索两大难题——以及他们如何构建一个能"推回"的 Jupyter 原生 Data Agent。

## 核心观点

- **数据创造了 AI，AI 却没有回报数据**：LLM 擅长语言和代码，但表格数据、结构化时间序列不是 LLM 的母语，直接丢进 token 会得到垃圾
- **数据科学工作流是非线性的**：EDA、清洗、回溯——这些过程难以验证直到完成，和软件工程的线性 spec 驱动截然不同
- **好的 Data Agent 必须是思维伙伴，不是听话的执行者**：数据科学家期待 Agent 能对坏主意"推回"，而不只是服从指令
- **自主模式的问题在于歧义消解**：企业场景下，"欺诈最多的国家"指的是数量还是比例？这类歧义必须由人类判断
- **数据科学缺乏训练/评测数据**：不像代码可以爬 GitHub，数据科学的过程性逻辑（从想法到洞察的轨迹）几乎没有公开数据

## 详细笔记

### CEO 背景

AI 研究出身，研究过 Transformer 和 GPT，后转入量化金融做交易模型。在量化领域构建交易型 Agent 的经验——Agent 必须在足够有挑战性的环境中产生客观正确的输出才能盈利——直接影响了 Sphinx 的设计哲学。

### 为什么现有 AI 工具服务不了数据科学

两个核心问题：

1. **表征问题 (Representation Problem)**：LLM 天然理解自然语言和代码（代码本身就是人工语言），但传统数据——表格、结构化序列——不是 LLM 的原生语言。直接 tokenize 往往得到无效输出。

2. **强化/探索问题 (Reinforcement Problem)**：数据科学工作流高度非线性。EDA 阶段方向模糊，清洗过程难以即时验证，回溯是常态。软件工程 Agent 的"给 spec → 执行"模式在这里不适用。

### Sphinx 的解法

**产品形态**：Jupyter Notebook 原生的 Copilot。不做学习曲线，Notebook 怎么用就怎么用，Sphinx 在旁边提供智能协助。

**核心技术——数据转 Token 层**：人类发明了 Excel、Matplotlib、Seaborn 等工具来将数据变成视觉 token 供自己理解。Sphinx 为 AI 构建了同样的层：
- 简单二维数据 → 散点图
- 大型表格 → 聚合统计、降维、分面可视化
- 高维数据 → 维度缩减后再探索

**演示案例**：加载 CSV 后，Sphinx 自动做 EDA，发现数据呈双模态分布（两个聚类）。基于此选择先线性回归（可解释性基线），再尝试多项式拟合，最后接受人工指导改用 K-Means 聚类 + 回归的组合模型。整个过程模拟了真实人类数据科学家的决策路径。

**全栈覆盖**：从数据发现（"去 Snowflake 帮我找数据"）→ 清洗 → 建模 → 可视化/Dashboard，覆盖从原始数据到商业洞察的全链路。

### 软本体 (Soft Ontology)

企业数据有大量"暗知识"——为什么这个 pipeline 开头要跑一个奇怪的 cell、这张表的某个字段有特殊含义。Sphinx 通过 Embedding 层构建软本体：
- 每次用户接管方向盘、做不同操作时，Sphinx 记录
- 探索性偏离、异常处理等都被收集为洞察
- 后续可检索复用，弥合"原始数据理解"和"实际数据科学工作"之间的鸿沟

不做硬本体（如 Palantir 式的数月 onboarding + 专职工程师维护），而是自动积累、按用户隔离、可查看但无需手动维护。

### 从探索到生产

Sphinx 不拥有生产系统，但能将 Notebook 中积累的上下文（代码、干预记录、决策原因）转化为 Streamlit / Airflow 等生产格式。关键洞察：Notebook 代码之所以难以工程化，是因为数据科学代码本身缺乏规范性，而 Sphinx 的上下文理解能自动处理这些细微差别。

### 为什么不做成全自主 Agent

两个核心原因：

1. **歧义消解需要人类**：举例——"哪个国家欺诈最多"按数量是某国，按比例是比利时。全自主模式无法获得修复这种歧义的"功劳"，而 Copilot 模式下用户看代码和逻辑，零秒修复。

2. **现有基准不够难**：DB-Step 等基准的难度来自歧义而非数据规模/复杂度。企业实际问题涉及数千张表跨 Snowflake 的复杂数据，远超基准覆盖。

### 评测与数据问题

- DB-Step 是他们目前参考的基准（多模态、多数据类型、源自 Fintech 的真实问题），Sphinx 表现不错
- 但 CEO 坦言不热衷追逐基准，更关注真实用户场景
- **核心瓶颈**：数据科学缺乏公开的过程性数据。GitHub 上的 Notebook 大多是垃圾——没有 kernel、数据缺失、充满调试残留——无法用于训练或评测
- 长期需要自建评测体系

### 目标用户与上线

- ICP：所有用 Jupyter Notebook 且羡慕别人有 Cursor 的数据工作者——数据科学家、量化研究员、数据工程师
- 安全：零数据保留，计算在客户侧
- 公开上线，提供免费试用额度，已有用户反馈效率提升 10 倍以上

## 我的评注

- **赞同**：数据表征问题是真实且被严重低估的。社区对"LLM + 工具调用"的 Agent 范式过于乐观，但表格数据确实不是 LLM 的自然输入，需要一个"数据→AI 可理解的 token"转换层，这个洞察很有价值。

- **赞同**："思维伙伴而非服从者"的定位精准。软件工程 Agent 可以执行 spec，但数据科学需要的是探索和判断，盲目服从比拒绝执行更危险。

- **质疑**：软本体的实际效果存疑。Embedding 层自动积累的"洞察"质量如何？和真正的数据目录/数据血缘工具比，这种隐式知识能否可靠地被检索和复用？CEO 没有给出具体案例。

- **质疑**：全栈覆盖（发现→清洗→建模→可视化→生产化）的野心很大，但每个环节都有专业工具竞争。Sphinx 的差异化到底在哪一层？如果核心价值在 EDA 阶段，为什么要覆盖全链路？

- **关联**：和 [[AI Agent自验证循环]] 有深层联系——Sphinx 的"推回"机制本质上是一种验证循环，但由人类而非 Agent 自身完成。和 [[上下文工程]] 的关联也很直接：数据→token 转换层就是在为 LLM 构造正确的上下文窗口。
