# OpenClaw实战：养虾指南！ 打造你的数字员工

## 一句话摘要

将 OpenClaw 从工具升级为全职员工——赋予独立身份、邮箱和工作流，构建覆盖销售管线、CRM、会议智能、知识库的自动化系统，并分享安全、成本、记忆管理等实战经验。

## 核心观点

- **Agent 的最高形态是组织成员**：给它独立邮箱、身份、工作账号，让它端到端处理业务流程（如赞助邮件筛选、CRM 更新、会议纪要），而非仅作为辅助工具
- **安全是 Agent 系统的基石而非附加**：三层 prompt injection 防御（确定性清洗 → 隔离沙箱 → 前沿模型扫描）+ 数据分级（机密/内部/受限）+ 出站 PII 脱敏
- **多模型时代需要双提示词栈**：Claude Opus 和 GPT-5.2 的提示最佳实践截然相反（如全大写态度），必须为每个模型维护独立提示词集，并通过夜间同步审查保持一致性
- **记忆问题的根因是上下文膨胀**：用 Telegram 分话题频道隔离上下文、定期修剪加载文件、监控 context 占用率，比换外部记忆系统更有效
- **全量日志是自愈的前提**：记录每次 LLM 调用、外部服务请求、错误事件，早上只需说"看日志修问题"即可启动自动修复循环

## 详细笔记

### 赞助邮件管线：Agent 作为销售员工

给 OpenClaw 分配独立邮箱，加入公开的赞助邮箱组。邮件进入后的处理流程：

1. **隔离扫描**：确定性代码检测 prompt injection / SQL injection → 下载邮件至隔离沙箱 → 用前沿模型二次扫描
2. **评分分类**：按五维度评分（匹配度、清晰度、预算、认真程度、公司可信度），加权得出总分
3. **分级响应**：Exceptional（8+）仅升级通知团队；High 通知但不自动回复；Medium 发资质问卷；Low 礼貌拒绝；Spam 忽略
4. **低置信度升级**：无法确定评分时，通过 Telegram 通知人工审核，人工可批准或给出修正反馈
5. **上下文感知起草回复**：参考历史邮件、公司调研结果，用 Sonnet 4.6 + skill 避免 AI 味，人工审核后发送
6. **HubSpot 同步**：自动检测邮件对话推进的交易阶段，更新 CRM，漂移检测（本地记录 vs HubSpot 不一致时通知团队）

评分体系不是即插即用，经过数天迭代：让 Agent 先评分，人工判断是否合理，再反馈修正 rubric。

### CRM 系统：从联系人管理到关系智能

- **数据采集**：扫描 Gmail、日历、Slack，过滤垃圾/营销/活动邀请，仅保留有效联系人（约 250 人）
- **主动研究**：自动搜索联系人和公司的最新新闻，存入本地数据库
- **跨系统关联**：结合知识库文章、历史对话、赞助评分，形成完整上下文
- **自然语言查询**："上周跟谁聊过"、"四个月没联系谁了"
- **自动跟进**：nudge、摘要、邮件草稿
- 数据库架构：SQLite + 向量列，同时支持 SQL 查询和 RAG 语义搜索

### 会议智能

- Fathom 自动转录 → 拉取转录稿 → 匹配 CRM 中的参会人 → 提取洞察和行动项 → 本地嵌入（Nomic 模型）→ 行动项经 Telegram 审批后同步至 Todoist 和 HubSpot（自动关联正确的人和相关 deal）

### 知识库

- 通过 Telegram 保存文章/视频/推文，自动下载、摘要、评价
- 团队成员分享的文章也可通过评论触发入库，自动避免重复交叉发布
- CRM 触发时自动搜索相关公司文章并入库
- 入库流程同样经过安全扫描（清洗 → 沙箱 → 前沿模型扫描）
- 支持语义搜索，可用于视频选题和大纲生成

### 内容管线

- 在 Slack 线程中标记"potential video idea"→ Agent 读取完整线程上下文 → 查询知识库 → 搜索 X/Twitter 补充 → 创建 Asana 卡片 → 生成大纲 + 参考材料 + 包装建议（钩子、缩略图、标题）

### 双提示词栈

核心问题：不同模型的提示最佳实践相互矛盾。

- Opus：不喜欢全大写强调，倾向于过度遵循指令，不需要"喊"
- GPT-5.2：欢迎全大写，提示风格完全不同
- 解法：根目录放 Claude 优化版，`codex/` 子目录放 GPT 优化版，内容一致但风格适配
- 夜间同步审查：检查两套提示词的事实一致性，发现漂移则 Telegram 告警，人工说"修"即可
- 模型切换命令：`swap model`，自动交换目录位置和模型名称引用

### 安全架构

| 层级 | 措施 |
|------|------|
| 网络层 | Token 认证、不直接暴露互联网、周验 |
| 通道层 | DM 全权限 / Slack 群组受限 / 邮件最严 |
| 注入防御 | 确定性清洗 → 沙箱隔离 → 前沿模型扫描 → 风险评分 |
| 秘密保护 | 出站 PII 脱敏、pre-commit hook 拦截密钥模式 |
| 自动审查 | 夜间安全理事会（攻防/隐私/运维）、文件权限巡检、SSRF/SQLi 防护 |
| 数据层 | 加密备份、数据分级（机密/内部/受限）|

### 记忆与上下文管理

- 使用默认记忆系统，未接入 QMD 或外部服务
- **关键技巧一**：Telegram 分话题频道，每个频道上下文独立，减少记忆压力
- **关键技巧二**：用 `frequently status` 监控 context 占用率（满时清理或调整过期策略）
- **关键技巧三**：自动化 cron 每隔一天修剪提示词文件，平均精简约 10%，同时文件也在增长，是持续博弈

### Cron 调度策略

重任务分散在夜间运行（1:00 Instagram 分析 → 1:15 Twitter → 1:30 YouTube → 2:00 CRM → ...），避免白天抢占 token 配额。5 小时窗口需要精打细算。

### 通知批处理

按优先级分级：Critical 立即送达；High 每小时汇总（CRM 更新、理事会摘要、cron 失败）；Medium 每 3 小时汇总（常规更新）。减少 Telegram 噪音。

### 成本控制

- 本地嵌入（Nomic emb-text，零成本）
- 模型分层：Sonnet 为主力，Opus 仅在需要时调用
- 全天分散使用，避免短窗口耗尽配额
- Prompt caching（内置）
- 日历感知轮询（只在有信号时拉取）
- 便宜模型处理低要求任务

### Agents SDK 迁移

Anthropic 禁止 OAuth 方式使用 Claude 订阅后，改用 Agents SDK 路由所有 Anthropic 调用，配合自动重试、日志、prompt caching。创建统一 LLM Router 同时路由 Agents SDK 和 OpenAI Codex SDK。

### 日志与自愈

全量日志（JSONL + 数据库）：LLM 调用、外部服务、错误、通知。每日晨间："看日志修问题" → Agent 自动定位、修复。同时维护 `learning.md`、`errors.md`、`feature-request.md` 避免重复犯错。

### 夜间理事会体系

- **平台理事会**：cron 健康、代码质量、测试覆盖、提示词质量、依赖、存储、技能完整性、配置一致性、CRM 数据完整性
- **安全理事会**：攻防、隐私、运维
- **创新侦察兵**：搜索他人 OpenClaw 用例，提出新想法

### 备份

- 自动发现数据库文件 → 加密 → 上传 Google Drive → 轮转
- 每小时 Git sync：检测变更 → 自动提交 → 推送 GitHub → Telegram 通知
- 恢复流程文档化

### 团队成员用例

- **健康追踪**：Oura Ring / Apple Health / Withings 数据 → JSONL → Claude 分析 → 每日摘要 + 趋势标记 + 教练建议
- **语音备忘**：B Pendant 实时录音 → 存入记忆 → Opus 4.6 语义搜索 → 上下文问答（单向，期待双向语音交互）

## 我的评注

- **赞同**：将 Agent 视为组织成员而非工具的思路极具前瞻性。独立邮箱 + 评分 rubric + 低置信度升级的组合，是 Agent 自主权和人类可控性之间的合理平衡点。三层安全防御是生产级 Agent 系统的最低标准，视频中展示的架构值得参照。
- **质疑**：视频展示的系统极度依赖个人手工搭建和维护（多个 prompt 文件、夜间理事会、晨间修日志），这不是"数字员工"而是"数字宠物"——需要持续喂养和训练。真正的员工应该减少管理开销，而非增加。45 亿 token 用量暗示这远未达到"省心"的状态。数据分级靠规则而非架构隔离（单实例跑个人+工作），在非确定性系统上是脆弱的——一次 prompt inject 突破就可能导致跨域泄露。
- **与 AI 工程实践的关联**：双提示词栈问题本质是模型可移植性——提示词是代码，模型是运行时，切换运行时需要适配层。这是 Agent 工程从 demo 走向产品的必经挑战。全量日志 + 自愈循环的模式（Log → Diagnose → Fix）是 SRE 思维在 Agent 领域的自然延伸。
