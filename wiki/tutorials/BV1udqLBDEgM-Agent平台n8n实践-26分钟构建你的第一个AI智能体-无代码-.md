## 01 背景：为什么这个问题现在值得讨论

AI Agent 的门槛在过去一年大幅降低。n8n、Dify、Coze 这类平台让不会写代码的人也能在几十分钟内拼出一个能跑的 Agent：接一个模型、挂一个搜索工具、写几句 Prompt——看起来一切正常。

但问题恰恰出在"能跑"上。大多数人把 Demo 当成品，跳过了护栏和评测就直接上线。结果是：模型偶尔输出不当内容，工具调用失败时整个流程崩溃，Agent 的表现随着数据漂移逐渐变差，而所有这些问题都是在用户投诉之后才发现的。

这不是技术能力的问题，是认知框架的问题。很多人不知道一个完整的 Agent 应该由哪些组件构成，更不知道哪些组件可以省、哪些不能省。

## 03 概念澄清：先把关键名词讲准确

### AI Agent

- 它是什么：一个以 AI 模型为核心、能够自主调用工具、访问知识、完成用户委托任务的软件系统
- 它解决什么问题：把"人对着聊天框一次一次提问"升级为"人给一个目标，系统自主规划和执行"
- 它不是什么：它不是聊天机器人（聊天机器人没有自主规划和工具调用），也不是自动化脚本（脚本没有推理能力，只能执行预设流程）
- 和相关概念的区别：Agent vs. Workflow——Workflow 是固定流程，Agent 有条件分支和动态决策能力；Agent vs. Copilot——Copilot 辅助人完成任务，Agent 代替人完成任务
- 例子：客服 Agent 收到用户问题后，自己决定查知识库、调用退单接口、还是转人工，而不是用户点一个按钮它做一步

### 六个核心组件

| 组件 | 作用 | 一句话 |
|------|------|--------|
| Model | 提供推理和语言能力 | Agent 的大脑 |
| Tools | 让 Agent 能和外部系统交互 | Agent 的手 |
| Knowledge & Memory | 存储上下文和领域知识 | Agent 的记忆 |
| Audio & Speech | 提供语音交互能力 | Agent 的嘴和耳朵 |
| Guardrails | 约束行为、过滤不当输出 | Agent 的刹车 |
| Orchestration | 编排、监控、评测、迭代 | Agent 的管理系统 |

### 护栏（Guardrails）

- 它是什么：在 Agent 输出或行为到达用户之前，进行安全检查和内容过滤的机制
- 它解决什么问题：防止 Agent 输出有害内容、泄露隐私、偏离任务目标
- 它不是什么：它不是 Prompt 里的"请不要输出不当内容"——Prompt 约束是软的，可以被绕过；护栏是硬的，是一道独立的检查关卡
- 和 Prompt 约束的区别：Prompt 约束 = 你告诉小孩别碰热锅；护栏 = 你在炉子前装了护栏
- 例子：用 OpenAI 的 Text Moderation API 检查 Agent 输出是否包含骚扰、仇恨、色情等类别的内容，如果检测到就拦截

### 编排与评测（Orchestration & Evaluation）

- 它是什么：让 Agent 在生产环境中持续运行、持续受监控、持续改进的一套机制
- 它解决什么问题：Agent 不是搭完就完的——它会漂移、会退化、会在新场景下翻车，评测是发现这些问题的唯一手段
- 它不是什么：它不只是"部署上线"——部署只是编排的一个环节；评测也不只是"跑几个样例试试"——评测需要结构化的测试用例和量化指标
- 和测试的区别：测试是开发阶段验证功能对不对，评测是上线后持续衡量表现好不好
- 例子：维护一个评测表格，里面有不同主题和时间跨度的测试用例，每次改动 Prompt 后跑一遍，看各维度的得分变化

## 04 整体框架：Agent 的六层完整性模型

一个 AI Agent 的完整性可以用六层来衡量，从下到上：

```
┌─────────────────────────┐
│   Orchestration 编排     │  ← 持续运行与改进
├─────────────────────────┤
│   Guardrails 护栏        │  ← 安全与约束
├─────────────────────────┤
│   Audio/Speech 语音      │  ← 交互方式（可选）
├─────────────────────────┤
│   Knowledge/Memory 记忆  │  ← 上下文与知识
├─────────────────────────┤
│   Tools 工具             │  ← 行动能力
├─────────────────────────┤
│   Model 模型             │  ← 推理能力
└─────────────────────────┘
```

**底层三层（Model / Tools / Memory）是 Agent 能运行的前提，没有这三层，Agent 不成立。中间层（Audio/Speech）是交互方式的增强，视场景决定是否需要。上面两层（Guardrails / Orchestration）是 Agent 能可靠运行的前提，没有这两层，Agent 只是一个 Demo。**

关键认知：六层不是"做了更好"，而是"缺了会出事"。底层缺失导致 Agent 不能用，顶层缺失导致 Agent 不可靠。

## 05 关键机制：Agent 工作流到底是怎么运行的

以视频中搭建的"AI 研究助手"为例，拆解完整工作流：

### 触发机制

- **输入**：用户通过表单提交「研究主题」和「时间范围」
- **处理**：表单数据作为变量传入后续节点
- **输出**：结构化的用户意图（topic + time_period）
- **为什么这样设计**：表单触发比聊天触发更可控——限定输入格式，减少 Agent 处理模糊意图的负担

### 核心推理

- **输入**：结构化的用户意图 + 系统提示词
- **处理**：模型根据提示词决定是否调用工具、调用哪个工具、如何组织最终输出
- **输出**：一段基于研究结果的文字摘要
- **为什么这样设计**：提示词是 Agent 行为的"宪法"——它定义了角色、输入、任务、输出格式和约束。视频里用一个 Meta Prompt（让 ChatGPT 生成 Agent Prompt 的提示词）来快速产出初版提示词，这是一个实用的起步方法
- **代价**：提示词的调优是持续工作，初版只能让 Agent 跑起来，不能让它跑得好

### 工具调用

- **输入**：模型决定要搜索，传入搜索查询
- **处理**：调用 Perplexity API（sonar 模型），返回搜索结果
- **输出**：搜索结果回传给模型，用于生成摘要
- **为什么这样设计**：Perplexity 作为"搜索即服务"工具，让 Agent 不需要自己爬取和索引网页，直接获得结构化的搜索结果
- **适合场景**：需要实时信息、不需要深度定制搜索逻辑的场景

### 护栏检查

- **输入**：Agent 生成的摘要文本
- **处理**：通过 OpenAI Text Moderation API 检测是否包含不当内容（骚扰、仇恨、色情等），输出 flagged 标记和具体类别
- **输出**：flagged=true（有问题）或 flagged=false（没问题）
- **为什么这样设计**：内容审核放在 Agent 输出之后、用户收到之前，形成独立的检查点。这是"防御纵深"的思路——即使 Prompt 里写了"不要输出不当内容"，仍然需要一个独立的安全层
- **代价**：增加延迟和成本；可能误判（false positive 会阻止正常输出）

### 条件分支

- **输入**：护栏检查的 flagged 结果
- **处理**：Switch 节点根据 flagged 值路由——flagged=false 则继续正常流程（转音频、发邮件），flagged=true 则发送警告邮件并终止流程
- **输出**：两条互斥的执行路径
- **为什么这样设计**：这不是唯一的选择。你也可以选择让 Agent 重新生成、或在邮件中标注风险而非终止。关键是要有明确的决策逻辑，而不是忽略问题

### 评测机制

- **输入**：一组结构化测试用例（来自 Google Sheets，包含不同主题和时间范围）
- **处理**：评测触发器逐条读取测试用例，传入 Agent 工作流，收集输出，用另一个模型（如 GPT-4o-mini）按指定指标（如 helpfulness）打分
- **输出**：每条测试用例的输出结果 + 评分，写回表格
- **为什么这样设计**：评测的目的是让 Agent 的表现可量化、可比较、可追溯。改了 Prompt 之后跑一遍评测，看分数是涨了还是跌了，这是唯一可靠的迭代方式
- **代价**：评测本身需要设计测试用例和评分标准，这是一次性投入；每次跑评测需要调用 API，有持续成本

## 06 方法拆解：从零搭一个完整的 Agent 工作流

### 第一步：明确 Agent 要做什么

**目标**：定义 Agent 的角色、输入、任务、输出和约束。

**具体动作**：
1. 写一句话描述 Agent 要完成什么："一个接收研究主题和时间范围、搜索信息、生成文字摘要的 AI Agent"
2. 明确输入（用户提交什么）、输出（Agent 返回什么）、约束（信息来源要可靠、输出要适合转音频）
3. 用 Meta Prompt 快速生成初版系统提示词，然后手动调整

**判断标准**：一个不熟悉你项目的人，只看提示词就能理解这个 Agent 要做什么。

**常见坑**：提示词写得太模糊（"帮我搜索一下"），模型会自由发挥；提示词写得太死板（精确到每个字怎么写），模型会丢失灵活性。

**产出物**：一份可用的系统提示词。

### 第二步：搭建工作流骨架

**目标**：实现从输入到输出的核心链路。

**具体动作**：
1. 创建表单触发器，定义输入字段（如 topic、time_period）
2. 添加 AI Agent 节点，配置模型（如 GPT-4o）、提示词、变量映射
3. 添加工具节点（如 Perplexity 搜索），配置 API 凭证和参数
4. （可选）添加记忆节点，存储会话历史
5. 执行测试，确认核心链路能跑通

**判断标准**：Agent 能接收输入、调用工具、返回结果。输出不完美没关系，但流程不能断。

**常见坑**：忘记把表单变量映射到提示词中——Agent 收不到用户的实际输入。

**产出物**：一个能运行的最小工作流。

### 第三步：添加后处理节点

**目标**：把 Agent 输出转化为最终交付物。

**具体动作**：
1. 如需音频输出，添加 TTS 节点（如 OpenAI TTS），将 Agent 输出作为输入
2. 如需通知，添加邮件/消息节点，将结果或附件发送给用户
3. 测试完整链路：表单 → Agent → 后处理 → 交付

**判断标准**：用户能收到最终交付物（邮件、音频文件等）。

**常见坑**：音频输出包含引用标记（如 [1][2]）或元信息，听感很差——需要在提示词中明确要求"摘要优化为音频格式，不要包含引用标记"。

**产出物**：完整的"能跑通"的 Demo。

### 第四步：加护栏

**目标**：在 Agent 输出到达用户之前，拦截不当内容。

**具体动作**：
1. 在 Agent 节点之后添加内容审核节点（如 OpenAI Text Moderation）
2. 添加条件分支（Switch）：审核通过则继续正常流程，不通过则走异常路径
3. 定义异常路径的行为——可以是终止并发警告、重新生成、或继续但标注风险
4. 用包含不当内容的输入做负面测试，确认护栏生效

**判断标准**：当 Agent 输出包含不当内容时，用户不会直接收到该内容。

**常见坑**：只做内容审核，不做错误处理——如果 Perplexity 搜索失败、Agent 返回空结果，流程直接崩溃。护栏不仅是过滤内容，还包括处理异常。

**产出物**：带安全检查的工作流。

### 第五步：加评测

**目标**：建立量化衡量 Agent 表现的能力。

**具体动作**：
1. 准备评测用例表格（Google Sheets），包含不同主题、时间范围、预期行为的测试数据
2. 在工作流中添加评测触发器，连接测试用例数据源
3. 添加"收集输出"节点，将 Agent 的实际输出写回表格
4. 添加"评分"节点，用模型按指定维度（如 helpfulness、correctness、是否包含关键信息）打分
5. 跑一轮评测，建立基线分数

**判断标准**：能自动跑完所有测试用例，并输出可比较的评分结果。

**常见坑**：评测维度太少——只看 helpfulness 不够，还要看事实准确性、格式合规性、是否包含关键信息等。另外，评测用例不能只有"正常场景"，还要包含边界和负面场景。

**产出物**：评测基线 + 可重复的评测流程。

### 第六步：部署与迭代

**目标**：让 Agent 上线运行，并建立持续改进的节奏。

**具体动作**：
1. 将工作流从测试模式切换为生产模式
2. 获取生产 URL，让用户可以通过表单访问
3. 每次 Prompt 改动后，跑一遍评测，确认分数没有退化
4. 根据线上反馈和评测结果，迭代提示词和工作流

**判断标准**：Agent 能持续稳定运行，且每次改动的影响可量化。

**常见坑**：上线后不再评测。Agent 的表现会随数据漂移和模型更新而变化，不评测就不知道它在变差。

**产出物**：一个在生产环境运行的、可评测、可迭代的 Agent。

## 07 案例讲解：一个 AI 研究助手的完整搭建过程

**场景背景**：你是一个内容创作者，经常需要快速了解某个领域的最新动态。传统方式是 Google 搜索 + 手动阅读 + 自己总结，耗时且容易遗漏。

**遇到的问题**：你需要一个工具——输入主题和时间范围，自动搜索、整理、生成摘要，甚至转成音频方便通勤时听。

**按框架如何处理**：

1. **定义 Agent**：研究助手，输入是主题和时间范围，输出是文字摘要（优化为音频格式），约束是信息来源要可靠

2. **搭骨架**：n8n 中创建表单（topic + time_period）→ AI Agent 节点（GPT-4o + Perplexity 工具）→ 生成摘要

3. **后处理**：摘要 → OpenAI TTS 转音频 → Gmail 发邮件（正文 + 音频附件）

4. **加护栏**：Agent 输出 → OpenAI Text Moderation 检查 → Switch 节点分流：通过则继续，不通过则发警告邮件终止

5. **加评测**：Google Sheets 维护测试用例 → 评测触发器逐条跑 → 收集输出 → GPT-4o-mini 按 helpfulness 打分 → 结果写回表格

6. **部署上线**：切换为生产模式，获取表单 URL，用户可直接提交

**最终结果**：用户在表单中输入"Vibe Coding，过去6个月"，几分钟后收到一封邮件，里面包含研究摘要和对应的音频文件。如果摘要触发了内容审核，用户不会收到有害内容，而是收到一条警告。

**说明了什么**：核心推理链路（模型 + 工具 + 记忆）只占整个工作流的 40%，剩下 60% 是护栏和评测——而这 60% 恰恰决定了这个 Agent 能不能真正交付给用户使用。

## 08 常见误区

**误区一：Prompt 写得好就够了，不需要护栏**

- 错误理解：只要在提示词里写"不要输出不当内容"，Agent 就会遵守
- 为什么错：提示词是软约束，模型可以忽略、可以绕过、可以在边缘情况下失效。没有任何提示词能 100% 控制模型输出
- 正确理解：Prompt 约束是第一道防线，护栏是第二道。两道防线叠加，出问题的概率才会降到可接受的水平
- 应该怎么做：在 Agent 输出和用户之间，加一个独立的内容审核节点

**误区二：Agent 跑通了就可以上线**

- 错误理解：手动测试了几次，输出看起来没问题，就可以部署了
- 为什么错：手动测试只能覆盖你能想到的几个场景，覆盖不了真实用户的多样性输入。上线后遇到边界情况，Agent 可能直接崩溃或输出离谱内容
- 正确理解：跑通是起点，不是终点。上线前需要有结构化的评测，上线后需要有持续的监控
- 应该怎么做：建立评测用例集，每次改动后跑评测，确认没有退化

**误区三：评测就是跑几个例子看看效果**

- 错误理解：随便输入几个主题，觉得"看起来还行"就算评测完了
- 为什么错：这不是评测，是抽查。抽查无法量化、无法比较、无法追溯——改了 Prompt 之后，你不知道效果是变好了还是变差了
- 正确理解：评测需要结构化的测试用例、明确的评分维度、可重复的执行流程、量化的评分结果
- 应该怎么做：维护评测表格，定义评分维度（helpfulness、correctness、格式合规等），用模型自动打分，建立基线

**误区四：护栏就是过滤脏话**

- 错误理解：护栏只需要检查输出有没有骂人
- 为什么错：内容安全只是护栏的一部分。另一部分是错误处理——工具调用失败怎么办？API 超时怎么办？返回空结果怎么办？
- 正确理解：护栏包含两层：内容安全（过滤不当输出）和流程健壮性（处理异常情况）
- 应该怎么做：在设计护栏时，同时考虑"输出了不该输出的"和"该输出的没输出"两种情况

**误区五：Agent 不需要记忆**

- 错误理解：每次调用都是独立的，不需要记住之前的交互
- 为什么错：对于多轮交互的 Agent（如客服、心理咨询），没有记忆意味着每次都从零开始，用户体验极差
- 正确理解：是否需要记忆取决于场景。单次任务型 Agent 可能不需要，但多轮交互型 Agent 必须有
- 应该怎么做：评估你的 Agent 是否需要跨会话记忆，如果需要，选择合适的记忆方案（简单存储、向量数据库等）

**误区六：评测只需要一个指标**

- 错误理解：用一个 helpfulness 分数就够了
- 为什么错：helpfulness 高不代表事实准确，事实准确不代表格式合规。单维度评分会掩盖问题
- 正确理解：评测应该是多维度的——至少包括相关性、准确性、完整性和格式合规性
- 应该怎么做：根据 Agent 的任务定义 3-5 个评测维度，分别打分

**误区七：六个组件必须全做**

- 错误理解：每个 Agent 都必须具备全部六个组件
- 为什么错：语音交互不是每个 Agent 都需要的，简单的记忆存储对单次任务型 Agent 来说也是多余的
- 正确理解：Model、Tools、Memory 是必选项；Audio/Speech 是可选项；Guardrails 和 Orchestration 是生产环境的必选项，但可以是简化版
- 应该怎么做：根据场景判断哪些组件是必需的、哪些可以简化，但不要把 Guardrails 和 Orchestration 砍掉

## 09 实战清单：读完后可以马上照着做

**立即能做：**

1. 检查你现有的 Agent 工作流，对照六组件模型，列出缺了哪些组件
2. 在 Agent 输出后加一个内容审核节点（OpenAI Text Moderation 或同类服务），跑一次测试确认它能拦截不当内容
3. 写下 5 个你 Agent 最容易出问题的输入场景，作为评测用例的种子

**一周内能做：**

4. 建一个评测用例表格（Google Sheets 即可），至少包含 10 条测试数据，覆盖正常场景和边界场景
5. 在工作流中添加评测触发器，跑一轮评测，记录基线分数
6. 定义 3 个评测维度（如 helpfulness、factual accuracy、format compliance），配置自动评分

**长期要沉淀：**

7. 建立"改动 Prompt → 跑评测 → 对比基线"的标准迭代流程，每次改动都有数据支撑
8. 定期（如每月）跑一次完整评测，监控 Agent 表现是否退化
9. 积累线上异常案例，持续扩充评测用例集——你的评测集越丰富，你对 Agent 的信心就越有依据

## 10 总结

AI Agent 的搭建门槛已经很低了。一个下午，你就能用 n8n 之类的东西拼出一个能跑的 Demo。但这恰恰是最大的陷阱——"能跑"让人产生"做好了"的错觉。

视频用一套六组件模型把这个问题讲清楚了：Model、Tools、Memory 让 Agent 能跑；Audio/Speech 让它更好用；Guardrails 让它不闯祸；Orchestration 让它不退化。前三个是 Demo 的条件，后两个是生产系统的条件。

护栏不是锦上添花，是底线。你的 Agent 不一定会输出有害内容，但如果你没有检查机制，你就永远不知道它会不会。评测不是可选项，是唯一的改进手段。没有量化，你就不知道改动是在优化还是在破坏。

**一个完整的 Agent 和一个 Demo 之间的差距，就是护栏和评测。这两个组件不会让你的 Agent 更聪明，但会让它更可靠——而可靠才是交付的前提。**
