# 规范驱动开发

## 定义

用结构化的规范（spec）驱动 AI 编程全流程——先定义需求和验收标准，再设计，再执行——而非让 AI 从 prompt 直接跳到代码。规范是系统的自然语言表示，包含约束、功能需求和非功能需求，同时是工作流和可复现工具集的载体。

## 为什么重要

Vibe coding 的根本问题不是"AI 写的代码差"，而是**质量完全取决于操作者实时纠偏**。人肉护栏不可扩展——你不可能每次都注意到 agent 偷懒跳过测试、用硬编码替代配置、选了次优技术方案。规范驱动开发把纠偏从"实时操作"前置为"设计时决策"：在写代码之前就对齐需求、验收标准和设计，让 agent 在结构化约束下工作而非自由发挥。

这改变了一个认知：AI 编程工具的价值不在于"更快写代码"，而在于"更可靠地交付正确的系统"。规范是达成后者的基础设施。

## 我的判断

- **赞同**：EARS 格式→属性测试的贯穿线设计是正确的方向。让需求本身成为测试的来源，比让 LLM 猜测该测什么更可靠。这和 [[AI Agent自验证循环]] 的逻辑一脉相承——测试信号越靠近需求层，验证的置信度越高。
- **质疑**：规范驱动开发的效果高度依赖规范本身的质量。如果需求有遗漏或歧义，结构化流程只会让你更快地交付错误的东西。视频中 Kiro 团队提到的"需求歧义检测"和"约束冲突检测"是缓解手段，但自动推理技术能发现的问题范围有限——隐含假设和领域知识缺口仍然需要人类判断。
- **补充**：规范驱动开发对团队协作的价值远大于个人开发者。团队需要共享理解、需要 review 机制、需要可审计的决策记录——这些正是规范天然提供的。个人开发者可能觉得"花5分钟写需求不如花5分钟写代码"，但这个取舍在项目复杂度上升后会逆转。

## 深层联系

- [[驾驭工程]] — 规范驱动开发是驾驭工程在"工作流层"的体现：不是给 agent 更多自由度，而是用结构化流程约束 agent 的行为空间。规范就是系统级的 harness。
- [[AI Agent自验证循环]] — 属性测试是自验证循环在需求层的实现：从需求提取不变量，用测试证伪不变量，形成从需求到代码的闭环验证。
- [[确定性输出]] — EARS 格式是确定性输出在需求层的实现：用结构化自然语言替代自由文本，减少 LLM 解析需求时的非确定性。
- [[复利工程]] — 规范是可复利的资产：每次变更在已有规范上做增量修改（amend），而非从零开始。规范的积累让后续开发越来越快。
- [[上下文工程]] — 规范是上下文工程的一种系统化形式：把关键决策和约束固化在文档中，避免 agent 在长会话中遗忘或偏离。
