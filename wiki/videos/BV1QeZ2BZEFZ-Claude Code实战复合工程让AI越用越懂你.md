# Claude Code实战：复合工程，让AI越用越懂你

## 一句话摘要
Karel（Cora CTO）展示完整的复合工程闭环：规划→执行→审查→提炼，以及他的 Compound Engineering 插件如何让 Claude Code 每次使用都比上次更懂你。

## 核心观点
- **AI 能学习，所以值得投资让它学**——每次发现错误都编码化，下次不再犯，这就是复利
- **规划阶段是最便宜的纠错点**——在规划时发现方向问题，远比实现半小时后推翻更高效
- **Playwright + Opus 4 是缺失的那块拼图**——AI 控制浏览器做端到端测试，发现 bug 还能立即修复并验证，形成闭环
- **审查要从多个视角展开**——安全、架构、代码简洁性、Agent 原生程度，每个视角由独立 Agent 审查后综合为优先级排序
- **最终形态是一个命令完成一切**——`lg` 命令将规划、实现、测试、审查、营销视频全自动串联

## 详细笔记

### 复合工程哲学

四步闭环：Plan → Work → Assess → Codify。

核心洞见：AI 能学习。如果你花时间让 AI 学会你喜欢什么、它做错了什么，下次它就不会再犯。这不是单次效率提升，而是每完成一份工作都让下一份更容易——复利。

最轻量的编码化方式：直接把学到的规则写入 CLAUDE.md。更系统化的方式：使用 Compound Engineering 插件，将学习结果存入 `docs/` 目录，规划时自动检索相关条目。

### 规划阶段（Workflow Plan）

规划命令启动多个子 Agent 并行研究：

1. **代码库研究**——扫描现有代码，识别已有模式，让规划基于现实而非想象
2. **最佳实践研究**——搜索在线文章，了解社区公认的做法
3. **框架研究**——检查所用框架/库的版本和文档，避免版本不匹配

这三个子 Agent 各自有独立上下文（5000-7000 tokens），不污染主线程。

**SpecFlow Analyzer**：用用户角色模拟走一遍规划，检查是否遗漏了页面、流程或功能。解决"AI 视角太窄，只见树不见林"的问题。

**Deep Plan**：加载所有可用信息，做极限深度的规划审查。Token 消耗大，但适合代码尚未编写时的零成本验证。

**迭代规划**：看到初步规划后可以要求修改——Karel 发现规划中为每个设置创建了独立工具，建议合并为一个通用工具，AI 接受并调整。**在规划阶段纠错远比实现后纠错成本低。**

### 编码化学习（Compound）

`compound` 命令将本次会话的发现组织为持久化文档：
- 架构决策（Architecture Decisions）
- 解决方案（Solutions）
- 存入 `docs/` 目录，规划阶段自动检索

两条路径：
- **轻量**：直接告诉 Claude "记住这个"，它更新 CLAUDE.md
- **系统化**：通过插件存入结构化文档，带关键词索引，规划时按需检索

两者可同时使用，不互斥。

### 执行阶段（Workflow Work）

从规划文档出发，AI 先检查是否有未定义的问题，然后制定执行策略。

关键点：清空上下文重新开始——因为规划已经捕获了所有信息，不需要保留规划阶段的上下文。这让执行阶段的上下文更干净。

比直接"去实现它"多了两件事：检查遗漏 + 制定执行计划（thinking mode）。

### 测试阶段（Playwright + Opus 4）

Opus 4 是第一个让 Playwright 真正可用的模型。AI 可以：
- 启动浏览器，点击元素，运行 JavaScript，读取控制台日志
- 截图、录制视频、调整屏幕尺寸
- 测试 Gmail 等外部服务（传统集成测试做不到的事）

最强大的特性：**发现 bug 可以立即修复并验证**——因为 Playwright 运行在 Claude Code 内部，测试失败→修复→重新测试，形成闭环。这是"用人测试"和"用脚本测试"之外的第三条路。

### 审查阶段（Review）

多个 Agent 从不同视角审查：
- 安全视角
- 架构视角
- 代码简洁性
- Agent 原生程度（由 Replit 创始者提出，观点鲜明）

所有审查结果综合为优先级排序（P1/P2/P3），写入 TODO 文件。不是自动修复，而是**先问你要不要修**——避免在实现完成后扩大范围。

**Triage 工作流**：AI 以对话方式逐条走查发现，让人类做决策，然后自动执行决策。

### 一键全流程（LG 命令）

`lg` 命令将上述所有步骤串联：规划→实现→测试→审查→生成营销视频→创建 PR。可以运行一小时，全自动完成。

### Commands vs SubAgents vs Skills

- **Commands（命令）**：你主动触发的业务逻辑——"做这件事"。可以嵌套调用子 Agent，是工作流的编排层
- **SubAgents（子 Agent）**：独立上下文的并行执行单元——你只关心结果，不关心过程。适合审查、研究等不需要主上下文的任务
- **Skills（技能）**：即时上下文注入——当 AI 需要某领域知识时才加载，避免一次性灌入所有信息杀死上下文。技能内可包含脚本，扩展 Claude Code 本身不具备的能力

### 实用技巧

- **权限管理**：`dangerously disable sandbox` 跳过所有权限确认，前提是环境安全（不能删生产数据）。也可以逐条添加权限，第一周痛苦但之后无感
- **移动端接力**：在 Claude Code 中用 `%` 前缀将任务推到后台，在 Claude 移动 App 中继续对话。也可反向操作
- **Warp 终端**：AI 终端，可以用自然语言修复命令行错误

## 我的评注

- **赞同**：规划阶段的"多子 Agent 并行研究"设计很精巧——代码库、最佳实践、框架文档三个维度同时调研，比单纯让 AI 看代码后直接规划质量高得多。SpecFlow Analyzer 是被低估的发明：让 AI 用用户视角走一遍，专门对付"AI zoom in 太深忘记全局"这个高频失败模式。
- **赞同**：Playwright 闭环测试是真正的新能力——不是"写测试脚本"，而是"让 AI 像人一样使用产品，发现问题就修"。这种"测试→修复→验证"的循环在传统开发中需要人手动完成。
- **质疑**：视频对 Token 成本的讨论过于轻描淡写（"Max Plan 不贵"）。规划阶段三个子 Agent 各消耗 5000-7000 tokens，加上 Deep Plan 和审查的多个 Agent，一次完整流程的 Token 消耗相当可观。对独立开发者或小团队，这并非零成本。
- **质疑**：`lg` 一键全流程的演示不够充分——只说"能运行一小时"，但没有展示结果质量。全自动化的风险在于：如果某个环节出错（比如规划方向偏了），后续所有步骤都在错误方向上叠加。
- **关联**：[[复利工程]] 的概念在这个视频中得到了最完整的实操展示。之前的视频更多是理念阐述，这次是端到端的工作流演示。[[上下文工程]] 在 Skills 的即时加载机制中体现最清晰——不是把所有知识塞进提示词，而是按需拉取。
