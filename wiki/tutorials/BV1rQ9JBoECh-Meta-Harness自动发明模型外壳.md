# Meta-Harness自动发明模型外壳：从视频到可复用 Agent 工程方法

## 一句话导读
Meta-Harness 把模型外部的检索、上下文组织、工具编排和状态管理视为可优化代码，让系统不只卷模型权重，而是自动改进模型真正工作的外壳。

## 适合谁看
- 正在做 Agent、工具调用、Skill 库或长期记忆系统的开发者。
- 需要把论文方法转成工程决策和评估标准的产品/研究同学。
- 想理解 Agent “自进化”到底发生在模型、外壳、技能还是数据层的人。

## 读完你会获得什么
- 能解释 `Meta-Harness自动发明模型外壳` 解决的核心 Agent 工程问题。
- 能区分它和同系列其他 Agent 进化路线的不同位置。
- 能把论文思路转译为自己的 Agent / Skill / Harness 系统设计检查项。
- 能识别这一路线的适用边界和潜在风险。

## 核心框架
- 模型能力不是只由权重决定，harness 决定信息如何存储、检索、呈现和执行。
- 优化对象从 prompt 扩展到一整层系统代码，包括检索逻辑、状态管理和工具调用流程。
- 方法强调读取完整历史、失败日志和版本差异，而不是只看压缩摘要。
- 每一轮新 harness 的代码、分数和轨迹都会写回文件系统，形成可检索经验。
- 价值在于把工程师调参式的 harness engineering 变成可评估、可追溯、可迭代的闭环。

## 01 问题背景：为什么不能只优化模型

- 落地系统的效果取决于模型与 harness 的共同作用。模型给出能力上限，harness 决定能否把能力稳定释放出来。
- 很多失败并不是模型不会，而是上下文、检索、工具顺序或状态边界设计不当。

## 02 机制：把 harness 当成可搜索的工程对象

- 系统保留不同 harness 版本、运行轨迹、分数变化和失败案例。
- 优化器不是只读一个总结，而是像工程师查事故档案一样检索历史，定位哪个设计导致退化。
- 新版本 harness 会再次评测，并把结果写回历史，供下一轮优化使用。

## 03 工程启发

- Agent 项目应把 prompt、检索策略、工具描述、状态守卫和校验逻辑都文件化。
- 每次改动都应配套评测与失败样本，否则无法知道 harness 变强还是只是在某组题上过拟合。

## 落地检查清单
- [ ] 这个方法优化的是模型内部能力、外部 harness、技能库，还是训练数据？
- [ ] 它依赖哪些可观测证据：轨迹、日志、分数、用户反馈、测试结果？
- [ ] 它的更新是否有验证、回滚或淘汰机制？
- [ ] 它是否会引入上下文成本、技能污染、过拟合或安全审计风险？
- [ ] 如果迁移到自己的项目，最小可试验版本是什么？

## 常见误区
- 不要把“保存更多历史”直接等同于“Agent 学会了经验”。经验必须变成可检索、可验证、可控制的表示。
- 不要只看单次成功案例。Agent 进化需要跨样本证据、失败归因和回归验证。
- 不要忽略运行成本。技能库、harness 日志、动态数据和测试沙箱都会引入额外 token 或执行成本。
- 不要把自动更新直接上线。共享技能和 harness 改动尤其需要灰度、回滚和审计。
