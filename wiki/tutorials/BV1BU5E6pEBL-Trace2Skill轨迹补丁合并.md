# Trace2Skill轨迹补丁合并：从视频到可复用 Agent 工程方法

## 一句话导读
Trace2Skill 把成功与失败轨迹先拆成技能补丁，再通过并行分析和层级合并形成可迁移技能，避免顺序更新造成技能漂移。

## 适合谁看
- 正在做 Agent、工具调用、Skill 库或长期记忆系统的开发者。
- 需要把论文方法转成工程决策和评估标准的产品/研究同学。
- 想理解 Agent “自进化”到底发生在模型、外壳、技能还是数据层的人。

## 读完你会获得什么
- 能解释 `Trace2Skill轨迹补丁合并` 解决的核心 Agent 工程问题。
- 能区分它和同系列其他 Agent 进化路线的不同位置。
- 能把论文思路转译为自己的 Agent / Skill / Harness 系统设计检查项。
- 能识别这一路线的适用边界和潜在风险。

## 核心框架
- 单条轨迹局部，但大量轨迹中反复出现的修复方式能反映任务域规律。
- 系统不直接把轨迹贴进文档，而是提炼插入、删除、更新等 skill patch。
- 成功轨迹侧重提取关键成功行为，失败轨迹需要多轮诊断和最小修复验证。
- 并行 patch 避免早期偶然错误污染后续更新。
- 层级合并用于去重、解冲突，并拒绝引用不存在文件或范围冲突的补丁。

## 01 为什么不是顺序更新

- 顺序更新会让后续分析看到已被前面案例改过的技能，容易围绕偶然版本继续修补。
- 并行分析让每条轨迹独立给出证据，最后再统一归纳。

## 02 成功与失败的不同价值

- 成功轨迹告诉系统哪些动作真正促成结果。
- 失败轨迹需要读日志、输入输出和标准答案，确认根因可复现，避免生成假补丁。

## 03 技能合并的工程约束

- 合并不只是让模型总结，还需要文件存在性、编辑范围冲突和格式校验。
- 这使 skill evolution 更像受约束的代码 review，而不是自由写作。

## 常见误区
- 不要把“保存更多历史”直接等同于“Agent 学会了经验”。经验必须变成可检索、可验证、可控制的表示。
- 不要只看单次成功案例。Agent 进化需要跨样本证据、失败归因和回归验证。
- 不要忽略运行成本。技能库、harness 日志、动态数据和测试沙箱都会引入额外 token 或执行成本。
- 不要把自动更新直接上线。共享技能和 harness 改动尤其需要灰度、回滚和审计。
