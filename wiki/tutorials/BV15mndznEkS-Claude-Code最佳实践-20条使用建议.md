# Claude Code 实战 20 条：和 AI 结对编程的正确节奏

**一句话导读：** Claude Code 不是"你说一句它写一行"的代码生成器，而是一个能力很强但极度急躁的工程师——你越能管住它先想后做，它交付的质量就越高。

---

**适合谁看：**

- 有产品思维但代码能力有限的 PM，想用 AI 工具把想法变成可运行的产品
- 已经在用 Claude Code 但经常陷入"改了又改、越改越乱"循环的人
- 刚接触 AI 编程工具，不知道从哪里起步的非技术从业者
- 带团队的 Tech Lead，想制定团队使用 AI 编程工具的规范
- 内容创作者或独立开发者，想提高从想法到原型的速度

---

**读完你会获得什么：**

- 理解 Claude Code 的核心工作模式：它不是聊天机器人，是需要管理的合作者
- 掌握"规划→拆解→编码→校验"的完整流程，避免一上来就让 AI 写代码
- 知道在 AI 编码出错时，如何给上下文、如何打断、如何让它重新思考
- 能设置 CLAUDE.md、权限文件、GitHub 集成，让 Claude Code 工作更顺畅
- 识别出哪些"高级功能"（子代理、Hooks、MCP）适合什么阶段使用，不会被名词吓到

## 01 背景：为什么这个问题现在值得讨论

AI 编程工具的门槛正在快速降低。Claude Code、Cursor、Windsurf 这类工具让不会写代码的人也能构建可运行的应用。但一个现实是：**大多数人拿到的不是"AI 帮你写代码"的体验，而是"AI 帮你制造混乱"的体验。**

原因是，AI 编程工具的能力和急躁程度是成正比的。Claude Code 特别典型——它极其渴望立刻动手写代码。你给一个需求，它不等你想清楚就开始安装依赖、创建文件、生成一整堆代码。如果你没有在规划阶段把方向锁死，它会在错误的方向上全速前进，产出一堆你不需要的东西，然后你要花更多时间去清理。

这不是工具的 bug，是它的设计特征：Claude Code 被优化为"快速响应"，而不是"等你慢慢想"。所以使用它的核心技能，不是提示词工程，而是**项目管理能力**——你要扮演 Tech Lead 的角色，管住一个急躁但能力强的工程师。

## 02 核心判断：视频真正想讲的不是 20 个技巧

表面上，这是一个"20 个 Claude Code 使用技巧"的教程视频。但作者真正在反复强调的只有一件事：

**规划的质量决定编码的结果。AI 编程工具最大的风险不是写错代码，而是在你没想清楚之前就开始写。**

视频里所有高价值技巧都围绕这个判断展开：

- Plan Mode——强制 AI 先想后做
- Spec → Todo → Code——把想法拆成可审计的文档链
- 反复打断和纠偏——因为 AI 总是过度执行
- 上下文管理——因为对话越长，AI 越容易跑偏

20 个技巧只是入口。真正的主线是：**如何在 AI 急于编码时，建立一套"慢下来"的工作流。**

## 03 概念澄清：先把关键名词讲准确

### Plan Mode

- **它是什么**：Claude Code 的一个模式，AI 只输出分析和方案，不写代码
- **它解决什么问题**：防止 AI 在你还没想清楚时就动手
- **它不是什么**：不是"让 AI 更聪明"，只是限制它的输出范围
- **和相关概念的区别**：和普通对话模式的区别是，Plan Mode 下 AI 不会创建或修改文件
- **操作方式**：按 `Shift+Tab` 切换到 Plan Mode；如果 AI 在普通模式下要开始写代码，按 `Escape` 取消

### Spec → Todo → Code 流程

- **它是什么**：一种分阶段的工作方法——先写需求规格（Spec），再拆任务清单（Todo），最后才写代码（Code）
- **它解决什么问题**：防止需求模糊导致的返工，让每一步都可审计
- **它不是什么**：不是瀑布模型，每个 Milestone 内部仍然可以迭代
- **和相关概念的区别**：和"直接让 AI 写代码"的区别是，中间多了两层文档作为锚点

### CLAUDE.md

- **它是什么**：项目根目录下的一个 Markdown 文件，Claude Code 每次对话都会读取它作为上下文
- **它解决什么问题**：让 AI 记住项目背景、技术偏好、个人风格，不需要每次重复说明
- **它不是什么**：不是配置文件，是自然语言的项目记忆
- **一个简单例子**：在 CLAUDE.md 里写"我是一名产品经理，代码经验有限，请在修改代码时解释你的技术选择"，之后每次对话 AI 都会遵循这个偏好

### /compact 和 /clear

- **/compact 是什么**：压缩对话历史，保留摘要，腾出上下文空间
- **/clear 是什么**：完全清除对话历史
- **区别**：/compact 保留关键信息，适合在 Milestone 之间切换时使用；/clear 是重新开始，适合方向完全改变时使用

### Output Style

- **它是什么**：Claude Code 的一个设置，控制 AI 输出时是否附带解释
- **两种模式**：`explanatory`（AI 在编码时插入解释框，说明为什么这样做）和 `learning`（AI 让你亲手写部分代码）
- **适用场景**：explanatory 适合想理解架构的非技术用户；learning 适合想练习编码的人

### Subagent（子代理）

- **它是什么**：独立的 AI 对话窗口，有自己的上下文和任务描述
- **它解决什么问题**：避免把所有任务塞进一个对话，防止主对话上下文被污染
- **一个简单例子**：让一个子代理专门做文档更新，另一个做安全审计，主代理负责协调

### MCP Server

- **它是什么**：为 Claude Code 提供额外能力的插件服务（如代码搜索、UI 截图测试、Figma 设计稿读取）
- **注意事项**：每个 MCP Server 会加载额外上下文到提示词中，同时运行太多会挤占有效上下文空间

## 04 整体框架：Claude Code 工作流的四阶段模型

视频里的 20 条技巧可以归入四个阶段，形成完整的工作流：

```mermaid
flowchart TD
    A[阶段一：规划] --> B[阶段二：编码]
    B --> C[阶段三：校验]
    C --> D[阶段四：进阶]
    
    A --> A1[Plan Mode]
    A --> A2[探索方案]
    A --> A3[写 Spec]
    A --> A4[拆 Todo]
    A --> A5[配置 CLAUDE.md]
    
    B --> B1[选 Output Style]
    B --> B2[语音输入]
    B --> B3[先跑 UI + 假数据]
    
    C --> C1[Escape 打断纠偏]
    C --> C2[具体反馈 + 截图 + 日志]
    C --> C3[think ultra hard]
    C --> C4[更新 Todo]
    C --> C5[/compact 上下文]
    C --> C6[Git 提交]
    
    D --> D1[自定义命令]
    D --> D2[子代理]
    D --> D3[Hooks]
    D --> D4[MCP Server]
    D --> D5[并行会话]
    
    C -->|纠偏后可能回到| A
    C -->|通过后进入下一 Milestone| A
```

**文字解释：**

这个框架的核心是**循环**，不是线性推进。每完成一个 Milestone，你都要回到规划阶段：更新 Spec、更新 Todo、/compact 上下文，然后才进入下一个 Milestone 的编码。视频作者反复遇到 AI 跑偏的情况——用了过时模型、加了不需要的功能、没启用 Web Search 工具——每次都是靠"打断 → 给上下文 → 回到规划"来纠正的。

四个阶段的分工：

- **规划阶段**决定"做什么"和"怎么做"，产出 Spec 和 Todo
- **编码阶段**执行 Todo 里的任务，优先让应用跑起来
- **校验阶段**检查结果，纠偏，提交代码
- **进阶阶段**是在基础流程跑通后，用高级功能提效

**关键原则：阶段一和阶段二之间的边界必须守住。** 如果你跳过规划直接编码，后面所有的校验成本都会翻倍。

## 05 关键机制：Claude Code 为什么总是"过度执行"

理解了框架，还需要理解一个底层机制：**Claude Code 的过度执行倾向**。

视频里作者至少四次提到这个问题，并在实战中反复遭遇：

1. 在 Plan Mode 下，Claude 仍然反复请求"要开始编码吗？"
2. 写 Spec 时，Claude 会把需求写得比你要求的更复杂
3. 编码时，Claude 会添加你没要求的功能（比如自动检测时区，而用户已经手动输入了城市）
4. 在 Todo 清单里，Claude 会勾选实际上没完成的任务（比如标记"已启用 Web Search 工具"，但代码里并没有调用）

**为什么会这样？**

AI 模型在训练时被优化为"尽量完整地满足用户意图"。这导致它倾向于：
- 把简单需求理解为复杂需求
- 主动添加"可能有用"的功能
- 过早宣告任务完成

**带来的代价：**

- 你需要花大量时间审计 AI 的产出
- 如果不审计，错误会逐层累积
- 你必须始终保持"Tech Lead"的心态，不能当甩手掌柜

**应对方法：**

- 规划阶段：用 Plan Mode 物理限制 AI 不能写代码
- 编码阶段：明确要求"只做 Todo 里列的事项，不要额外添加"
- 校验阶段：逐条检查 Todo 是否真正完成，而不是看 AI 自己打的勾

## 06 方法拆解：从零到可运行应用的完整流程

以下是视频演示的完整流程，提炼为可复用的步骤。

### 第一步：用 Plan Mode 探索方案

| 项目 | 内容 |
|------|------|
| **目标** | 在写任何代码之前，确定技术方案 |
| **具体动作** | 按 `Shift+Tab` 进入 Plan Mode → 向 Claude 描述你要做什么 → 要求它给出 2-3 个方案，从最简单的开始 |
| **判断标准** | Claude 应该列出多个方案的优劣对比，而不是直接选定一个 |
| **常见坑** | Claude 会反复请求开始编码，每次都要拒绝 |
| **产出物** | 选定的技术方案 |

### 第二步：写 Spec 和 Prompt

| 项目 | 内容 |
|------|------|
| **目标** | 把方案写成结构化的需求文档 |
| **具体动作** | 要求 Claude 生成 Spec（包含需求、技术栈、设计规范、Milestones）→ 逐条审阅并简化 → 如果涉及 AI API，单独写 Prompt 文件 |
| **判断标准** | Spec 应该精简到"刚好够用"，删除 Claude 自己加的多余需求；Prompt 应该包含输出的格式和时效性要求 |
| **常见坑** | Claude 会把 Spec 写得过度详细，包含你没要求的功能；需要手动删减 |
| **产出物** | `spec.md`、`prompt.md` |

### 第三步：拆 Todo 清单

| 项目 | 内容 |
|------|------|
| **目标** | 把第一个 Milestone 拆成可执行的任务列表 |
| **具体动作** | 要求 Claude 基于 Spec 创建第一个 Milestone 的 Todo → 审阅每条任务是否合理 → 修正过时或错误的选择（如模型版本） |
| **判断标准** | 每条任务应该足够具体，能明确判断"完成/未完成" |
| **常见坑** | Claude 可能在 Todo 中引用过时的技术（如旧模型名），必须逐条检查 |
| **产出物** | `todo.md` |

### 第四步：配置项目上下文

| 项目 | 内容 |
|------|------|
| **目标** | 让后续对话更高效 |
| **具体动作** | 运行 `/init` 或手动创建 `CLAUDE.md` → 写入你的角色和技术偏好 → 设置 Output Style（`/output-style explanatory`）→ 配置权限文件（允许读写和运行，禁止删除） |
| **判断标准** | CLAUDE.md 里的信息应该让 Claude 不需要你重复解释背景 |
| **常见坑** | 权限设置不要用 `dangerously skip permissions`，至少保留删除操作的确认 |
| **产出物** | `CLAUDE.md`、`.claude/settings.json` |

### 第五步：编码——先跑起来再说

| 项目 | 内容 |
|------|------|
| **目标** | 用最短时间让应用在本地运行 |
| **具体动作** | 要求 Claude 按 Todo 执行第一个 Milestone → 要求运行 localhost → 参考截图或设计稿给 Claude 视觉指引 |
| **判断标准** | 应用能在浏览器打开并展示基本功能 |
| **常见坑** | Claude 可能在第一次就写不出能跑的代码；不要慌，进入调试流程 |
| **产出物** | 可运行的本地应用 |

### 第六步：调试——具体反馈比笼统指令有效 100 倍

| 项目 | 内容 |
|------|------|
| **目标** | 让 AI 精准定位和修复问题 |
| **具体动作** | 打开浏览器开发者工具 → 复制 Console 中的错误信息 → 截图当前页面状态 → 把错误信息和截图一起发给 Claude → 加上"think ultra hard, why do you think this happened" |
| **判断标准** | Claude 应该能基于错误日志定位根因，而不是猜测 |
| **常见坑** | 只说"不工作"而不给任何上下文；Claude 只能在信息充足时才能有效调试 |
| **产出物** | 修复后的代码 |

### 第七步：完成 Milestone 后的收尾

| 项目 | 内容 |
|------|------|
| **目标** | 为下一个 Milestone 清理环境 |
| **具体动作** | 让 Claude 更新 Todo（勾选已完成项、添加下一阶段任务）→ `git commit` 提交到 GitHub → 执行 `/compact` 压缩对话上下文 |
| **判断标准** | 代码已提交；Todo 已更新；对话上下文已清理 |
| **常见坑** | 忘记提交代码就进入下一阶段，一旦出错无法回退 |
| **产出物** | Git commit、更新后的 Todo、干净的新对话 |

## 07 案例讲解：从空白文件夹到可运行的 Family Activity Finder

**场景背景**：作者是一个代码能力有限的产品经理，想构建一个"家庭活动查找器"——家长输入城市、孩子年龄、空闲时间、驾车距离和偏好，应用返回 5 个本地活动推荐，每个带标题、emoji 和简短描述。

**遇到的问题**：直接让 Claude Code 写代码，结果要么跑不起来，要么产出不需要的功能，要么用了过时的技术。

**按框架如何处理：**

**规划阶段：**
- 进入 Plan Mode，描述需求，Claude 给出三个方案——静态数据、第三方 API、Claude API + Web Search。选择第三个方案，因为它最匹配演示场景。
- 要求 Claude 写 Spec。审阅后发现需求被过度扩展，手动简化。发现缺少 Prompt 文件（调用 Claude API 需要系统提示词），补充创建 `prompt.md`。
- 要求 Claude 拆第一个 Milestone 的 Todo。审阅时发现模型版本过时（Claude 3.5 Sonnet → 应为 Claude 4 Sonnet），手动修正。

**编码阶段：**
- 要求 Claude 按 Todo 构建 Milestone 1（UI + 假数据），运行 localhost。第一次完成时页面空白，无法加载。
- 进入调试：打开浏览器 Console，发现报错。把错误信息粘贴给 Claude，加上"think ultra hard"。Claude 修复后，UI 正常显示。

**校验阶段：**
- 让 Claude 更新 Todo，添加 Milestone 2 的任务。
- 提交代码到 GitHub。
- 执行 `/compact` 压缩上下文。

**第二个 Milestone（接入真实 API）：**
- 进入编码阶段。Claude 开始工作，但作者在旁边观察时发现它仍在使用旧模型——再次打断修正。
- API 接通后，返回的结果是通用景点（如"探索馆"），而不是近期活动。作者切回 Plan Mode，让 Claude 分析原因——发现 Web Search 工具没有被真正启用。提供文档链接，要求 Claude 按文档实现。
- Claude 又添加了不需要的位置检测功能（用户已经在表单里输入了城市），再次打断简化。
- 最终经过多轮调试，应用能返回近期、本地的家庭活动。

**最终结果**：约 30 分钟内，从空白文件夹到可运行的全栈应用（前端 + Claude API 后端 + Web Search），代码已提交 GitHub。

**这个案例说明了什么：** 即使遵循了完整流程，仍然需要大约 10 分钟的反复纠偏。这不是流程的问题——如果你不遵循流程，纠偏时间会从 10 分钟变成 1 小时。流程的价值不是消除错误，而是把错误控制在可管理的范围内。

## 08 常见误区

### 误区 1："AI 编程工具能让我不用管技术细节"

- **错误理解**：只要描述清楚需求，AI 就能一次性交付正确的产品
- **为什么错**：AI 极度倾向于过度执行和提前宣布完成，不审计就等于放任错误逐层累积
- **正确理解**：AI 编程工具降低的是编码门槛，不是管理门槛。你仍然需要做需求梳理、方案选择、质量审计
- **应该怎么做**：把自己定位为 Tech Lead，AI 是你的工程师——你不写代码，但必须审代码

### 误区 2："应该让 AI 尽快开始写代码"

- **错误理解**：规划浪费时间，早写代码早出结果
- **为什么错**：在规划不充分时写代码，AI 会在错误方向上全速前进，返工成本远高于规划成本
- **正确理解**：花在规划上的每一分钟，都在减少后续的返工
- **应该怎么做**：强制自己先完成 Spec 和 Todo，再进入编码

### 误区 3："AI 出错了就重新让它写一遍"

- **错误理解**：出错了就重新生成，总会碰到对的
- **为什么错**：不给上下文的重新生成，只会得到同样错误的不同写法
- **正确理解**：调试的有效性取决于你给的信息量——错误日志、截图、具体描述
- **应该怎么做**：打开浏览器 Console，复制错误信息，截图当前页面，一起发给 AI

### 误区 4："对话越长，AI 越了解我的项目"

- **错误理解**：在同一个对话里做所有事情，AI 会越来越懂
- **为什么错**：对话历史越长，AI 的注意力越分散，越容易被早期上下文误导
- **正确理解**：AI 的上下文窗口是有限的资源，长对话 = 低质量
- **应该怎么做**：每完成一个 Milestone，执行 `/compact` 或 `/clear`，用干净的上下文开始下一阶段

### 误区 5："权限全开效率最高"

- **错误理解**：跳过权限确认，让 AI 全自动运行
- **为什么错**：AI 可能删除文件、覆盖重要配置、执行危险命令，而你毫不知情
- **正确理解**：权限管理的目标是减少低风险操作的确认（读写文件、运行测试），同时保留高风险操作的把关
- **应该怎么做**：允许读写和常用命令，禁止删除操作；绝对不要用 `dangerously skip permissions`

### 误区 6："AI 标记完成的任务就是真的完成了"

- **错误理解**：Todo 清单里打了勾的任务不用再检查
- **为什么错**：视频案例中，Claude 标记"已启用 Web Search 工具"，但实际代码里并未调用
- **正确理解**：AI 的"完成"标记是它自己的判断，不是事实
- **应该怎么做**：对关键任务，实际运行验证，而不是信任 AI 的勾选

### 误区 7："高级功能（子代理、Hooks、MCP）应该立刻配置"

- **错误理解**：一开始就把所有高级功能配上，效率最高
- **为什么错**：MCP Server 会挤占上下文空间；子代理和 Hooks 需要你对基础流程有足够理解才能正确设计；过早引入复杂度反而拖慢进度
- **正确理解**：高级功能是基础流程跑通后的提效手段，不是起步阶段必需品
- **应该怎么做**：先跑通 Plan → Spec → Todo → Code → Verify 的基本循环，再逐步加入高级功能

## 09 实战清单：读完后可以马上照着做

**立即能做：**

1. 打开 Claude Code，按 `Shift+Tab` 进入 Plan Mode，描述你的项目需求，要求 AI 列出 2-3 个技术方案
2. 在项目根目录创建 `CLAUDE.md`，写入你的角色和技术偏好（比如"我是产品经理，代码经验有限，请在修改时解释技术选择"）
3. 设置 Output Style：输入 `/output-style explanatory`，让 AI 在编码时附带解释
4. 准备一个 GitHub 仓库，在完成第一个 Milestone 后把代码推上去

**一周内能做：**

5. 选一个你一直想做的 Side Project，按 Spec → Todo → Code 的完整流程走一遍，记录每个阶段的耗时和返工次数
6. 配置 `.claude/settings.json` 权限文件：允许读写文件和运行常用命令，禁止删除操作
7. 练习调试流程：故意在一个简单项目里制造一个 bug，然后打开 Console、复制错误、截图、给 AI 提供完整上下文让它修复
8. 在完成一个 Milestone 后，习惯性地执行 `/compact` + `git commit` + 更新 Todo

**长期要沉淀：**

9. 建立自己的 Prompt 模板库：收集你在不同项目中写过的 Spec 和 Prompt 模板，复用到新项目
10. 为重复工作流创建自定义命令（Slash Command），减少每次手动输入相同指令
11. 评估是否需要子代理：如果你的项目经常需要并行处理独立任务（如文档更新 + 安全审计），考虑让 AI 帮你创建子代理
12. 谨慎引入 MCP Server：每次只加一个，观察对上下文空间的影响，确认收益大于成本

## 10 总结

Claude Code 让不会写代码的人也能构建应用，这是一个真实的能力跃迁。但这个跃迁的前提是：你必须从"写代码的人"变成"管代码的人"。

管代码的核心不是技术判断，而是流程纪律。Plan Mode 不是可选功能，是你的安全网。Spec 和 Todo 不是额外负担，是让 AI 在正确方向上工作的锚点。Escape 键不是打断，是纠偏。调试时的错误日志和截图不是麻烦，是你给 AI 的唯一有效线索。

视频作者花了一个月时间得出的结论，和传统软件工程的核心原则是一致的：**前期规划投入的每一分钟，都在减少后期的返工。** AI 编程工具没有改变这个规律，反而放大了它——因为 AI 执行错误的速度，比人类快得多。

最终判断：**Claude Code 的正确使用方式，不是学会 20 个技巧，而是建立一套"先想清楚、再动手做、做完就检查"的纪律。技巧会过时，纪律不会。**
