# OpenClaw实战：Tiktok自动运营！完整工作流

## 一句话摘要

用OpenClaw AI Agent（"Larry"）实现Tiktok内容创作→发布→数据分析→迭代的完整闭环，让AI自主驱动应用下载和收入增长。

## 核心观点

- AI Agent不是工具，是员工——给它一个目标（"自动化我的营销"），让它自主研究、执行、迭代
- 内容营销的核心闭环是：创作→发布→分析数据→反馈到下一次创作，Agent可以完全自主完成这个循环
- 不要过度干预Agent的输出——作者发现Agent"犯错"的内容反而成为最高播放量的视频
- CTA（行动号召）决定转化率，播放量不等于收入，必须把业务指标反馈给Agent才能闭环
- Skills是SaaS的本地化替代——不再依赖云托管，技能文件本地运行、用户完全可控

## 详细笔记

### 背景：从手动营销到自动化

Oliver因帮女朋友做室内设计，发现ChatGPT生成房间设计时经常"乱加门窗"，于是锁定prompt后做成App"Snugly"。营销路径：

1. 最初拍真人出镜视频——费时且效果一般
2. 尝试Canva做幻灯片——手动制作，一条爆款6万播放验证了方向
3. 尝试SaaS自动化工具——产品不好用
4. 转向OpenClaw Agent"Larry"——一次对话启动，目标是"自动化我的营销"

### Larry的成长轨迹

**阶段一：探索期（人工监督）**
- Larry用DALL-E 3生成图片，效果差（AI感太重、黑边格式错误），播放量低
- 尝试AI人脸——人类太擅长识别假脸，效果不好
- 终于找到第一个爆款格式：13.7万播放

**阶段二：信任建立期**
- 发现关键格式：特定图片风格 + 翻钩文案 = 爆款
- Larry回溯历史数据，找到之前6万播放的视频，复用成功公式
- 作者仍手动检查每条内容后再发布

**阶段三：放手期（Larry成为老板）**
- 作者本想纠正Larry把文字放在顶部而非中间的"错误"，但该视频成为史上最高播放
- 评论区"长辈挑错"效应反而推动传播——"灶台去哪了？""只能空气炸锅了"
- CTA从模糊的"redecorating snugly"改为明确的"Snugly App帮我终于说服了她装修厨房"

**阶段四：自主迭代期**
- Larry观察数据发现"房东"钩子播放量下降，自动切换到"妈妈"钩子
- 完全自主决定内容方向、钩子类型、发布节奏
- 额外任务：基于App分析数据，完全重写了Snugly的onboarding流程，新用户数创新高

### Larry循环（核心方法论）

不是简单的内容自动化，而是完整的反馈闭环：

```
Tiktok分析数据 → 内容创作 → 发布 → 分析数据 → 反馈到下一轮创作
                                              ↓
                              App指标（下载/付费）也反馈回顶部
```

关键：不只是播放量，业务指标（下载率、付费率）也必须反馈给Agent。Larry通过分析"高播放但低下载"发现CTA问题，通过分析App留存数据重写onboarding。

### 发布策略

- **不要通过API直接发布**——Tiktok会识别API发布，限流
- **发布为草稿→手机端发布**——添加音乐（算法权重高），Tiktok认为是真人操作
- Larry通过Telegram通知作者"草稿已准备好"，作者手机端加音乐后发布
- 实际操作：每天1-2小时，主要是发短信/语音给Larry

### Skills与SaaS的未来

- Skills = Neo插入Matrix学会功夫——给Agent上下文，它立刻拥有能力
- Skills不是黑盒：用户完全拥有skill文件，可以修改任何部分（UI、后端、图片生成模型）
- Larry Brain：Skills市场，一次订阅获得所有skill的上下文
- 作者做了SuperX替代品作为概念验证：SaaS产品可以完全作为Skill本地运行，无需云托管/域名/存储/认证
- OpenClaw是你家电脑上的服务器——本地host一切成为可能

### 模型选择与工具建议

- 作者用Opus（Anthropic Pro计划，约90英镑/月）
- 建议：不要在模型间反复切换优化，选一个学会怎么用它
- 98%用户不会注意到模型间的微小差异
- 新手建议：先用Manus（托管方案，"训练轮"），熟练后再上OpenClaw
- Ernesto Lopez用类似方法做到7万美元月收入

## 我的评注

- **赞同**：把AI Agent当作员工而非工具，这个心智模型非常准确——给它目标而非指令，让它从数据中学习。作者反复强调"让它自己迭代"而非"帮它完美化"，这是Agent工程的关键洞察
- **赞同**：闭环思维比内容创作本身更重要。很多自动化营销只做了"创作→发布"，缺少"分析→反馈→迭代"的回路。Larry循环的真正价值是业务指标（不只是播放量）回流到创作端
- **质疑**：作者对"完全放手"的描述可能有幸存者偏差——他只展示了成功的迭代，但早期大量低播放内容的试错成本（时间、账号权重）被轻描淡写。对于没有初始数据的新账号，冷启动阶段仍需大量人工干预
- **质疑**：Skills替代SaaS的说法过于乐观。本地运行意味着没有多设备同步、没有协作、没有可靠备份，这些对于非技术用户是硬伤。概念验证≠生产可用
- **关联**：Larry循环本质上是[[AI Agent自验证循环]]的一个实例——Agent执行任务、观察结果、调整策略。与Claude Code的"读取错误→修改→重新运行"是同一种模式，只是应用在营销领域。这也验证了[[任务即子Agent]]模式：Larry自己保持全局上下文，具体执行委托给子Agent

## 待深入问题

- Larry的"学习"实际上存储在哪里？是memory文件还是每次重新分析历史数据？这对Agent的长期可扩展性至关重要
- Tiktok算法变化时，Larry的适应性有多强？作者提到"房东钩子失效后Larry自动切换"，但这种适应是否可以持续，还是需要人工干预？
- 闭环中的延迟问题：Tiktok数据到Agent反馈的延迟有多长？如果一天才出数据，迭代速度是否够快？
- Skills作为SaaS替代的实际边界在哪？哪些类型的产品适合本地化，哪些必须有云端协作？
- 从几百美元月收入到Ernesto的7万美元，中间的关键变量是什么？是应用数量、内容质量还是账号矩阵策略？
