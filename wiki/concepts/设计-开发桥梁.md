# 设计-开发桥梁

## 定义
设计师与工程师之间的协作模式正在从"交接"（handoff）转向"融合"（fusion）——设计师直接进入代码库理解约束、验证方案、交付实现，工程师也参与设计反馈。角色边界变得流动，但决策权仍属专家。

## 为什么重要
传统设计-开发流程是串行且损耗大的：设计师做完 Figma → 写 spec → 交接给工程师 → 工程师实现时发现设计不可行 → 回到设计师修改 → 循环。AI 改变了两个关键点：1）设计师可以直接进入代码库理解技术约束，在设计阶段就避免不可行方案；2）设计师可以直接交付代码实现，消除翻译损耗。这不是设计师变成工程师，而是设计师获得了"代码视角"这个新维度。

## 我的判断
- **赞同**：Megan 描述的"90% 时间在理解代码库和做最终打磨"是设计师最合理的代码参与方式——不需要从头搭建架构，但在关键节点（方案可行性、视觉打磨）直接介入代码产出最高价值。
- **质疑**：角色流动的前提是组织文化允许。Megan 反复强调 Anthropic 的"anyone can code"文化——但在分工更严格、代码审查门槛更高的组织中，设计师 push 代码可能面临权限、质量标准、责任归属的障碍。
- **补充**：Megan 和 Jenny 的路径对比揭示了桥梁的两种建法——Jenny 通过 Co（AI 降低门槛）让设计师不写代码也能产出，Megan 通过 Code（AI 提升能力）让设计师直接写代码。两者不是替代关系，而是适配不同技术背景的设计师。
