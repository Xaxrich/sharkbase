# Claude Code实战：如何将个人产出提高15倍

## 一句话摘要
两人团队用 Claude Code 做出 15 人产出——不是靠写代码更快，而是靠让 AI 做一切非编码工作，并在规划阶段而非实现阶段进行人工干预。

## 核心观点

- **AI 不只用于编码，而是用于一切**：研究、工作流、产品营销、Bug 调查——所有工程工作都应该交给 Agent
- **复利工程**：每一份工作都应该让下一份工作更容易。构建生成提示的提示，是最典型的复利效应
- **在最低价值阶段拦截问题**：来自《High Output Management》的 50 年老原则——AI 时代更需遵守，因为杠杆越长，方向偏差的代价越大
- **Agent 分工而非 Agent 统一**：不同 Agent 做不同的事，像招聘专家一样——Claude Code 做研究，Friday 做 UI，Charlie 做代码审查
- **传统测试仍是最好的护栏**：写冒烟测试、跑 Eval、用 MCP 工具做视觉验证——"无聊的传统方法"在 AI 时代反而更有效

## 详细笔记

### 从"编码助手"到"工程助手"的转变

Here（Corera 工程师）和 Natasha（Corera GM）描述了过去三周的感受：编码 Agent 的能力跨越了一个临界点。关键不在于模型变聪明了，而在于 Agent 足够好，可以承担编码之外的所有工程工作——研究、规划、追踪、营销文案。

Claude Code 的差异化：不是另一个 Cursor 或 Windsurf，而是**更简单但更强大**的工具。终端界面只有一个文本框，没有快捷键、没有命令面板——因为底层模型足够强，可以在更少的 UI 约束下工作更长时间、使用更多工具。

### Claude Code 的具体使用场景

1. **产品营销**：输入"过去一周我们发了什么"，Claude Code 查 git log，生成非技术语言的功能总结和 Bug 修复清单
2. **进度追踪**：输入"下周要发什么"，查 GitHub 项目板，输出即将上线的功能列表
3. **Bug 调查**：发现问卷未发送，Claude Code 查日志变更、定位被误删的代码、创建 PR 修复、还主动写了数据迁移脚本补救漏发
4. **语音输入 + Agent 执行**：Herein 几乎从不打字，全部用语音转文字（内部工具 Monologue）描述需求，Agent 执行

### 自定义命令：提示生成提示

他们创建了 Claude Code 的自定义命令（slash command），核心流程：

1. 接收语音输入的功能描述
2. **研究代码库**——了解现有实现
3. **搜索最佳实践**——查开源模式、Web 资源
4. **生成实现计划**——人类审核（Human-in-the-loop）
5. **创建 GitHub Issue**——放入正确的看板列

这就是"复利工程"的实例：花时间构建一个生成研究文档的提示，以后每次新功能都不用从头写需求——Agent 自动完成研究和文档化。

### 在最低价值阶段拦截问题

Natasha 引用 Andy Grove《High Output Management》第一章：**任何生产过程中，应在最低价值阶段修复问题**。

具体含义：当 Claude Code 生成了详细的 GitHub Issue 后，直接让另一个 Agent 去实现是很诱人的——但如果 Issue 中的方向有偏差，实现阶段的修正成本远高于规划阶段。因此人工审核必须放在规划阶段。

Herein 补充：PRD 很无聊，但可以让它更有趣——要求 Agent 以"PM 会问什么问题"的形式输出，或给两个选项让你选，而非让你读完 20 页文档。

### 测试与 Eval 作为护栏

- **冒烟测试**：让 Agent 写最基本的测试——"这东西能不能跑起来？"
- **Eval 即提示的测试**：让 Claude Code 跑 Eval，发现 4/10 次失败，让它自己跑 10 次、看 trace、找到根因（工具描述不够具体）、自动修复提示直到全部通过
- **视觉验证**：用 Figma MCP 让 Agent 截图移动端版本，与设计稿对比——尚未充分使用但方向正确

### Agent 排名

Herein 给出的编码 Agent 排名：

| Agent | 排名 | 理由 |
|-------|------|------|
| Claude Code | S | 最灵活，不只编码；模型最强，自我纠错能力好 |
| Friday | S/A | 有主见的工作方式，UI 实现能力突出；尚未用 Claude 4 |
| Cursor | A | 配合 Claude 4 很强，但版本混乱（哪个模型？背景 Agent？） |
| Charlie | A（审查）/ B（Agent） | 代码审查极好，作为通用 Agent 一般 |
| Devin | B | 不够集成，设置复杂，代码质量不如 Cursor/Claude Code |
| Codex | B | 中规中矩 |
| Factory | B | 适合企业级、多仓库场景，Web 端操作不方便 |
| Windsurf | C | 没有 Claude 4，三周前还是 A |
| Copilot | 未评 | 传统版本太旧，新版 Agent 模式未测试 |

### 专家协作的 Agent 化

当需要基础设施专家时，他们录了一段两小时的对话，把录音喂给 Claude Code，10 分钟后输出了研究 Issue——专家对 AI 的产出质量感到惊讶。此后该专家将自己所有的 Cursor/Windsurf 工作流迁移到了 Claude Code。

## 我的评注

- **赞同**：复利工程是最有价值的框架。多数人把 AI 当"更快的打字机"，但真正的杠杆在于让 AI 做之前没人有空做的事——写 PRD、跑 Eval、查日志、生成营销文案。每个被自动化的元任务，都让后续任务启动成本更低。
- **赞同**：在最低价值阶段干预的原则被严重低估。AI 的杠杆越大，方向偏差的代价越大——这和火箭发射一个角度的偏差等于数千英里的道理一样。
- **质疑**：15 倍产出缺乏可验证的度量。"两人团队感觉像 15 人"是主观感受，不是生产力指标。如果没有对照（同样两人不用 AI 的产出），数字没有意义。视频中展示的产出量（一周 6 个功能 + 5 个 Bug 修复 + 3 个基础设施更新）确实可观，但无法确认基线。
- **质疑**：Agent 排名有明显的时间依赖性——Windsurf 三周前是 A 现在是 C，Cursor 版本混乱。这种排名的半衰期可能只有几周，更适合作为当前快照而非决策依据。
- **关联**：复利工程与 [[驾驭工程]] 是同一思想的两面——驾驭工程是"约束模型以激发能力"，复利工程是"自动化元任务以降低后续成本"。底层逻辑一致：**系统的设计比单次执行更重要**。

## 待深入问题

- 复利工程的可迁移性：这种"提示生成提示"的模式在非编码领域（内容创作、数据分析）是否同样有效？
- Agent 之间的信息传递：当 Claude Code 做研究、Friday 做 UI、Charlie 做审查时，上下文如何在 Agent 间流转？是否存在信息损耗？
- 人工干预的时机选择：规划阶段干预是共识，但"规划"的粒度如何定义？太粗会漏掉方向偏差，太细则抵消了 Agent 的自主性收益。
