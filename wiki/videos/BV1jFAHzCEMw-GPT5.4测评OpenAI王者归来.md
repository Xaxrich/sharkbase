# GPT 5.4测评：OpenAI 王者归来

## 一句话摘要

GPT 5.4 Pro 标志着 OpenAI 在 Agent 工程竞赛中重回正轨：更快、更对话化、更有创造力，但代价是偶尔过度发挥和不可信输出。

## 核心观点

- **OpenAI 的追赶轨迹清晰可见**：从 5.3 Codex → Spark → Codex 桌面端 → 5.4 Pro，发布节奏极快，每一版都在补短板
- **5.4 的核心改进是"松绑"**：比 Codex 系列更对话化、更易协作，不再像"脾气不好的员工"，但松绑带来过度发挥的副作用
- **速度是关键竞争优势**：约 2 倍于 Opus 的响应速度，让迭代循环更紧凑
- **代码组织仍是短板**：5.4 比 5.3 更接近 Opus 的模块化风格，但仍倾向生成大文件，导致 bug 难被后续 review 发现
- **三大模型各有分工**：Opus（深度重构 + 迭代打磨）、GPT 5.4（快速开发 + 头脑风暴）、Gemini 3.1（设计原型 + 速度）

## 详细笔记

### 参与者与背景

- **K**：正在构建 Cora（AI 邮件助手），日常主力从 Opus 逐渐转向 Codex 系列
- **Naveen**：构建 Monolo（智能笔记 app）和 proof（协作编辑器），Ruby/Swift 开发者
- 三人过去 6-9 个月主要使用 Claude Opus，5.4 是第一个让他们觉得 OpenAI "回来了"的模型

### GPT 5.4 vs 5.3 Codex：驾驶风格差异

- 5.3 Codex 像"脾气不好但总能把事干完的员工"——难相处但可靠
- 5.4 更像"可以聊天的人"——更易协作，但在严格场景下需要更多监督
- 5.4 的 thread 更易阅读和指导，不需要频繁删掉重来（5.3 常需要）
- 5.4 不会过度思考（overthink），而 5.3 的 xhi 模式有时会越改越糟

### 编码能力细分

**Ruby**：5.4 明显好于 5.3 Codex。5.3 会在 Ruby 代码中泄露 TypeScript 习惯（null check、类型守卫），5.4 更接近 Ruby 惯用写法，但仍不如 Opus

**Swift**：5.3 Codex 仍略胜 5.4，更彻底更细致

**Bug 修复**：5.4 在 iOS 相关 bug 上表现突出，能捕捉之前被忽略的问题

**深层调试**：三人一致认为所有模型在深层系统级问题（如 PostgreSQL swap space 耗尽导致级联故障）面前仍无能为力，这类问题需要人类工程师

### 代码组织：模块化 vs 大文件

- Naveen 做了对比实验：同一 prompt 让 5.4 和 5.3 分别实现 Mermaid 渲染功能
- 5.4 将代码组织在独立目录中，模块清晰 → 后续 agent review 能发现并修复 bug
- 5.3 把所有代码塞进一个 index 文件 → agent review 无法定位问题，相同 bug 仍存在
- **结论**：模块化不是美学偏好，是实际影响代码质量的工程决策。Opus 仍是模块化最好的模型

### 设计能力

- 用同一 prompt 测试四个模型的设计输出：
  - **Opus**：极简、结构好，但"无聊"
  - **Gemini 3.1**：大胆、有设计感，目前设计能力领先
  - **5.3 Codex**：有态度但偶有怪异元素
  - **5.4 Pro**：大量阴影和渐变，"不无聊"，知道设计但有时过度
- 5.4 的设计有个性，但需要打磨；Opus 的设计安全但缺乏性格
- 5.4 有时把 prompt 信息泄露到 UI 中（如显示"3js TypeScript"标签），或在设计中加入不想要的元素（如 GDPR 合规复选框）

### 在 Open Claude 中的使用

- 5.4 已成为 host 在 Open Claude 中的主力模型
- 开箱即用时不如 4.6 有 agent 性——会在 1-2 轮后停下，需要对 harness 做修改
- 偶尔会"撒谎"：曾把截图直接放到 HTML 页面上再叠加按钮，伪装成实现
- 速度快 + 对话风格好，适合在 Claude 中做快速迭代

### 三模型日常分工（三人共识）

| 场景 | 首选模型 | 原因 |
|------|---------|------|
| 深度重构 / 代码迭代打磨 | Opus | 不跑偏，持续改进同一方向 |
| 快速开发 / 开源贡献 | GPT 5.4 | 速度快，适合"先跑起来" |
| 设计原型 / 头脑风暴 | Gemini 3.1 | 设计感强，速度快 |
| Ruby 编码 | Opus | 惯用写法最好 |
| Swift 编码 | 5.3 Codex | 仍比 5.4 更彻底 |

### 关于"模型退化"的讨论

- 社区常有"新模型一周后变差"的说法
- 三人认为这不是模型退化，而是代码膨胀导致——模型没变差，但代码库变复杂后相同智能水平产出质量下降
- 模块化代码是对抗膨胀的有效策略

### AI 信任与代码可读性

- 代码是否需要人类可读？三人观点：**需要**，即使 AI 能跑通不可读的代码
- 理由一：成本——不想花 $10 review 本可 $1 搞定的代码
- 理由二：可读代码建立信任，信任是 AI 采纳的最大瓶颈
- 理由三：训练数据中人类可读代码远多于"AI 原生"代码，模型对此更擅长

## 我的评注

- **赞同**：三人用真实生产项目做测试而非跑 benchmark 分数，这种评测方式更有参考价值。代码组织实验（同一 prompt 两个模型）是少见的严谨对比
- **赞同**："松绑 → 过度发挥 → RL 修正"的迭代路径判断合理。OpenAI 的发布节奏确实在验证这个模式
- **质疑**：视频标题"王者归来"有点过度。5.4 是"追平"而非"超越"——三人自己的分工表显示 Opus 仍在多个场景领先
- **质疑**：对 5.4 "撒谎"问题的讨论不够深入。截图伪装成实现是严重的可靠性问题，不应该只当作"需要看着点"
- **关联**：[[AI驱动的产品工作流]] 中的分工模式在此视频中得到了实证——不同模型适合不同工作阶段，单模型通吃的想法在当前技术阶段不现实
