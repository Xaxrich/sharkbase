# LLM-Agent工程实践

## 核心主张
好的 Agent 工程是**约束中激发能力**，而非堆功能。Claude Code 的"克制式"设计——52个工具只暴露~20个、默认拒绝所有权限、五种协作模式只开放两种——不是保守，而是对"模型上下文中信息越多决策越差"这一基本事实的回应。同一个逻辑在 RLVR 训练中也成立：环境约束恰当，小模型能击败大模型。

## 综合分析

### 做减法 > 做加法：跨领域的工程共识

来自 [[BV1Y4oLBuEu6-吃透Claude-Code核心源码]] 的核心论据：Claude Code 的整个设计哲学是"克制"——不断收缩工程功能，激发模型自身能力。三层工具过滤（feature flag → 权限模式 → 项目规则）将52个工具缩减到~20个；安全上默认全部拒绝；Agent协作五种模式只开放两种。这不是"还没做完"，而是刻意的选择。

来自 [[BV1D9ojBzEAd-将小模型训练成特定领域大师]] 的佐证：在 RLVR 训练中，同样的模型在不同环境约束下表现天壤之别。对手太强（约束过度）→模型永远赢不了学不到；对手太弱（约束不足）→模型学不到策略；噪声太大（环境不稳定）→训练崩溃。**环境设计的质量决定了模型能力的上限**——这和 Harness 设计的质量决定 Agent 能力上限是同一逻辑。

两者的共同结论：**能力不来自工具/数据的数量，而来自约束的精准度**。这在 [[MVP思维]] 中有更广泛的回响——做减法是跨领域的元模式。

### Harness 的核心架构：从 Claude Code 看最佳实践

[[BV1Y4oLBuEu6-吃透Claude-Code核心源码]] 提供了目前最完整的 Harness 参考实现，以同心圆架构展开：

**Query Engine（神经系统）**：ReAct 循环是所有 Agent 的底层模式——模型思考→调用工具→获得结果→再思考。System Prompt 的静态分隔符策略（静态内容前置，最大化 Token 缓存命中）是成本控制的关键工程智慧。记忆管理的三层设计（声明式→Extended Memory→Auto Dream）体现了从简单到智能的递进，Auto Dream 对应的 Garbage Collection 是决定项目能否长期运行的核心能力。

**工具系统（手脚）**：Claude Code 不用 RAG，全靠 grep + 语法树做代码检索——这对代码库场景够用，但企业级大量文档场景下 RAG 仍必要。MCP 的动态加载机制解决了工具描述过长的问题，和 Skills 系统的延迟加载思路一致。

**安全（基础设施）**：六大原则（纵深防御、最小权限、安全默认、零信任、TOCTOU防御、企业可控）的核心是"安全没有一招先"——只能在每个漏洞点层层设防，永远不依赖模型判断来决定是否安全。提示注入防控是针对每种攻击方法的专项防御：环境变量Key清除、Skill路径随机化、路径遍历防御。

### 仍然缺失的：评估体系与开发 Harness → 评估体系已补全

Claude Code 暴露了 Harness 的空白：开发 Harness（Anthropic 如何用 Claude Code 开发 Claude Code 本身）完全不可见。这就像看到了一辆车的内部结构，但不知道造车的流水线——理解了切面，但不知道如何重现切面。

但评估体系的空白已被 [[BV1gXqLBXE87-AI评估实战50分钟完整入门课程]] 填补。视频提供了完整的 AI 评估方法论：四种评估类型（代码评估 > 人工评估 > LLM-as-Judge > 用户评估）、黄金数据集构建流程、评分标准定义、人工标注与 LLM-as-Judge 的对齐匹配率。虽然场景是客服机器人而非 Agent，但核心方法论是通用的——评估的本质是"用确定性锚点校准非确定性系统"，和 [[确定性输出]] 的逻辑一脉相承。

关键实践洞见：
1. **人工标注是不可跳过的基础**——LLM-as-Judge 在不对齐人工标签时会系统性给出错误评估（如给所有回复打"好"）
2. **迭代速度和置信度是正交维度**——数据少迭代快但不确定，数据多置信高但迭代慢，PM 需要在这个权衡中找到团队节奏
3. **代码评估应优先部署**——成本最低、确定性最高，在能用二元判断的维度上绝不交给模型

### 实践中的驾驭工程：Noah 的第二大脑作为案例

[[BV15UndzSE6x-Claude Code与Obsidian打造第二大脑]] 提供了一个非代码场景的驾驭工程实例：Claude Code 运行在 Obsidian 根目录，配合系统提示、子代理设计、package.json 自定义命令，构建出完整的"第二大脑"工作流。关键工程决策包括：

1. **目录选择**：在知识库根目录而非项目子目录启动 Claude Code，释放全文检索能力——这是"模型可访问的上下文决定输出质量"的直接体现
2. **思考模式子代理**：专门的系统提示强制 AI 只提问不写作——这是另一种形式的"约束激发能力"，与 Claude Code 自身的工具过滤逻辑一脉相承
3. **每日回顾机制**：用 AI 重建中断后的上下文——对应 Auto Dream 的"垃圾回收"逻辑，解决长时运行中上下文丢失的问题
4. **隐性代码共享**：不抽象共享库，靠 AI 跨项目阅读理解后重新实现——这是对传统"抽象-模块化-统一"路径的替代，也是一种"做减法"的实践

这个案例说明驾驭工程不限于代码场景——任何需要 AI 与人类长期协作的领域，系统提示设计、上下文管理和工作流约束都是核心杠杆。

### Skill：从"提示约束"到"工作流约束"的进化

[[BV1LfmHBuEzt-Claude Skill实战创建AI团队]] 提供了驾驭工程的另一个维度：把约束从系统提示层面提升到工作流层面。

Claude Projects 的局限在于：你给 AI 一个办公室和一堆资料，但 AI 自行决定如何使用——分析数据时每次方法不同，输出每次不同。这和 Harness 的"工具过滤"问题一样：不是工具/资料不够，而是缺乏流程约束。

Skill 的三层结构（指令+引用+脚本）解决了这个问题：
1. **指令层**：定义任务步骤和输出格式——相当于 Harness 中的 system prompt
2. **引用层**：按需加载参考文件（品牌指南、术语表）——相当于 Harness 中的延迟上下文加载
3. **脚本层**：用代码替代 LLM 的非确定性推理——相当于 Harness 中"不让模型做它不擅长的事"

这个三层架构和 Claude Code 的同心圆设计是同一逻辑：[[驾驭工程]] 控制模型能做什么，[[上下文工程]] 控制模型能看到什么，[[确定性输出]] 控制模型不能算错什么。Skill 把三者打包为可复用的工作流单元。

视频中最有说服力的案例是营销数据分析：上传 CSV 后，Skill 内嵌 Python 脚本做确定性计算（总花费、渠道对比、转化率），LLM 只负责组织输出和解读趋势。对比之下，Project 模式中 LLM 自由分析同一份数据，容易幻觉数字。这印证了核心主张——**约束不是限制能力，而是让能力在正确的轨道上释放**。

### Vibe Coding 的安全陷阱：当约束缺失时

[[BV19tqjBZEWD-Vibe Coding实战从原型到SaaS应用]] 揭示了"约束中激发能力"的反面——约束缺失时会发生什么。

**原型与生产之间的鸿沟**：AI 编程工具擅长生成客户端原型，但服务器端逻辑、认证、支付、文件存储、分析——这些生产级功能几乎不会被主动添加。AI 生成的代码中充斥着 localhost 硬编码、base64 内联图片等"看起来能用但不能部署"的问题。这和 Claude Code 的工具过滤逻辑形成镜像：Claude Code 主动隐藏不必要的工具来约束输出质量，而 Vibe Coding 工具默认不做约束，导致输出"能跑但不能上线"。

**RLS 暴露的抽象层问题**：Lovable/Bolt 使用 Supabase 的"无服务器"模式，自动生成 API 端点，但 RLS（Row Level Security）规则默认完全开放。大多数用户不知道 RLS 存在，更不知道如何配置。这不是 Supabase 本身的缺陷，而是抽象层的根本矛盾——**隐藏复杂性降低了门槛，但被隐藏的恰恰是最关键的安全配置**。这与 Harness 的"安全默认"原则（Claude Code 默认拒绝所有权限）形成鲜明对比。

**模板作为 Harness 的一种形态**：视频的核心工程洞见是 SaaS 模板的作用——不是省时间，而是约束 AI 的决策空间。模板中已有的数据库 schema、认证流程、支付集成模式让 AI "不需要猜测如何做，只需遵循已有模式"。这正是 [[上下文工程]] 和 [[确定性输出]] 在代码生成场景的结合：模板提供了精准的上下文（已有代码模式），同时把 AI 的输出约束到确定性的架构上。

**API 过时问题**：AI 编程工具的模型训练数据有截止日期，导致它用过时的 API 或错误的模型名。手动提供最新文档来修正 AI，本质上是在做上下文工程的补丁——补充模型缺失的关键上下文。

### Cursor Rules 与自验证：工程习惯的编码化

[[BV1UZqLBJEH1-Cursor主管演示从新手到精通]] 提供了驾驭工程在开发者日常工具层面的直接体现。

**Cursor Rules 作为编码化的工作习惯**：当你发现自己在多个对话中重复相同指令（"总是跑测试"、"用 pnpm"、"提交要描述性"），就该写成 Cursor Rule。这和 Harness 的 system prompt 是同一逻辑——[[驾驭工程]] 不是一次性的架构决策，而是持续把隐性知识显式化、把重复指令自动化的过程。Rules 的两种形式（单文件 `.cursorrules` vs 多文件 `.cursor/rules/`）反映了从"大而全的约束"到"模块化按需加载"的进化，和 MCP 的动态加载思路一致。

**测试作为 Agent 的反馈信号**：这个视频最核心的洞见是——测试在 AI 时代的角色发生了转换。传统上测试是给人看的质量保障，现在测试同时是给 Agent 看的**自验证回路**。Agent 写代码→跑测试→读失败输出→自动修复→再跑测试，形成闭环。TypeScript 编译器、ESLint、任何能输出结构化错误信息的工具，都是 Agent 的"感觉器官"。这改变了"AI 时代测试是否还重要"的讨论方向——不是更重要了因为覆盖率，而是更重要了因为 Agent 需要它们来工作。这正是 [[AI Agent自验证循环]] 的核心论点。

**Vibe coding 与工程实践的诚实分野**：Lee Robinson 的态度比之前的讨论更明确——vibe coding 适合第一天（快速原型、个人项目、可丢弃的代码），不适合第一天之后（长期维护的产品、团队代码库、生产环境）。关键区别不在工具，在知识："不懂 API key 的人不会知道该问'为什么 API key 不能放客户端'"。这和 [[驾驭工程]] 的核心主张一致——Agent 放大的是你已有的判断力，不是替代你缺乏的知识。

**Cursor vs Vercel 的工程文化差异**：Cursor 工程师即产品经理，极高自主权，快速试错；Vercel 有成熟的产发流程和专职 PM。这呼应了 [[MVP思维]] 中的"约束产生聚焦"——Cursor 的约束是"人少速度快"，这反过来要求每个工程师都是产品型工程师（product-minded engineer）。

### 多模型协作与 Vibe Building：实测中的工程选择

[[BV1AwveBXEBE-Claude 4.5 vs Gemini 3 Pro测评]] 提供了同题竞速的实证数据，核心发现在三个层面：

**模型选择不是单选题**：Opus 4.5 在落地页美学和产品深度上领先，Gemini 3 Pro 在 AI-first 功能直觉上更大胆，Antigravity 在工作流整合（先生成 mockup 再写代码）上独特。实践中最优路径是多模型协作——Claude 做主力工作马，Gemini/GPT 做外部顾问获取不同视角。这和 [[智能体分工]] 的逻辑一脉相承。

**Skills 把 vibe building 从随意变为系统化**：视频中最有工程价值的部分不是模型对比本身，而是展示 Skills 如何改变产出质量。Frontend design skill 压制 AI 默认审美，品牌 voice skill 锁定个人语言风格，转化架构 skill 约束页面结构——三个 Skill 叠加后，一次提示的产出从"典型的 AI 紫渐变页面"变为"接近生产级的转化页面"。这印证了核心主张：**约束不是限制能力，而是让能力在正确的轨道上释放**。前期做"无聊的研究"（建 Skills），后期一次提示即出高质量结果——这正是 [[复利工程]] 的精确体现。

**文案 > 设计的转化率洞察**：视频指出 vibe coding 社区普遍忽视 copy 而专注 visual，但决定转化率的核心瓶颈通常是文案。这和"内容即 UX"的判断一致——在 AI 把视觉执行成本压到零后，文字质量成为最后的差异化变量。[[Vibe Building]] 作为新概念，正是把 vibe coding/marketing/designing 的界限消融后，重新强调判断力和系统化准备的价值。

### 规范驱动开发：从 vibe coding 到工程化交付

[[BV1VczqBREQ8-亚马逊Kiro团队规范驱动开发]] 提供了从"人肉护栏"到"系统护栏"的完整方案，核心论据在三个层面：

**Vibe coding 的根本问题是人肉护栏**：当前 AI 编程依赖操作者实时纠偏——"agent 说完成了但测试没通过"是常态。Kiro 团队把这个问题归因为缺乏结构化流程：没有需求定义、没有验收标准、没有设计评审，agent 直接从 prompt 跳到代码，质量完全取决于操作者的警觉性。规范驱动开发用三阶段流程（需求→设计→执行）替代人肉纠偏，把质量保障从"执行时检查"左移到"设计时决策"。

**EARS→属性测试的贯穿线**：这是视频中最有工程价值的创新。EARS 格式（"当[条件]时，系统应[行为]"）让需求既人可读又可解析为系统属性，属性测试框架再用自动生成的输入尝试证伪。如果需求→属性→测试→代码的链条成立，"通过测试"就等于"满足需求"——这比传统"先写代码再补测试"的流程更可靠。这和 [[AI Agent自验证循环]] 的逻辑一脉相承，但把验证信号从代码层提升到需求层。

**MCP 和 steering 作为规范流程的放大器**：MCP 不只是聊天辅助，应在规范流程的每个阶段使用——需求阶段从任务管理器拉已有需求，设计阶段搜索同类产品和 API 文档，执行阶段获取最新技术参考。Steering 文档（等同 Cursor Rules）持久化项目偏好和技术决策，避免 agent 在长会话中遗忘或偏离。两者组合让规范驱动开发不依赖单个操作者的记忆和判断。

**隐含偏见问题**：视频中最有警示价值的发现是——用户在 prompt 中无意提到的技术偏好（如"用 S3 存储会话"）会绑定 agent 的整个决策链，即使存在更优方案。解决方案是主动要求 agent 提出替代方案（"这是惯用做法吗？"），这和 [[驾驭工程]] 的"约束中激发能力"一致——但这里的约束不是限制 agent 做什么，而是限制 prompt 中的隐含假设。

### 原型优先与个人OS：PM视角的AI工作流

[[BV1GAzqBWEWx-AI产品经理如何用AI做原型设计战略和个人OS]] 提供了三个真实PM的AI工作流实测，核心发现在两个层面：

**原型优先开发**：PM用AI做原型的速度超过设计师做Figma mockup——这改变了产品验证的节奏。传统流程是PRD→Figma→开发，AI让PM可以跳过中间步骤直接出可交互原型。类比数据分析领域的民主化（Mixpanel/Amplitude让PM自己跑数据，分析师聚焦高价值问题），AI原型让PM自己出原型，设计师聚焦高价值设计判断。向VP展示原型比展示文档清单有效得多——这是 [[上下文工程]] 在沟通场景的体现：原型提供更丰富的上下文（视觉+交互+场景），减少理解偏差。

**个人OS作为上下文管理的终极形态**：三位PM各自构建的系统（Claude Project模板+调研、Obsidian+Cursor、Claude Code+Skills）形态不同但本质相同——每个人都在构建自己的个人AI产品，自己既是用户也是产品经理。核心架构是三层：行动层（Skills/MCP/APIs）→ 任务层（Obsidian看板/Linear）→ 记忆/知识层（目标文件/会议记录/偏好）。这印证了 [[上下文工程]] 的核心论点：**精准上下文 > 大量信息**。目标文件让AI对齐你的长期方向，偏移检测让AI在你跑偏时提醒你——这不是"AI更聪明"，而是"AI有更好的上下文"。

**元洞见**：几乎不需要vibe coding，大部分工作是组织markdown文件和管理上下文。"If I can summarize what I've learned about AI, it's all text files all the way down." 这和 [[驾驭工程]] 的核心主张一致——决定AI效果的不是工具数量，而是你如何组织信息让AI使用。

### 主动式 Agent：从"工具"到"员工"的思维跃迁

[[BV1paf9BTEBk-OpenClaw现场演示如何使用]] 提供了开源 Agent 框架 Claudebot 的实操实录，核心发现在三个层面：

**"入职培训"作为上下文工程的极致应用**：Alex 的做法是把所有个人信息、业务目标、工作偏好灌入 Agent 记忆，然后设定"主动式"期望——不需要我指令，自己发现任务并执行。这本质上是 [[上下文工程]] 的完整实践：不是"给 AI 一个好 prompt"，而是"给 AI 一个完整的人格和使命"。Agent 的记忆能力让这种上下文投入产生复利——每一次对话都强化已有上下文，下一次行动更精准。这和 [[复利工程]] 的逻辑完全一致。

**挖掘 unknown unknowns 才是真正的杠杆**：大多数人使用 AI 只做想到的事。Alex 的方法论是反复问 Agent"基于你对我的了解，你还能为我做什么？"——竞品监控、内容复用技能、自主功能开发，都是 Agent 自己提出的。这揭示了主动式 Agent 的核心价值不在于执行效率，而在于**发现人类认知盲区中的任务**。

**安全是主动式 Agent 的阿喀琉斯之踵**：Agent 越主动、权限越大，提示注入的杀伤力越大。当前最务实的防护是权限隔离——不给关键账户权限、创建独立邮箱、从最小权限逐步扩展。但这只是权宜之计，不是根本方案。提示注入是 LLM 架构层面的根本问题——模型用同一个表示空间处理指令和数据，没有结构化的隔离机制。这和 Claude Code 的安全设计形成对比：Claude Code 有完整的纵深防御体系（路径随机化、Key 清除、TOCTOU 防御），而开源 Agent 框架目前几乎没有系统性的安全机制。

**模型层分工的工程智慧**：Opus 做大脑（思考和决策），Codex 做肌肉（代码编写和执行），避免在单一模型上耗尽额度。这和 [[智能体分工]] 的逻辑一致，但在模型层面而非工具层面——同一 Agent 内部用不同模型处理不同子任务，比多 Agent 协作更轻量。

### AI 产品设计中的"引导 vs 自由"张力

[[BV1G3zXBPEUk-ClawdBot席卷硅谷最新AI工具]] 提供了 AI 产品 UI 设计的完整迭代实录，核心发现在两个层面：

**从结构化到极简的退行**：Claude Co 的 UI 经历了四次重大方向调整——工作流导向（结构化输入/输出界面）→ 引导式分类（按分析/文档等分类，每种有不同参数）→ 向导式创建（点击创建文档、设定页数，展示大量 UI 元素）→ 最终的极简聊天+任务列表。每一次"加引导"的尝试都失败了，原因都指向同一个问题：**在 2025 年，让用户填表式地描述需求，不如让用户自然语言地描述需求**。这和 [[驾驭工程]] 的核心逻辑一致——不是给 AI 更多约束，而是给 AI 正确的约束。Claude Co 的经验说明，对 AI 产品而言，"正确的约束"往往是**更少的 UI 约束，更多的工作流约束**（如定时任务、文件夹挂载、Skill）。

**内部 dogfooding 的双重海拔**：Anthropic 的内部反馈文化是 Claude Co 和 Claude Code 成功的重要因素，但内部和外部反馈的海拔不同——内部用户给交互层面的深层反馈（"这个动画时机不对"），外部用户给功能层面的使用反馈（"这个能不能做 X"）。两者互补，缺一不可。这印证了 [[原型优先开发]] 的核心逻辑：快速出原型→内部验证交互→外部验证功能→快速迭代。

**设计师角色的转变**：Jenny 的实践表明，设计师正从"产出者"转向"策展者"——AI 生成大量选项（线框图、洞察摘要、演示文档），人的价值在于判断和选择。这与 [[AI驱动的产品设计工作流]] 的核心判断一致。但 Jenny 也强调，进入设计工具做打磨和微迭代的环节**没有消失**——AI 做广度（生成选项），人做深度（微迭代到生产级）。

### 异步 Agent 范式：Claude Cowork 与非技术用户的解锁

[[BV1xEzqBVEeb-ClaudeCowork是我们所有人的ClaudeCode]] 提供了异步 Agent 范式面向非技术用户的首次大规模产品实证，核心发现在三个层面：

**Claude Cowork = Claude Code 的 UI 包装**：底层报错信息来自 Claude Code，运行在用户本地，有文件系统和 Chrome 浏览器控制权限。这验证了一个关键产品策略——**同一 Harness 可以面向不同用户群提供不同 UI**。Claude Code 给开发者终端界面，Cowork 给非技术用户友好界面，但 Agent 的核心能力（长时间运行、工具调用、异步交互）完全相同。这是 [[驾驭工程]] 在产品维度的延伸：不是改 Harness，而是改 Harness 的入口。

**异步交互的心智转换**：非技术用户习惯了同步模式——发 prompt，几分钟内等回复。Cowork 的核心差异是"交办→审查"：你可以说"分析我过去一个月的日历"，然后去做别的事，30分钟后回来看结果。这种模式对开发者已不陌生（Claude Code 就是异步的），但对非技术用户是根本性的交互范式变化。Dan 的洞察：**用户不会在第一次使用时意识到这有多有用**，需要一个学习曲线来从"对话"思维切换到"交办"思维。独立 Tab 的设计不是功能分区，而是心智分区——帮用户建立"这是不同的用法"的认知。

**Agent 原生架构四原则的实证**：Every 团队总结的原则在 Cowork 中得到验证——
1. **Parity**：当用户请求访问一个文件夹时，Agent 自动模拟了文件选择器的点击操作，而非告知"请在 UI 中手动选择"
2. **Granularity**：Skills 把功能定义从代码层推到 prompt 层，工具保持低粒度
3. **Composability**：Ken 演示了 Swiss Design + 3D Print 双 Skill 组合出"设计一把椅子并生成 3D 打印文件"的未预见能力
4. **Emerging Capability**：Felix 明确表示"我更关心人们用它做什么，而非我预想它能做什么"——产品团队主动拥抱涌现

Felix 的关键补充：**模型能力提升速度 > 工具开发速度**，因此越通用的工具设计越能从模型进步中受益——做特化工具是在和模型赛跑，必输。

### 任务系统与上下文智能：Agent 协作的基础设施

[[BV1hkFkz9E6N-Claude如何让AI直接做待办事项]] 提供了 Claude Code 内置任务系统的首次深度逆向工程，核心发现在三个层面：

**任务 = 重命名的子 Agent**：Claude Code 的任务系统不是 TODO 列表，而是拥有独立上下文的子 Agent 实例。每个任务可以传递信息、跨会话持久化（存储在 `~/.claude/` 下），这让多实例协作成为可能——一个实例做规划，一个做执行，一个做测试。这是 [[智能体分工]] 在单工具内的实现：不需要外部编排框架，通过共享任务账本协调。

**上下文智能 vs 上下文工程**：视频提出的关键区分——[[上下文工程]] 是"你给 AI 什么"（人工编排），[[上下文智能]] 是"AI 自己找到什么"（自主查询）。现实中的上下文散落在 Slack/Notion/Google Docs/代码仓库等各处，强迫人类整理成 Markdown artifact 是死路。Unblocked 这类产品（连接所有数据源、提供 MCP 接口）指向了正确方向。但核心挑战是：**任务系统不应与上下文智能混为一谈**——任务追踪回答"做什么"，上下文智能回答"知道什么"，两者正交。

**当前系统的 v1 局限**：通过现场逆向工程发现——任务是会话级的而非全局的，依赖关系仅限同会话内，缺少"待审批"和"阻塞"状态，无项目/标签/优先级元数据，无删除操作。社区会用 hack 绕过（自定义属性前缀 `engineering_*`），等官方支持后迁移。这和 [[驾驭工程]] 的核心逻辑一致：当前系统选择了最简约束（扁平 TODO），让模型自行推理任务关系——但项目管理的复杂度（分类、优先级、依赖）迟早需要结构化支持。

### 复合工程闭环：从理念到实操的完整演示

[[BV1QeZ2BZEFZ-Claude Code实战复合工程让AI越用越懂你]] 是对 [[复利工程]] 四步闭环（Plan→Work→Assess→Codify）最完整的端到端实操演示，核心发现在三个层面：

**规划阶段的工程化设计**：Compound Engineering 插件的 `workflow plan` 命令启动三个并行子 Agent——代码库研究、最佳实践研究、框架研究——各自独立上下文（5000-7000 tokens），不污染主线程。SpecFlow Analyzer 用用户角色走一遍规划，专门对付 AI 的"zoom in 太深忘记全局"的高频失败模式。这比单纯让 AI 看代码后直接规划质量高得多，但 Token 成本也显著更高。

**Playwright + Opus 4 的闭环测试**：这是视频中最有实战价值的发现——Opus 4 是第一个让 Playwright 浏览器自动化真正可用的模型。AI 可以启动浏览器、点击元素、运行 JavaScript、读取控制台日志，甚至测试 Gmail 等外部服务。最强大的特性是**发现 bug 可以立即修复并验证**——因为 Playwright 运行在 Claude Code 内部，测试失败→修复→重新测试，形成闭环。这是"用人测试"和"用脚本测试"之外的第三条路：像人一样操作，像脚本一样可重复，像 Agent 一样能修复。

**Commands/SubAgents/Skills 的清晰分层**：Karel 给出了这三个 Claude Code 机制最清晰的定位——Commands 是业务逻辑编排层（"做什么"），SubAgents 是独立上下文的并行执行单元（"只关心结果"），Skills 是即时上下文注入（"需要时才加载"）。这个分层和 [[驾驭工程]] 的三层逻辑对应：Commands 对应 Harness 的流程约束，SubAgents 对应上下文隔离，Skills 对应精准信息供给。

### Harness 工程的维护者视角与开源信任重建

[[BV1mncRznEd6-Ghostty创始人如何用AI写代码]] 提供了从基础设施巨头创始人到独立开源维护者的完整视角，核心发现在三个层面：

**Harness 工程作为日常实践**：Mitchell Hashimoto 的"harness 工程"不是理论框架，而是具体的工作习惯——每当 AI 做错事，就构建工具让它调用以预防或纠正。这和 [[AI Agent自验证循环]] 的区别在于视角：自验证循环是 Agent 运行时的内建反馈回路，harness 工程是维护者主动构建的外部防护网。两者互补——前者让 Agent 自己发现问题，后者让 Agent 无法犯特定类错误。Mitchell 的另一个关键实践是"关闭通知，Agent 不能打断你"——这是 [[驾驭工程]] 在人机协作边界的核心原则：Agent 是工具，人决定何时交互。

**开源信任模型从"默认允许"到"默认拒绝"的转型**：AI 让创建"看起来合理但实际错误"的低质量 PR 变得轻而易举，开源的信号噪声比急剧恶化。过去贡献成本本身就是质量过滤——即使代码差，贡献者也是真正努力了。AI PR 的本质区别是低努力：提交者几分钟产出，但审查者需要数小时。Ghostty 的治理演进（披露→禁令→担保系统）指向了一个更广泛的趋势：开源必须从"默认信任"转向"信任需赢得"，担保系统+连带封禁是当前最具体的方案。这催生了 [[开源信任系统]] 这一新概念。

**工程基础设施的系统性变革**：Mitchell 的判断是"这是20年职业生涯中首次看到这么多东西同时面临变革"——Git/GitHub 工作流（单体仓库+合并队列在 AI 产出量下不可行）、CI/CD（沙箱环境推升计算单元数量曲线跳变）、测试体系（AI 目标导向性会破坏不在测试覆盖内的行为）、编辑器（前所未有的用户流动性和 Cursor 的天价估值）。核心洞察：沙箱环境等非生产工作负载的增长速度是斜率跳变而非线性增长，Kubernetes 等系统将承受前所未见的压力。

### AI驱动增长闭环：从创意到A/B测试的工具链实战

[[BV1HwdjBHENb-Claude Code实战工作流]] 提供了AI驱动营销增长的完整工具链演示，核心发现在三个层面：

**约束词策略作为设计质量的杠杆**：视频中最实操的发现是，给Claude的指令精度直接决定设计产出质量。"subtle animation"远优于"add animation"，"refine the design, consistent layouts, cohesive"远优于"improve the design"。这和核心主张"约束中激发能力"完全一致——但这里约束的载体不是架构层面的工具过滤或安全默认，而是**日常交互中的用词精度**。这降低了驾驭工程的门槛：不需要构建复杂的Harness，从改变几个关键词开始就能显著提升输出。

**设计系统先行而非事后修补**：先给Claude参考网站截图让它提取设计元素，生成风格指南，然后所有后续组件基于该系统构建。这避免了vibe coding的典型问题——每个组件风格不一致、整体缺乏cohesiveness。这和 [[驾驭工程]] 的逻辑一致：提前建立约束（设计系统），比事后在代码中逐个修正效率高得多。Tailar等组件库进一步降低执行门槛——找参考组件→截图→安装→微调，而非从零生成。

**Agent即CMS的产品判断**：Humblely从Webflow→Framer→自定义代码的迁移路径，驱动力是让Agent成为CMS——Claude Code直接更新内容、A/B测试动态修改页面、CRON定时拉取数据生成报告。这在营销网站场景成立（内容变更频繁、实验节奏快），但视频忽略了复杂内容工作流（权限审批、版本回滚、多人协作）的约束。A/B测试自动化的闭环设计（数据→分析→变体建议→实验→结果）是 [[主动式Agent]] 在营销领域的具体实现。

### PM 的"多线程存在"：多个第二大脑的上下文隔离实践

[[BV1ZqBgBHEfM-AI第二大脑产品经理]] 提供了上下文工程在 PM 工作流的直接应用案例，核心发现在三个层面：

**多 Project 架构 = 手工版 RAG + System Prompt**：受访者将 Claude 和 ChatGPT Projects 作为独立上下文容器，每个预加载不同文件集（kickoff 文档、Reddit CSV、竞品定价页 PDF）和不同指令（专业 PM 角色、写作教练约束、面试官行为）。这印证了 [[上下文工程]] 的核心论点——不同工作流需要不同上下文，混在一起会互相污染。Projects 的文件+指令模式本质上是手工版的 RAG（文件即检索语料）+ System Prompt（指令即行为约束），但无需任何代码即可搭建。

**"一切皆文本"降低了上下文工程门槛**：网页打印为 PDF、Google Slides 导出为 PDF、CSV 数据直接上传——所有非结构化信息都能成为 AI 的输入。这和 [[个人操作系统]] 的 "all text files all the way down" 原则一致，但提供了更具体的实操路径：不需要刻意整理为 Markdown，PDF 就够了。

**Reddit 爬虫：非技术用户突破技术门槛的典型案例**：PM 不是程序员，但在 Claude 的逐步指导下搭建了完整的 Reddit 数据采集管线（开发者账号→Python 环境→脚本编写→数据提取），产出 34,000 行对话数据。这和 [[Vibe Coding]] 的模式一致——核心不是学编程，而是学会给 AI 正确的上下文和约束。AI 分析数据时的验证方法（要求引用原文）也呼应了 [[AI评估体系]] 的核心原则——不能盲目信任 AI 输出，需要可核查性。

## 仍然开放的分歧

1. **克制 vs 扩展的边界在哪？** Claude Code 的克制在当前阶段是合理的，但当模型能力继续提升，是否需要更多工具暴露？还是说克制本身就是永恒正确的？
2. **ForkAgent vs SubAgent 的取舍** — ForkAgent 利用服务端 Token 缓存成本极低，但上下文过长；SubAgent 空白起点成本低但需要重建上下文。哪种在更多场景下更优？
3. **企业级身份认证** — 所有基于 MCP 的 Agent 系统都面临身份认证难题，目前没有通用解决方案

## 我的立场

驾驭工程的方向是对的，但当前对它的讨论过于聚焦 Claude Code 一个样本。Claude Code 是"个人助手型"Agent 的最佳实践，但企业级多 Agent 协作、嵌入式 Agent、代码生成 Agent 可能需要截然不同的 Harness 设计。不应该把一种模式当成普适法则。

同时，驾驭工程需要与 [[复利工程]] 结合才完整。驾驭工程解决"单次执行的正确性"，复利工程解决"多次执行的累积效应"。没有复利思维的驾驭工程，每次都从零开始；没有驾驭约束的复利工程，方向偏了还越跑越快。两者的交汇点在于：**在最低价值阶段拦截问题**——这正是驾驭工程的"约束"和复利工程的"杠杆"的交汇。
