# Ghostty创始人：我现在如何用AI写代码？

## 一句话摘要

Mitchell Hashimoto 从 HashiCorp 联合创始人到 Ghostty 终端开发者的完整心路，以及他对 AI 如何重塑编程工作流、开源治理和软件工程基础设施的深度思考。

## 核心观点

- **AI Agent 的正确用法不是让它替代你思考，而是让你选择思考什么**——把不需要思考的任务委托给 Agent，自己专注于真正需要判断力的问题
- **开源的默认信任模型已被 AI 击溃**——过去"谁都能提 PR"靠的是贡献成本作为自然门槛，AI 消除了这个门槛，开源必须转向"默认拒绝，信任需赢得"的模型
- **约束是更好软件的催化剂**——Vagrant 选 VirtualBox 不选 EC2 是因为没钱，这个约束反而塑造了产品形态；最佳工程师是工作时专注、不刷社交媒体的人
- **几乎所有工程实践都将被重塑**——Git/GitHub 工作流、CI/CD、测试体系、代码审查，都在 AI 代码产出的压力下面临根本性变革
- **创业比你想的长得多，需要适度傲慢**——想象做十年，既要有足够自信认为自己能比别人做得更好，又不能傲慢到对变化视而不见

## 详细笔记

### 从自学编程到 HashiCorp 创立

Mitchell 12-13 岁自学编程，动机是做游戏相关网站。没有钱买专业工具，开源是唯一出路。打印了 PHP 手册前 30-40 页，每天上学路上读，几周后才突然理解"变量"是什么——"12 岁根本不会在任何语境下听到'变量'这个词"。

大学期间收到一封邮件问要不要做 Ruby on Rails 程序员，以为是诈骗，但对方在洛杉矶就去了——结果是一家 Rails 咨询公司，每两个月换一个客户，大量接触不同技术和场景。

在咨询公司遇到一位运维高手：拔掉他的鼠标逼他学键盘操作，装 screen 逼他学终端复用，装包管理器逐步带入基础设施世界。同时加入华盛顿大学的 Seattle 项目（分布式计算研究），**完全失败了**，但把缺失的组件写进笔记本——这些组件后来成了 HashiCorp 的产品线。

Armon（联合创始人）发邮件问"要不要做创业公司？"Mitchell 两分钟内回复"好"。

### HashiCorp 产品线与商业探索

**产品演进**：Vagrant（可复现开发环境）→ Packer（镜像构建，解决冷启动问题）→ Consul（服务发现与组网）→ Terraform（基础设施即代码）→ Vault（密钥管理）→ Nomad（调度器）

Vagrant 选 VirtualBox 而非 EC2 的原因：大学生没钱。这个约束塑造了产品——"软件工程中很大一部分是约束，和约束共处能创造更好的软件"。

**商业化的曲折**：前四年没有真正的可复现商业模式。第一个商业产品 Atlas 彻底失败——问题不是技术，是**预算归属**：安全团队、网络团队、基础设施团队、DevOps 团队互相推诿，没人愿意付钱。"公司想为软件付钱，但他们会为'谁的预算来付'而战。"

转折点：一次糟糕的董事会后，Mitchell 和 Armon 闷头开车回办公室，白板上做了个思想实验——"如果没有沉没成本，今天我们会怎么做不同？"答案：按产品做企业版，先做 Vault。周末决定全部转向，周一全员会议宣布。**没人辞职**，反而团队因为有了明确方向而士气高涨。

### 云厂商的真实面目

- **AWS**：极其傲慢，每次互动都感觉"他们在施舍你"。威胁说如果不合作就自己建竞品。Terraform 的 AWS Provider 有 5 个全职工程师（年成本约百万美元）维护纯开源集成，AWS 完全不帮忙。直到 Mitchell 团队威胁要公开宣布废弃 AWS Provider，AWS 才开始配合。
- **Microsoft**：最好的商业伙伴。每次会议第一个问题是"我们怎么双赢？"最先支持 Terraform Provider，多年来态度一致。
- **Google Cloud**：技术最好，架构思维最先进——自动生成 Terraform Provider 的集成质量很高。但**没人关心商业**，一谈联合销售、配额归属就谈不下去。

### VMware 收购未遂

公司成立约一年时，VMware 提出收购。过程：基层 BD 邮件 → VP 工程师碰面 → 高管晚餐 → "合作"讨论 → "如果你有 VMware 资源会怎么做"的假设性问题。口头报价约 2000 万美元——对 23 岁的创始人是"梦想终结金额"：个人生活彻底改变，但产品在 VMware 体系内毫无重要性。最终 VMware 董事会投票未通过。"如果那票过了，Terraform 可能永远不会存在。"

### Ghostty：从玩具项目到严肃产品

**起源反常识**：不是"找到问题再找技术"，而是"找到技术再想能做什么"。15 年基础设施经验让桌面和系统编程技能萎缩，选 Zig（更好的 C）、GPU、桌面软件，然后问"我能做什么？"——终端。

**终端的本质**：不是简单的文本框，更像是"文本内容的浏览器"。Ghostty 架构：UI 线程（窗口管理）→ IO 线程（shell 通信）→ 渲染线程（绘制画面，362 fps 采样终端状态）。**30% 是终端，70% 是字体渲染器**。

AI 给终端带来了意外红利：Claude Code、Codex 等 CLI 工具让终端使用量暴增。libghostty 项目：零依赖可嵌入终端库，MIT 协议，解决"到处都是残缺终端实现"的问题。

### AI 编程工作流

**核心原则：始终有一个 Agent 在做事。**

- 不是同时跑很多 Agent（清理 Agent 产出很累），而是至少一个 Agent 在并行工作
- 编码时让 Agent 做规划；Agent 编码时自己审查；让 Agent 做研究任务
- 不确定的高难度任务会让 Agent 竞争（Claude Code vs Codex）
- **关闭所有通知——Agent 不能打断你，你选择何时打断 Agent**

**对产出代码的态度**：Ghostty 的代码逐行审查；个人网站完全不管。AI 生成代码是否重要取决于上下文。

**从抗拒到精通的过程**：2024 年 5 月首次尝试 Claude Code，不太满意。夏天看到大量正面评价后害怕落后，开始**强迫自己用 Agent 复现手动工作**——即使更慢也坚持。逐步发现：先做规划步骤效果更好；更好的测试套件让 Agent 更可靠；CLAUDE.md 记录纠错后 Agent 不再犯同样错误。"就像有人用了一小时 Git 就断定不高效——AI 工具也需要更长时间才能熟练。"

### AI 对开源的冲击与治理

**核心问题**：AI 让创建"看起来合理但实际错误"的低质量贡献变得轻而易举，开源的信号噪声比急剧恶化。

过去开源的天然门槛是贡献成本——即使代码差，贡献者也是真正努力了，维护者愿意花时间教育。AI PR 的本质区别是**低努力**：维护者不应为提交者几分钟的 Agent 产出投入数小时审查。

Ghostty 的治理演进：
1. 要求 AI 披露（效果一般，因为低质量 PR 数量太多）
2. AI PR 禁令：无关联 Issue 的 PR 直接关闭，不看内容
3. **担保系统**（进行中）：任何人不能直接开 PR，必须由已有社区成员担保。担保者连带责任——被担保人违规，担保者及整个邀请树永久封禁。支持"举报"机制主动封禁恶意行为者。灵感来自 Lobsters 和 π 项目。

**对开源未来的判断**：开源一直是信任系统，过去是"默认信任"，现在必须转为"默认拒绝，信任需赢得"。Fork 应该更多——合并只是最简单的步骤，维护才是硬工作。

### 工程实践的未来

**Git/GitHub 可能不会以当前形式存在**：
- 单体仓库在 AI 代码产出量下面临性能瓶颈
- 合并队列对人类勉强够用，AI 10x-1000x 产出使其完全不可行
- 需要类似 Gmail 对邮件的变革——不删分支、不丢上下文、更好的信息检索

**Harness 工程**：让 AI 不做坏事的工具链。每当 AI 做错事，构建能让它调用的工具来预防或纠正。测试必须变得更广泛——AI 是目标导向的，会为了达成目标而破坏不在测试覆盖内的行为。

**CI/CD 和基础设施**：沙箱环境（Agent 需要）正推动计算单元数量曲线跳变，Kubernetes 等系统将承受前所未见的非生产工作负载压力。

### 关于最佳工程师和招聘

最佳工程师的特征：**没有社交媒体，朝九晚五，工作时间完全锁定**。不在 GitHub 上有公开贡献，在没听过的公司工作过——但工作时间内产出极高。"在社交媒体上的每一分钟都是从其他事情上偷来的，而进入心流状态需要时间。"

AI 时代招聘：必须会使用 AI 工具，但不必用于一切。关键能力是**判断何时该用何时不该用**。原型验证是最佳场景——用 AI 快速出 slop 验证想法，比人工花一周做注定扔掉的东西高效得多。

### 给创业者的建议

创业比想象的长得多（想象十年而非五年）。需要适度的傲慢——相信自己做十年能比别人更好，但不能傲慢到看不见变化。很多酷想法的人会很快燃尽。

## 我的评注

- **赞同**："始终有一个 Agent 在做事"是当前最实用的 AI 工作流原则。它的精髓不在于 Agent 多强，而在于**人选择思考什么**——把非思考性任务委托出去，释放注意力给真正需要判断力的问题。这比"AI 替我写代码"的叙事更准确也更有操作性。
- **赞同**：开源信任系统必须从"默认允许"转向"默认拒绝"的判断。AI 之前，贡献成本本身就是质量过滤；这个屏障消失后，治理机制必须补偿。担保系统是合理的方向——让贡献者之间有声誉绑定。
- **质疑**：Mitchell 对"最佳工程师是 9-to-5 无社交媒体的人"这个观察可能存在幸存者偏差。他在 HashiCorp 和基础设施领域的经验未必适用于所有领域——某些需要快速跟踪前沿变化的岗位（如 AI 应用层），社交信息流本身就是工作输入的一部分。
- **关联**：这个视频和 [[AI Agent自验证循环]] 以及 [[上下文工程]] 形成有趣的互补——Mitchell 的"关闭通知、人打断 Agent 而非反过来"原则，本质上是在设计人机协作的上下文边界。他说的"harness 工程"和自验证循环是同一思路：构建让 Agent 自我纠错的脚手架，而非事后审查。
- **待深入**：担保系统在实际运作中的效果如何？邀请树连带封禁的机制是否会导致社区分裂而非净化？这是一个值得持续跟踪的实验。
