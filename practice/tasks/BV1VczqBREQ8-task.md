### 任务 1：用 EARS 格式重写现有需求

**任务目标**：将一个正在开发中的功能的自由文本需求，转化为 EARS 格式，消除歧义。

**输入材料**：
- 一个你当前正在开发的功能的自然语言描述（可以是 PRD 片段、issue 描述、或你给 AI 的 prompt）

**执行动作**：
1. 列出该功能所有你期望系统做的行为
2. 对每条行为，用"当……时，系统应当……"句式重写（功能需求用 When 句式，非功能需求用"系统应当始终……"句式）
3. 对每条 EARS 需求，检查：去掉所有实现细节（"用什么技术"），只保留"做什么"
4. 找一条原始描述，对比 EARS 版本，列出原始描述中有哪些歧义点被消除了

**产出物**：一份 EARS 格式需求文档 + 一份歧义消除对比表

**验收标准**：
- [ ] 每条需求都符合 EARS 句式
- [ ] 需求中不含任何实现选型（技术栈、具体工具名）
- [ ] 一个没参与讨论的人阅读后能无歧义理解系统行为
- [ ] 至少识别出 3 个原始描述中的歧义点

**常见失败**：
- 把"系统应当用 Redis 缓存"当需求写——这是实现，不是需求
- 只写了 happy path，没写异常和边界条件
- EARS 句式写出来了但条件部分仍然含糊（"当系统繁忙时"——多忙算繁忙？）

### 任务 2：对 prompt 做去偏见审计

**任务目标**：识别并移除你最近 3 次给 AI 的 prompt 中隐含的技术选型偏见。

**输入材料**：
- 你最近 3 次与 AI 编程工具的对话记录（或 prompt 文本）

**执行动作**：
1. 逐条审阅每个 prompt，标记所有包含特定技术选型的句子（"用 X 实现""通过 Y 方式""基于 Z 框架"）
2. 对每个标记，判断：这是需求约束还是个人偏好？如果是偏好，问 AI 这是否是最佳方案
3. 重写 prompt：把"用 X 实现 Y"改为"实现 Y，用什么方式请研究后推荐"
4. 记录偏见模式：你的偏见倾向于哪类？（偏好熟悉的工具？偏好最新的工具？偏好某种架构风格？）

**产出物**：去偏见后的 3 条 prompt + 个人偏见模式记录

**验收标准**：
- [ ] 每个 prompt 中的技术选型标记完毕
- [ ] 至少发现 2 个隐含偏见
- [ ] 重写后的 prompt 不含不必要的实现锁定
- [ ] 偏见模式记录中有可复用的识别规则

**常见失败**：
- 认为"我写的就是需求"而不质疑——讲者自己演示时也犯了这错
- 去偏见后变成完全不含约束的模糊描述——去偏见不是去约束，是去不必要的实现锁定
- 只审阅了一次就结束——偏见需要多次审阅才能发现模式

### 任务 3：从 EARS 需求提取属性测试

**任务目标**：将 3 条 EARS 格式需求转化为可执行的属性测试（property-based testing）。

**输入材料**：
- 任务 1 产出的 EARS 需求文档（或任意 3 条 EARS 需求）

**执行动作**：
1. 对每条 EARS 需求，提取系统应满足的不变量（正确性属性）
2. 用你使用的语言的属性测试框架（Python/Hypothesis、JS/fast-check、Go/rapid）写出属性测试
3. 运行测试，检查是否有属性在初始实现上就失败（说明实现或属性定义有问题）
4. 记录：哪些需求的属性容易提取？哪些需求本身表述不够精确导致属性模糊？

**产出物**：3 个属性测试文件 + 需求-属性映射表

**验收标准**：
- [ ] 每条需求至少有一个对应的属性测试
- [ ] 属性测试用随机输入运行至少 1000 次不失败
- [ ] 映射表标注了哪些需求需要补充条件描述才能提取精确属性
- [ ] 故意引入一个 bug，属性测试能检测到（证明测试有效）

**常见失败**：
- 写的属性太弱（如"函数不抛异常"），任何实现都能通过
- 需求的条件部分太模糊，提取的属性无法精确表达
- 忘了测试属性的完整性——属性测试只能验证你写了属性的部分

### 任务 4：搭建 Spec-Driven Development 的最小可运行流程

**任务目标**：在一个真实的小功能开发中，完整走一遍需求→设计→任务→实现→验证→回流的闭环。

**输入材料**：
- 一个待开发的功能（建议选择 1-2 天可完成的小功能）

**执行动作**：
1. 写 EARS 需求（不少于 5 条）
2. 画系统架构，标注每条需求对应的模块和接口，列出约束条件
3. 配置至少一个 MCP 服务器，让 AI 在设计阶段查阅外部文档
4. 分解为可执行任务，每个任务包含验收标准和测试用例
5. 逐个执行任务，每完成一个检查测试
6. 全部完成后运行属性测试，如失败则回流到需求层修正

**产出物**：完整的规格文档（需求+设计+任务）+ 通过属性测试的代码 + 流程复盘

**验收标准**：
- [ ] 需求→设计→任务→实现全链路有文档记录
- [ ] AI 在需求或设计阶段使用了 MCP 获取外部信息
- [ ] 代码变更可追溯到需求条目
- [ ] 属性测试全部通过
- [ ] 复盘中记录了至少一个"在设计/实现中发现需求遗漏并回流"的实例

**常见失败**：
- 跳过设计直接从需求到实现——设计阶段是发现需求遗漏的关键
- AI 说"完成"就接受——必须看测试结果
- 回流时直接改代码不改需求——问题会再次出现

### 任务 5：为团队定制规格模板和 Steering 规则

**任务目标**：创建适配你团队工作方式的规格模板和 AI 行为约束文件。

**输入材料**：
- 团队当前的代码规范、测试要求、提交规范、部署流程
- 过去项目中反复给 AI 重复说明的偏好列表

**执行动作**：
1. 创建需求模板：在 EARS 基础上，加入你的业务特有的需求分类（安全、合规、性能等）
2. 创建设计模板：包含架构图区域、约束条件区域、属性定义区域、测试策略区域
3. 创建任务模板：包含验收标准、关联需求 ID、关联属性测试
4. 写 Steering 规则：测试覆盖率下限、commit 规范、代码风格偏好、禁止模式（如"不得在需求中指定实现技术"）
5. 用一个小功能验证模板可用性

**产出物**：需求模板 + 设计模板 + 任务模板 + Steering 规则文件

**验收标准**：
- [ ] 模板覆盖从需求到验收的完整流程
- [ ] Steering 规则包含至少 5 条去偏见规则
- [ ] 模板在实际小功能试用中不需要大量手动补充
- [ ] 团队成员能在 10 分钟内理解模板结构

**常见失败**：
- 模板太重，每个字段都要填——模板应该是骨架，不是问卷
- Steering 规则太笼统（"写好代码"）——规则必须具体到可执行
- 一次就想做到完美——模板应该迭代，先最小可用再逐步完善
