## 需求编写检查清单

- [ ] 每条需求都使用 EARS 句式（When...shall... 或 shall always...）
- [ ] 需求中不包含任何实现选型（技术名、工具名、架构模式名）
- [ ] 条件部分可客观判定，不含"适当""合理""足够"等主观词
- [ ] 覆盖正常流程、异常流程和边界条件
- [ ] 非功能需求（性能、安全、可用性）有对应条目
- [ ] 需求之间无冲突
- [ ] 一个不参与讨论的人阅读后能无歧义理解系统行为
- [ ] 是否识别了原始需求未明说的边界条件？
- [ ] 是否把隐含需求转成独立 EARS 条目？
- [ ] 是否输出了歧义消除对比表？
- [ ] 是否区分了"业务行为"与"实现选型"？

## Prompt 去偏见检查清单

- [ ] 审阅 prompt 中是否包含特定技术选型（"用 X""基于 Y""通过 Z"）
- [ ] 区分"需求约束"和"个人偏好"——需求约束保留，个人偏好交给 AI 推荐
- [ ] 是否问了 AI "这是最佳方案吗？有哪些替代？"
- [ ] AI 是否通过 MCP 或搜索查阅了最新文档后再推荐
- [ ] 去偏见后的 prompt 是否仍保留了原始需求意图

## Spec-Driven 流程执行检查清单

- [ ] 需求阶段：EARS 格式，已去偏见，已做完整性审查
- [ ] 设计阶段：架构覆盖所有需求，有约束条件，有测试策略，MCP 辅助验证
- [ ] 属性阶段：核心需求有属性测试，属性可 falsify
- [ ] 任务阶段：每个任务有关联需求和验收标准
- [ ] 实现阶段：逐个执行，每步验证测试，不看 AI 的"完成"声明
- [ ] 回流机制：问题回流到正确层级，不是在代码层打补丁
- [ ] 交付：代码-需求映射完整，属性测试全部通过

## Brownfield 规格化检查清单

- [ ] Steering 规则文件已创建，包含去偏见规则
- [ ] MCP 服务器已配置（代码搜索 + 文档访问）
- [ ] 至少 1 个核心模块完成反向工程（代码→EARS 需求→属性测试）
- [ ] 反向工程的需求经人工验证（AI 可能把实现当需求）
- [ ] 新功能开发走完整规格流程
- [ ] 每次迭代有回顾记录

## AI "完成"声明不信任检查清单

- [ ] 任务有显式测试用例，不只是"AI 说完成了"
- [ ] 测试已实际运行，不是 AI 说"测试通过"
- [ ] 边界情况有测试覆盖
- [ ] 属性测试全部通过
- [ ] 编译/构建成功（不是 AI 口头确认）
- [ ] 如有 CI，CI 绿灯
