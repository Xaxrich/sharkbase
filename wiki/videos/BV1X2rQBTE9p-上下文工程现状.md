# 上下文工程现状：Agentic RAG、上下文腐烂、MCP、SubAgent

## 一句话摘要

Contextual AI 研究总监在 NeurIPS 现场回顾 2024 年上下文工程的核心进展：Agentic RAG 成为新基线、子代理需要强制终止条件、MCP 加速原型但加剧上下文腐烂，整个领域仍处于原型阶段，明年将走向完整系统设计。

## 核心观点

- **Agentic RAG 已取代普通 RAG 成为新基线**：仅做查询改写（拆分子查询、并行检索、合并结果）就能大幅提升性能，这是最低门槛的升级
- **上下文腐烂（Context Rot）是真实且量化的威胁**：百万 token 上下文中 7000 token 的检索精度只有 30%，每多塞一个不相关工具都在恶化性能
- **子代理必须有终止约束**：无限制的子代理会反复检查自己的工作、穷尽搜索每个角落，在大规模数据上既浪费又危险；通过 RL 奖励结构或系统提示词强制限制轮次是必要的
- **MCP 加速原型但引入上下文膨胀**：10+ 个工具的 JSON 描述很快撑爆上下文窗口；实用做法是先用 MCP 快速验证价值，再迁移到精简的 API 调用
- **完整系统的设计模式是下一年的方向**：当前讨论仍停留在单个组件（记忆系统、reranker、压缩策略），明年将出现端到端的系统级设计模式

## 详细笔记

### 小模型的困境

- OpenRoute 数据显示：开放模型中，小模型（<15B）市场份额持续下降，中等模型（57-70B）上升，大模型持平；闭源模型份额持续走高
- Apple Intelligence 作为小模型标杆今年被广泛认为失败；Gemini Nano 在 Chrome 中的部署也进展缓慢
- 小模型的实际价值在专用组件上：reranker 因延迟约束，小就是好——但业界首个指令跟随 reranker 直到今年 3 月才出现，因为传统观点认为指令跟随需要大模型，影响延迟预算

### Agentic RAG：从查询改写到并行检索

- 普通 RAG 的"死亡"和 Agentic RAG 的崛起——争论本身意义不大，因为 Agentic RAG 在几乎所有场景下都更好
- 关键第一步：**查询改写**——将用户查询拆分为子查询，分别检索文档后合并结果，仅此一步就能大幅提升性能
- Contextual AI 的 Fast Context 模型创新：
  - 训练模型支持 6-8 路并行搜索（常规工具调用只有 1-4 路）
  - 引入有限代理性（limited agency）——通过 RL 激励代理在有限轮次内返回答案，避免无限搜索

### SubAgent：今年最重要的工程模式

- **核心发现**：在 Retail Universe 黑客松（10 万文档、PDF/日志/表格/Parquet）中，无约束子代理会：
  1. 疯狂扩展搜索轮次，试图翻遍每一块石头
  2. 反复检查自己的输出，陷入自我验证循环
- **解决方案**：轮次限制 + 子代理验证约束，无论是通过 RL 奖励还是系统提示词显式指令
- 黑客松结果：AI 系统得分 ~25-29，人类基准 ~23，AI 已超越人类但方案路径与人类不同（甚至发现了标准答案中的错误）
- 领先方案：第一名用 Mixbread + Claude，第二名用 Cursor 自带组件

### 上下文腐烂与 Reranker

- 上下文腐烂是当前最被广泛认知的上下文工程问题——每个从业者都在博客中讨论
- **量化指标**：百万 token 上下文中仅检索 7000 token，精度约 30%——有了具体数字才能跨方案比较
- Reranker 在上下文工程中的双重作用：
  - 初始检索阶段：追求高召回率（recall），多捞相关文档
  - 上下文窗口阶段：追求高精度（precision），只塞最相关的，避免腐烂

### MCP：快速原型与上下文膨胀的矛盾

- MCP 是今年上下文工程的最大驱动力之一，但也是最大漏洞之一
- **核心问题**：大量工具的 JSON 描述直接撑爆上下文窗口——10+ 个工具就开始出现明显的上下文腐烂
- 实用策略：用 MCP 快速原型验证价值，然后迁移到精简 API 调用以降低复杂度和上下文开销
- MCP 选择本身已经是上下文工程问题——Contextual AI 用子代理来选择应该激活哪些 MCP Server
- Anthropic 推出的 MCP 注册表（registry）设计为供代理读取而非人类浏览
- 安全考量：即使代理能力增强，MCP Server 的选择仍应由人类把关

### 提示词优化：Jedi 与 ACE

- **Jedi**：原始 DSA 思路的进化版——设定目标，让 LLM 通过输出反馈自我优化提示词，类似训练但只改提示词不动权重；加入进化/遗传元素：多次采样，选择最优幸存者
- **ACE（Agent Context Engineering）**：在金融等复杂文档上表现更好
  - 关键创新：不重写整个提示词，而是在当前提示词上做小幅度修改
  - 对比：Jedi 式的"压缩-展开-压缩-展开"循环会丢失信息，导致性能显著下降

### KV Cache 与长对话退化

- KV Cache 同时服务两个目的：成本效率 + 为代理提供更稳定的行动环境
- 长对话中代理容易混乱，导致幻觉和性能退化——KV Cache 有助于缓解
- 现实问题：Cursor 用户在对话过长时主动开新窗口，本质是手动上下文压缩——因为不信任模型的自动压缩
- 各前沿模型（OpenAI、Anthropic、Gemini）都在模型内部做 compaction，但效果仍不够可靠

### 领测与趋势

- **被低估的**：完整系统级设计——当前讨论都停留在单个组件优化，明年将出现端到端的系统设计模式
- 基准测试趋势：SWE-bench 类的复杂基准出现后很快被饱和，需要更多工业级基准（大规模数据、无法塞入上下文窗口的真实场景）
- Anthropic 在上下文工程领域的博客和工具使用模式指南被认可为高质量参考

## 我的评注

- **赞同**：子代理必须有终止约束——这是我在工程实践中反复踩的坑。无限轮次的子代理不仅浪费 token，更危险的是会"过度验证"产生看似合理实则偏离的结论。轮次限制是简单但极有效的护栏
- **赞同**：量化上下文腐烂（百万上下文 7000 token 检索精度 30%）比抽象讨论"上下文会退化"有价值得多。工程问题需要工程指标
- **质疑**：对"小模型已死"的论断过于悲观。OpenRoute 数据反映的是通用模型市场，而视频自己也承认 reranker 等专用组件上小模型反而更优。真正的趋势可能是**分层架构**——大模型做推理，小模型做检索和路由，而非简单的大胜小败
- **质疑**：MCP "先用后迁 API"的策略暗示 MCP 本质上是验证工具而非生产架构。如果最终都要迁走，MCP 的长期定位是什么？视频没有回答这个关键问题
- **关联**：视频中提到的"主动开新窗口"行为与 [[上下文工程]] 中上下文压缩的讨论直接呼应——当前模型的自压缩还不够可靠，人工干预仍是常态。这与 [[MVP思维]] 中"先跑通再优化"的思路一致：先接受手动压缩，等模型能力提升再自动化
